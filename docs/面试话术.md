# 高并发售票系统 · 面试话术

## 一、开场项目陈述（30 秒）

> 这是仿 12306 的高并发售票系统，后端我一个人写完。要解决三件事：并发下不超卖、Redis 和 MySQL 最终一致、查余票不压垮数据库。方案是 Redis 加 Lua 原子扣减防超卖，事务消息加三个定时对账任务保一致，三级缓存接读流量，外面套两级令牌桶限流。最近补齐的三块：加了业务指标监控、起第二个实例验证分布式锁真的互斥、把 Redis 从单实例迁到 6 节点集群并实测了故障转移。写压测 1000 线程抢 100 张，成交恰好 100 单，库存归零，零超卖。

## 二、项目全景

| 维度 | 情况 |
|---|---|
| 业务链路 | 下单、支付、退票退款、退款对账、限流五条 |
| 技术栈 | Spring Boot 4.1.2、JDK 21、MyBatis 原生 XML、MySQL 8、Redis 8.10、RocketMQ 事务消息、Actuator + Micrometer |
| 缓存 | Caffeine 本地 1 秒 → Redis → DB，三级 |
| 演示数据 | 一条车次 G1001，三站两区段，二等库存 100、一等 20、商务 5 |
| 压测 | 写 1000 线程、读 2000 样本；多账号压测 100 并发 |
| 部署 | 应用双实例 8081/8082（验证分布式锁）；Redis 3 主 3 从集群，跑在虚拟机 7000~7005 |

规模不大，但五条链路是一条完整、能跑通的链路：抢票、付款、退票、退款到账，每一步失败都有补偿兜底。**而且关键能力都留了实测证据，不是"方案里有"。**

## 三、九个核心难点

### 1. 不超卖

**难点**：1000 个请求同时抢 100 张票，任何"先查库存再扣库存"的写法都会超卖，因为两条 Redis 命令中间有时间差。

**解法**：把判断和扣减塞进同一个 Lua 脚本。Redis 执行 Lua 期间不会穿插执行其他命令，所以不存在两个线程同时看到"还有票"的情况。另外两道防线：订单表对同乘客同车次建唯一索引，订单状态靠 CAS 条件更新。

**为什么这么解**：不用分布式锁，因为锁的粒度比 Lua 大、开销也更高；也不用数据库悲观锁，行锁会把并发压成串行。

**数据**：1000 线程抢 100 张，成交 100 单，DB 和 Redis 库存都是 0/0，第 101 单不存在。

**坑**：最早我写的是先 `get` 再 `decr`，压测直接多卖出十几张。改成单脚本才归零。

> 如果面试官问，我可以展开讲讲 Lua 里为什么三个 key 要带同一个 hash tag。

### 2. Redis 与 DB 最终一致

**难点**：扣减分散在 Redis、MQ、MySQL 三处，任何一步断掉都会留下"Redis 扣了、订单没建"这种脏数据。

**解法**：先写一条"扣减中"的流水，再用事务消息驱动后续步骤，成功提交、失败回滚；应用宕机没给结果时 Broker 回查流水状态。再加三个定时对账任务扫中间态，按判定矩阵补偿。

**为什么这么解**：链路短、库存只有一份，用本地状态机加持定时对账就够了，上 XA 或 Seata 的成本远大于收益。

**数据**：扣减对账扫中间态超 5 分钟的流水，每轮最多 200 条；退款对账扫退款中超 300 秒的记录，每轮 20 条；超时关单扫已确认超 900 秒的订单。

**坑**：对账一开始我扫的是订单表，后来发现订单只是状态镜像，拿不到渠道退款单号，根本判不出"渠道到底受没受理"。改成扫退款流水表才对。

> 如果面试官问，我可以展开讲讲四类渠道结果分别对应什么动作。

### 3. 读流量不压垮数据库

**难点**：抢票高峰余票查询比下单多一个数量级，全打到 MySQL 会直接把连接池占满。

**解法**：三级缓存。Caffeine 本地 1 秒 TTL，命中直接返回；未命中查 Redis 的 stock Hash，跨区段取最小值；再没有才回源数据库并回填。查不存在的车次在 Redis 写空值标记，TTL 60 秒，挡住穿透。

**为什么这么解**：本地缓存 1 秒是刻意选的折中——1 秒内重复查询几乎零成本，最多容忍 1 秒延迟，而下单的正确性完全不依赖本地缓存，所以延迟不会导致超卖。

**数据**：2000 样本，2442 TPS，平均 54 毫秒，三级缓存全部实测命中。

**坑**：一开始压测只看 TPS，看不出到底命中哪一级。后来在响应里加了 source 字段标明 Caffeine / Redis / DB，才确认三级都真的生效——否则很容易出现"以为走了 Redis，其实全打在 DB"。

> 如果面试官问，我可以展开讲讲空值标记和本地缓存的一致性边界。

### 4. 流量整形

**难点**：秒杀瞬间的请求量远超系统容量，全放进来会让线程池排队、连接池打满。

**解法**：两级令牌桶。内层按"用户 + 车次"限，容量 3、每秒补 1 个，专门防单个用户连点；外层按车次全局限，容量 500、每秒补 500 个，保护系统入口。全局限流在单用户限流之前执行，拒绝语义分开：全局返回"当前抢票人数过多"，单用户返回"操作过于频繁"，都是 429。限流本身异常时选择拒绝而不是放行。

**为什么这么解**：限流只做流量整形，不参与正确性判断。就算限流全放开，超卖也由 Lua 和唯一索引兜住——这条认知很关键。

**数据**：同一个 token 并发打 10 个请求，前 3 个 200，后 7 个 429，精确 3 放 7 拒。

**坑**：限流上线后第一次跑 1000 线程压测，只成交 3 单。我一开始以为是限流误杀正常用户，查下来是压测脚本 1000 个线程共用一个 admin token，全被单用户桶挡在 3 个。后来只把单用户桶临时放到 1000、全局保持 500/500，再跑一遍：成交 100 单、库存 0/0、平均 1145 毫秒，零超卖。

> 如果面试官问，我可以展开讲讲为什么限流参数不能拍脑袋定、得用压测定阈值。

### 5. 钱的部分

**难点**：支付回调是外部系统打进来的，会重复、会延迟、金额也可能被篡改，还可能用户付完钱但我这边已经超时关单了。

**解法**：统一下单拿凭证 → 模拟收银台确认 → 渠道 HMAC 签名异步回调。回调进来先验签，再校验三方金额一致（订单、流水、回调），再走幂等，最后在事务里 CAS 更新流水和订单，同订单其余待支付流水一并关闭。

**为什么这么解**：金额不匹配时**绝不能取消订单**——用户钱已经付了，只是校验不过，取消等于把用户的票抢走。这时只挂起告警，等人工或对账处理。

**数据**：边界 12 项全过；金额篡改回调返回 FAILURE、订单保持已确认；超时关单 49 秒命中并精确回补 1 张。

**坑**：同一订单连续 prepay 两次会生成两条待支付流水，旧凭证居然还能付款。后来在回调事务里批量 `casClose` 把其余流水关掉才堵住。

> 如果面试官问，我可以展开讲讲关单前为什么必须先查一次"是否已支付"。

### 6. 退票与退款对账

**难点**：退票要同时干三件事——切订单状态、回补库存、调渠道退款。顺序错了会真超卖，重试错了会重复退款。

**解法**：先定一条铁律——订单状态是"是否占座"的唯一判据，所以**状态先切、库存后补**。`applyRefund` 事务内只做插流水和 CAS（已支付→退款中），事务提交后才回补 Redis 和 DB，最后调渠道。对账则扫退款流水表，按四类渠道结果分四类动作：库存没补就补、没渠道单号就重发、查回成功只修本地状态**绝不重发**、查回处理中只刷新时间、查回不存在才允许重发、查回失败置失败并告警。

**为什么这么解**：如果渠道明明已经退款成功、只是回调丢了，再重发一次就是重复退钱，数据库的唯一索引根本拦不住——它拦的是"插第二条流水"，不是"再调一次渠道"。所以对账的本职是"查"，不是"重发"。

**数据**：退票 17 项验证全过（10 项主链路、7 项边界）；两个线程同时退同一单，一个 200、一个 400「该订单已提交退票，请勿重复操作」，回调到 3 次但状态只变一次；退款对账 7 项断言全过。

**坑**：库存回补的 SQL 是 `remain = remain + 1`，语义上不幂等，对账每重试一次就会多补一张，几轮之后库存能补成 101。后来加了 `stock_restored` 标记，并且让回补和置标记在同一个事务里，才彻底堵死。

> 如果面试官问，我可以展开讲讲为什么"处理中"这个状态不能算重试次数。

### 7. 可观测性：这个项目所有失败都是 HTTP 200

**难点**：所有业务失败都是 `HTTP 200` + `code 200`，真实结果藏在响应体的 `status`（"已取消"）和 `message`（"余票不足，抢票失败"）里。光看 HTTP 层的 QPS 和 2xx 比例，**分不出"抢到票"和"没抢到"**。

**解法**：接 Actuator，只暴露 `health/info/metrics` 三个端点；自己埋四类业务指标——下单成功、下单失败（带 reason 标签区分限流/余票不足/判重）、告警总数、对账处理量（带 task 标签区分三个任务）。

**为什么这么解**：技术指标（QPS、耗时、错误率）在这个项目里是失真的，业务指标才是真的。限流拦截、余票不足、乘车人重复，三种情况对调用方都是"失败"，但对系统的含义完全不同——一个是容量问题、一个是库存问题、一个是业务规则问题。

**数据**：12 项断言全过，`/actuator/metrics` 99 个指标，`health` 七个组件全 UP。

**坑**：首轮跑完发现 `traffic.order.success` 在指标清单里**查不到**。原因是 Micrometer 的计数器首次 `increment` 才创建，冷启动时段面板是空白的——你分不清"今天零成交"还是"指标根本没注册"。改成在构造时就预注册三个无标签指标。

> 如果面试官问，我可以展开讲讲为什么用标签区分失败原因，而不是拆成不同指标名。

### 8. 分布式锁：单实例永远验证不了自己

**难点**：三个定时任务都靠 Redis `SETNX` 保证多实例只有一个执行。但项目一直只跑一个进程——**把锁整个删掉，行为完全一样**。面试官问"你怎么证明锁起作用"，答不出来。

**解法**：给锁的 value 从常量 `"1"` 改成实例标识（`端口:8位随机码`），再起第二个实例 8082，用 `-DLOG_HOME` 隔离日志目录。两个实验：

1. **锁采样**：每秒读一次三个锁，持续 100 秒 → 任一时刻只有一个 value，跨分钟在 8081 和 8082 之间交替（证明 SETNX 只有一个赢家，且两个实例都在抢）
2. **业务互斥**：造一笔超时未支付的订单，两个实例的定时任务都会扫到 → 结果只有一个实例动手，执行次数合计 **1 次**（8081=1，8082=0），库存只回补一次（99→100，不是 101）

**为什么这么解**：value 带实例标识不是为了正确性，是为了排障——出问题第一句话是"这轮是谁跑的"。

**数据**：8 项断言全过。

**坑**：两个进程写同一个 `logs/app.log` 会互相覆盖，按天滚动也会失效，因为 logback 的锁只在进程内有效，不做跨进程文件锁。改成日志目录可由 `-DLOG_HOME` 注入，第二实例写自己那份。

**诚实边界**：这件事能证明"有锁时只执行一次"，但**"去掉锁会补成 101"是推理不是实测**——真要测得改代码、重新打包、重启两个实例、再改回来。这一点必须说清楚，不能把推理当证据。

> 如果面试官问，我可以展开讲讲 55 秒锁重叠的残余风险和数据库 CAS 怎么兜底。

### 9. Redis 集群：唯一一处"只讲过没做过"的能力

**难点**：简历上写"支持 Redis Cluster"，但从来没起过集群。最大的风险是 **Lua 脚本跨槽**——集群下脚本里的所有 key 必须落在同一个哈希槽，否则直接 `CROSSSLOT` 失败。

**解法**：虚拟机起 6 个节点（7000~7005，3 主 3 从），用 `--network host` 避免容器端口映射导致集群通告地址错乱。然后是核心验证：**hash tag**。

| key 写法 | 落槽 | 结果 |
|---|---|---|
| `stock:{G1001}:SECOND_CLASS` | 2723 | 三者同槽 ✅ |
| `deducted:{G1001}:SECOND_CLASS` | 2723 | |
| `passenger:dedup:{G1001}:1001` | 2723 | |
| 去掉花括号的三个 key | 1673 / 9138 / 2654 | 同一脚本立刻 `CROSSSLOT` ❌ |

**为什么这么解**：花括号是设计时就埋的伏笔——只对花括号内的内容算哈希，所以同一车次的 key 必然同槽。没有它，整个下单链路在集群上直接崩。

**验证**：
- **关掉旧单实例 6379 后业务照常**——这是"流量真走集群"的唯一硬证据，否则可能是它偷偷还连着老 Redis
- **故障转移**：停掉持有该车次全部 key 的主节点，从节点 12 秒接管槽位，`cluster_slots_fail:0`，下单成功；节点恢复后自动变回从节点，不抢主
- **并发**：100 个独立账号并发抢 50 张，正好 50 抢到、50 余票不足，Redis 和 DB 都是 0/0

**代价（这条一定要主动讲）**：hash tag 保证原子性，但**同一车次的所有 key 只能落在一个节点**。实测 G1001 的 13 个 key 全在 7000，分片只在"车次之间"生效，**单车次内部没有分片能力，是单热点**。要拆只能按区段拆槽，但那样一次下单涉及多区段就跨槽了，原子性直接没。这是原子性和热点的取舍，我选了原子性。

**坑**：第一次压测脚本用 `code == 200` 判成功，报出"100 笔成功、库存 0、超卖 50 张"——吓一跳。真相是业务失败也是 200，数据库里只有 50 条"已确认"。**这也正好印证了第 7 项加业务指标的必要性。**

**顺带修的**：`reset_redis.py` 原来硬编码连 6379，单实例一关就失效。改成集群版：解析 `CLUSTER NODES` 找所有主节点逐个 `SCAN`（任意节点只持有部分槽），并处理 `MOVED` 重定向。

> 如果面试官问，我可以展开讲讲为什么没做库存分桶、以及 CROSSSLOT 的报错长什么样。

## 四、高频追问 Q&A

**Q1：怎么防超卖？**
> 关键是把"判断库存"和"扣减库存"放进同一个 Lua 脚本，Redis 单线程执行 Lua 期间不会被其他命令打断，所以不存在两个线程同时看到有票、各扣一次的问题。Java 代码里先查再扣是两条命令，中间有时间差，必然超卖。

**Q2：Lua 里三个 key 分别是什么？**
> 第一个是 stock Hash，存各区段库存；第二个是 deducted Set，记录"这张订单 Redis 已经扣过"，回补时靠它判断幂等；第三个是 passenger:dedup，做同一乘车人同一车次只能买一张的判重。三个 key 都带 hash tag，保证集群下落在同一个槽，才能在一个脚本里同时操作。

**Q3：判重口径是什么？**
> 按乘车人不是按用户。一个用户可以给自己维护的多个乘车人各买一张，但同一身份证同一车次无论什么席别、买分段都只能一张。

**Q4：既然有原子扣减，为什么还要只读预检？**
> 解决的是资源保护问题。1000 人抢 100 张票，900 个请求在预检处就被挡回，不写流水、不发 MQ、不碰数据库。预检不参与最终正确性，真实兜底仍在扣减 Lua——因为预检和扣减之间有时间差，这一点我会主动说明。

**Q5：RocketMQ 事务消息怎么保证一致？**
> 先发半消息，消费者看不到；然后执行本地事务（写流水、扣 Redis、建单、扣 DB）；成功就提交让下游消费，失败就回滚。如果应用宕机没给结果，Broker 主动回查，我根据流水状态返回提交或回滚，避免消息丢失或把正常订单误取消。

**Q6：宕机后数据怎么恢复？**
> 定时对账任务加分布式锁，扫描"Redis 已扣但订单没建成"这类卡住的流水，按状态机判定矩阵：该补单的补单、该回补库存的回补。回补 Lua 先检查 deducted 标记，没扣过的不回补，防止超卖。

**Q7：本地缓存为什么设 1 秒？**
> 这是一致性和性能的折中。1 秒内重复查询走内存，几乎零成本；最多容忍 1 秒数据短暂延迟，下单写链路不依赖本地缓存，所以不会导致超卖。

**Q8：怎么防缓存穿透？**
> 查不存在的车次，数据库也没有时，在 Redis 写一个空值标记，TTL 60 秒，恶意请求就被挡在 Redis 层，不会反复打数据库。

**Q9：为什么不用 XA/TCC/Seata？**
> 这个场景链路短、库存只有一份，不需要重型分布式事务。我用"本地状态机 + 事务消息 + 定时对账"达到最终一致，实现和运维成本都低，这也是互联网秒杀的主流做法。

**Q10：瓶颈在哪？怎么扩展？**
> 单机瓶颈是 MySQL 同一行库存更新的 InnoDB 行锁串行化，我通过 jstack 定位确认过。Redis 已经迁到 6 节点集群，但 MySQL 还是单机、没做读写分离。所以往下真正卡住的是数据库这一层：治本要做库存分桶把热点行拆开，但拆了会和 Lua 的"同槽"要求冲突——同一订单涉及的多个桶必须落在同一个槽，等于把分片又收了回去，需要重新设计 key 的槽归属。数据库以下的扩展我没做，我会明确说这个边界。

**Q11：限流会不会误杀正常用户？**
> 两个桶的目的不一样。单用户桶容量 3 是防一个账号连点，正常人手速到不了；全局限流 500 是系统入口容量，正常不会撞到。我实测过：同一个 token 并发发 10 个请求，前 3 个 200、后 7 个 429，精确。如果真出现大面积误杀，说明是那一个账号在刷，本来就该拦。

**Q12：限流上线后压测为什么只成交 3 单？**
> 因为 1000 个线程共用同一个 admin token，全被单用户桶卡在 3 个。这不是限流的问题，是我的压测脚本没考虑到"多用户"这个前提。后来只把单用户桶临时放开、全局保持不动，再跑一遍就是成交 100 单、零超卖。这个坑我特意留着，因为它说明压测结果一定要先看"参数是否匹配真实场景"。

**Q13：退款为什么不能重发？**
> 渠道查询会返回四种结果，只有"不存在"允许重发。返回"成功"说明钱已经退了，只是回调丢了，重发就是重复退钱；返回"处理中"说明银行在清算，重发只是多压一笔申请。数据库的唯一索引拦不住重发，因为重发不是插新流水，而是再调一次渠道接口。

**Q14：库存回补为什么非要加 `stock_restored`？**
> 因为回补 SQL 是 `remain + 1`，不是"设成某个值"，重复执行就会多补。对账每轮重试一次，几轮下来库存能补成 101。加了标记之后，标记和回补放在同一个事务，要么都成要么都不成，物理上不可能出现"标了没补"。

**Q15：三个定时任务会不会互相打架？**
> 不会。它们扫三张不同的表、用三个不同的锁，职责完全分开：扣减对账管下单一致性、超时关单管订单生命周期、退款对账管退票一致性。万一真的重叠执行（比如某轮跑超过 55 秒锁过期了），还有数据库 CAS 兜底——谁先改谁生效，另一个影响行数为 0 直接放弃，最坏是白跑一趟，不会把库存补多。

**Q16：为什么专门加业务指标，Actuator 自带的指标不够用吗？**
> 不够。自带的是 HTTP 层和 JVM 层指标，而这个项目所有业务失败都是 HTTP 200 + code 200。抢到票和余票不足，在 HTTP 层长得一模一样——都是 200、都很快。我要的是"今天有多少人被限流挡掉、多少人是真没票"，这个只能自己埋点。

**Q17：指标为什么会出现"清单里查不到"？**
> Micrometer 的计数器是懒注册的，第一次 increment 才创建。冷启动时段面板一片空白，你分不清是"今天真的零成交"还是"指标根本没注册"。监控系统的沉默有两种含义，必须能区分开。改成构造时预注册就解决了。

**Q18：分布式锁，单实例的情况下怎么验证？**
> 验证不了，这是关键。单实例跑一万轮，把锁删了行为完全一样，日志里一点区别都没有。所以要起第二个实例，并且给锁的 value 加实例标识，才能看到"这一轮是 8081 还是 8082 抢到的"。

**Q19：两个实例写同一个日志文件会发生什么？**
> 互相覆盖。两个进程各自以为自己知道该写哪一行，实际可能写同一位置、互相盖掉。更麻烦的是按天滚动——一边刚把文件改名准备新建，另一边还拿着旧的文件句柄，写进去的内容可能落到已改名的文件里，或者直接丢。logback 的锁只在进程内有效，跨进程它看不见对方。所以每个实例写自己的日志目录。

**Q20：Redis 切集群，Lua 脚本会崩吗？**
> 取决于 key 有没有做 hash tag。集群下脚本里所有 key 必须同槽，否则直接 CROSSSLOT。我在写 key 的时候就用了花括号，`stock:{G1001}:...`，实测三个 key 都落 2723 槽；把花括号去掉，同样的脚本立刻报错。这是设计时就留的后路，不是事后补的。

**Q21：怎么证明流量真的走了集群，而不是还连着原来的单实例？**
> 把原来的单实例直接关掉。6379 一停，业务还能跑，那就只可能是集群。这是唯一能排除"其实没切成功"的办法——配置文件改了不算证据。

**Q22：集群的代价是什么？**
> 同一车次的所有 key 只能落在一个节点，等于单车次是单热点。分片只在车次之间生效，车次内部没有分片能力。要拆只能按区段拆槽，但那样一次下单涉及多个区段就跨槽，Lua 原子性直接没了。这是原子性和热点之间的取舍，我选了原子性，因为这个项目正确性的优先级高于扩展性。

**Q23：压测为什么要建 100 个账号？**
> 因为单用户限流是令牌桶，容量 3、每秒补 1。一个 token 发 100 个请求只会放过 3 个，剩下全被限流挡掉，根本压不到库存。每个用户只发 1 次请求，才能测到真实的并发抢票。这也说明压测前要先检查"脚本的行为是否符合真实用户分布"。

## 六、诚实边界清单

被追问到这些，直接承认，不要绕：

1. 应用是双实例（8081/8082），但只在本地一台机器上，不是真正跨机部署；MySQL 单机，没做读写分离。
2. 支付渠道是 Mock，不是支付宝或微信的真实 SDK。异步回调、验签、重试那一套结构是真的，但钱是假的。
3. 下单验证码没做。方案里算过，但优先级排在有正确性风险的模块之后。
4. 库存分桶评估过但没做。热点行确实能拆，但拆完跨行一致性成本更高，且和 Lua 同槽要求冲突，当前数据量下不划算。
5. 退款对账里"渠道处理中"这条分支、还有"超过最大重试只告警一次"，只有代码路径，没有运行时证据——Mock 渠道只会返回成功，造不出处理中。
6. 支付前端是我手工点验的，没有自动化 UI 测试。
7. 退款对账超过最大重试只发日志告警，没有后台管理界面能人工改状态。
8. Mock 渠道的退款结果存在内存里，应用一重启就清空，对账会把在途退款全判成"不存在"并重发一次。真实渠道不会这样。
9. **"去掉锁会补成 101"是推理，不是实测。** 要实测得改代码、重新打包、重启两个实例、再改回来，成本高于收益。本轮只证明了"有锁时确实只执行一次"。
10. **Redis 集群跑在 1 核虚拟机上，QPS 数字没有参考价值。** 那次并发测试是 0.58 秒、QPS≈171，瓶颈是虚拟机 CPU，不是集群能力。
11. **集群只做了 `docker stop` 模拟节点消失，没做真实网络分区。** 也没测"切换那 10 秒里有多少请求失败"，只验证了切换完成后业务恢复。
12. **观察到过一次 1 张的库存偏差（DB 段1=0 / Redis 段1=1），未归因也未复现。** 理论排除（Lua 内两次 HINCRBY 原子、回补也是 Lua），第二次干净复现完全一致。只出现过一次，不能说成"已知缺陷"，也不能假装没发生。
13. 集群没接 Prometheus，各节点的内存、命中率、槽迁移都没有监控。
