# 多实例与分布式锁验证

日期：2026-11-15
定位：排期第 3 项。这是分布式锁**第一次被真正验证**——之前单实例跑了几十轮，"锁生效"只是推理。

---

## 一、为什么必须做这件事

三个定时任务（扣减对账、超时关单、退款对账）都靠 Redis 的 `SETNX` 锁保证互斥。但项目一直只跑一个进程，**把锁整个删掉也不会产生任何变化**：

- 不会有两个实例并发
- 不会出现重复回补
- 日志里也看不出区别

也就是说，"加了分布式锁"这句话在此之前**没有任何证据支撑**。面试官只要问一句"你怎么验证锁起作用的"，就没法答。

---

## 二、改了什么

| 文件 | 改动 | 为什么 |
|---|---|---|
| `common/InstanceId` | **新建**，生成 `端口:8位随机码` 形式的实例标识 | 锁 value 原来是常量 `"1"`，Redis 里只能看出"被持有"，看不出"被谁持有" |
| 三个任务类 | 锁 value 改为 `instanceId.get()`，日志里打印持有实例 | 排障第一句话是"这轮是谁跑的" |
| `logback-spring.xml` | `LOG_HOME` 改为 `${LOG_HOME:-logs}`，可用 `-DLOG_HOME` 覆盖 | 两个进程写同一个 `logs/app.log` 会互相覆盖，滚动也会失效 |

### 为什么实例标识要带随机码

只写端口不够：容器部署时多个实例端口都是 8080，光看端口分不清。`8081:79101249` 里的随机码在进程启动时生成，重启即变化，能唯一定位到某个进程的某次运行。

---

## 三、验证方法一：直接观察锁的持有者

启动第二个实例（8082，命令行 `java -jar --server.port=8082 -DLOG_HOME=logs-8082`），然后每秒读一次三个锁的值，持续 100 秒。

结果（节选）：

```
+  0.0s  reconcile:lock       = 8081:79101249  (TTL 4s)
+  0.0s  payment:timeout:lock = 8082:9975ea5f  (TTL 4s)
+  9.0s  reconcile:lock       = 8082:9975ea5f  (TTL 55s)
+  9.0s  payment:timeout:lock = 8081:79101249  (TTL 55s)
+ 69.3s  refund:reconcile:lock = 8081:79101249 (TTL 54s)
```

两个结论：

1. **任一时刻，每个锁只有一个 value** —— 这就是互斥的直接证据，`SETNX` 只有一个实例能成功
2. **跨分钟发生过交接**（8081 → 8082 → 8081），说明两个实例都在参与竞争，不是"其中一个根本没跑"

TTL 显示 4 秒是因为采样时刻接近上一轮锁的过期时间；到下一个整分钟被另一实例重设后回到 55 秒。

---

## 四、验证方法二：制造一笔会被重复处理的订单

只看锁的 value 还不够——那只能证明"锁是唯一的"，不能证明"业务不会被重复执行"。所以要造一个**两个实例都会扫到**的数据：

1. 下一单不支付，订单停在「已确认」，库存扣到 99
2. 把订单 `create_time` 改到 1000 秒前（超过 900 秒支付时限）
3. 两个实例的 `PaymentTimeoutTask` 每分钟都会扫到它
4. 观察：几个实例动手、库存被补几次

结果：

| 断言 | 实际 |
|---|---|
| 订单被超时关单 | 已取消 |
| 两个实例合计执行次数 | **1 次**（8081=1，8082=0） |
| 库存回补 | 99 → **100**（只 +1） |
| 是否被补两次 | 不是 101 |

如果锁不生效，两个实例会各关单一次、各调一次 `restoreRealStock`，库存会变成 **101**——一张已经被卖掉的票凭空多出来，这就是超卖的来源。

---

## 五、过程中发现的真实问题

**两个实例写同一个日志文件会互相覆盖。**

这是启动 8082 时才暴露的：`logback-spring.xml` 里 `LOG_HOME` 写死成 `logs`，两个进程的 `RollingFileAppender` 指向同一个 `logs/app.log`。logback 不做跨进程文件锁，结果是日志交错、滚动重命名失败。

修法是把 `LOG_HOME` 改成可外部注入（`${LOG_HOME:-logs}`），第二实例用 `-DLOG_HOME=logs-8082`。**这是多实例部署必须做的事**，Docker 阶段每个容器要挂不同的日志卷。

---

## 六、诚实边界

1. **"去掉锁会补成 101"是推理，不是实测。** 要到这一步得改代码、重新打包、重启两个实例、再改回来，成本高于收益。本轮的实测只覆盖了"有锁时确实只执行一次"。这一点必须说清楚，不能把推理当证据。
2. **55 秒锁重叠的残余风险仍在。** 如果某一轮执行超过 55 秒，锁会过期并被另一实例拿走，理论上两轮会重叠。本项目靠数据库 CAS（`casUpdateStatus`、`casUpdate`）兜底，不会真出重复回补，但"锁"这一层此时是失效的。
3. **没有验证实例崩溃的场景。** 一个实例执行中途被 kill，锁会靠 TTL 自然过期，下一轮由另一实例接管。这个场景没人为构造。
4. **8082 是命令行起的，不是 IDEA**，验证完可以关掉；它和 8081 共用同一个 MySQL 和 Redis。

---

## 七、一句话面试版

> 分布式锁这东西单实例跑一万轮也验证不了——把锁删了行为完全一样。我起了第二个实例 8082，先给锁的 value 加上实例标识，在 Redis 里能看到"这轮是 8081 还是 8082 抢到的"，采样确认任一时刻只有一个持有者；再故意造一笔超时订单让两个实例都能扫到，结果只有一个实例动手、库存只回补一次。如果锁没生效，库存会被补两次变成 101，等于凭空多出一张票。
