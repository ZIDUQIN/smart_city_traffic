# 监控端点改造（Actuator + Micrometer）

日期：2026-11-15
定位：排期第 2 项「工程化」的第一块，也是后面 AI 功能的底座（AI 调用耗时必须有地方看）。

---

## 一、为什么做这件事

系统原本只有日志。日志的问题是**要一条条翻**，回答不了三个问题：

1. 现在系统健康吗？
2. 今天抢票成功多少单、失败多少单？
3. 对账任务到底有没有在干活？

更麻烦的是本项目所有业务失败都是 **HTTP 200 + 响应体里的错误码**（`Result.error` 只改 code 字段，不改 HTTP 状态）。所以即便接了 HTTP 层监控，看到的也全是 200，**分不出「抢到票」和「余票不足」**。必须有业务维度的指标。

---

## 二、改了什么

| 文件 | 改动 |
|---|---|
| `pom.xml` | 加 `spring-boot-starter-actuator`（传递带入 micrometer-core，不用另加） |
| `application.yml` | 加 `management` 段：只暴露 `health/info/metrics`；health 显示组件明细；所有指标打 `application` 标签 |
| `security/SecurityConfig` | 放行 `/actuator/health`、`/actuator/info`、`/actuator/metrics/**` |
| `common/BusinessMetrics` | **新建**，业务指标统一入口 |
| `common/AlarmService` | `send()` 里同步打计数 |
| `task/DeductReconcileTask` | 上报本轮处理条数，`task=deduct` |
| `task/PaymentTimeoutTask` | 同上，`task=payment-timeout` |
| `task/RefundReconcileTask` | 同上，`task=refund` |
| `service/impl/OrderServiceImpl` | 成功/失败埋点，失败带 reason 标签；两处限流分别标 `限流-全局` / `限流-单用户` |

### 为什么只暴露三个端点

`env`、`beans`、`configprops` 会把环境变量、Bean 定义、配置项全吐出来，本地也没必要开。要排障就够用 `health` 和 `metrics`。

### 为什么 health 要显示明细

`show-details: always` 会返回每个组件的状态。Redis 虚拟机掉过一次，当时的现象是接口 500、日志里一堆连接超时，但**没有一处能直接说"是 Redis 挂了"**。有了明细，`/actuator/health` 一眼就能看到 `redis: DOWN`、`db: UP`。

## 三、指标清单

| 指标名 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `traffic.order.success` | counter | — | 真正抢到票的单数（库存已扣、订单已确认） |
| `traffic.order.fail` | counter | `reason` | 下单失败数，按原因分开 |
| `traffic.alarm.total` | counter | — | 告警总次数 |
| `traffic.reconcile.handled` | counter | `task` | 每个定时任务累计处理条数 |

`traffic.order.fail` 的 reason 取值（实测出现过）：

| reason | 说明 |
|---|---|
| `余票不足` | 正常流量，说明抢的人多于库存 |
| `该乘车人已购买此车次车票` | 幂等检查生效，正常 |
| `限流-单用户` | 同一用户点太快，被内层桶挡住 |
| `限流-全局` | 系统入口满，被外层桶挡住 |
| `系统异常` | MQ 不可用、发消息失败等真故障 |

**这张表的用法**：如果 fail 里 `余票不足` 占绝对多数、`系统异常` 为 0，系统是健康的；一旦 `系统异常` 开始涨，就是出事了。混成一个总数就看不出来。

## 四、一个必须修的问题：指标懒注册

首次实测发现 `traffic.order.success` 在指标清单里查不到，要等第一单成功后才出现。原因是 Micrometer 的 counter 是**首次 `increment` 时才创建**。

这不是测试写错，而是真实的可观测性缺陷：**冷启动后一段时间内监控面板是空的**，看的人分不清"今天一单没成功"和"指标还没注册"。而 0 本身是有意义的值——今天零成交就是异常信号。

修法是在 `BusinessMetrics` 构造时预注册三个无标签指标：

```java
registry.counter("traffic.order.success");
registry.counter("traffic.alarm.total");
registry.counter("traffic.reconcile.handled");
```

`traffic.order.fail` 带 `reason` 标签，没发生失败前无法预知取值，只能等它自然出现。

## 六、诚实边界

1. **指标在内存里**，应用重启全部清零。没接 Prometheus 就没有历史曲线，只能看"当前值"和"启动以来累计"。接 Prometheus 是第 6 项 Docker 阶段的事。
2. **`/actuator/**` 是匿名放行的**。本地排障方便，但真实生产不能这样——调用量、错误率、连接数都是敏感信息。生产做法是走独立管理端口或加 IP 白名单。
3. **没有告警规则**。现在只是"能看到"，没有"指标超过阈值自动通知"。真正的企业做法是 Prometheus + Alertmanager 配规则。
4. **没有分实例**。只有一个 `application` 标签值，多实例部署时需要它来区分数据来源。

## 七、一句话面试版

> 项目所有业务失败都是 HTTP 200，错误码在响应体里，所以光看 HTTP 监控分不出"抢到票"和"余票不足"。我用 Micrometer 埋了业务指标，失败按 reason 打标签——余票不足占多数是正常流量，系统异常涨起来才是故障。另外把指标预注册了，因为"数值为 0"和"指标不存在"是两种完全不同的信号，冷启动期间面板空白会误导人。
