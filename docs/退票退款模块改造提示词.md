## 一、背景与现状（已核实的代码事实，不得臆测）

项目：`D:\IDEAproject\smart-city-traffic`，Spring Boot 4.1.2 + JDK21 + MyBatis + Redis + RocketMQ。
端口 8081，包根 `com.smartcity.traffic`。

**已有能力**：

- 下单：`OrderServiceImpl.createOrder` → 限流（全局→单用户）→ 预检 check.lua → 事务消息 → deduct.lua → 建单 → 扣 DB 库存。
- 支付：`PaymentServiceImpl.prepay`（统一下单）→ 写 `payment_record`（待支付）→ `MockPayChannelServiceImpl.confirm` 异步回调 `/api/pay/notify` → `handleNotify` 验签→校验→事务内 CAS。
- 取消：`PaymentServiceImpl.userCancel`，顺序是 **CAS 已确认→已取消 → rollback.lua → restoreRealStock → 关闭待支付流水**。
- 库存回补：`RedisLuaService.rollback`（SREM 判定首次才逐段 +1，幂等）+ `StockService.restoreRealStock`（DB 逐段 +1）。

**订单状态（`OrderRecord`）**：`待确认` / `已确认` / `已支付` / `已取消`。

**缺口**：已支付订单不能退票。`cancel` 明确拒绝已支付订单（`throw new BizException("已支付订单不可取消")`）。

**关键前置判断（必须遵守）**：

1. 库存回补和订单状态切换**必须状态先切、库存后补**。理由：超卖的定义是"两笔已支付订单占同一座位"，订单一旦转出"已支付"，就不再是有效占座订单。若先补库存后切状态，切状态失败就会真超卖。
2. Redis 回补**不能**放进 DB 事务内：Redis 不参与 DB 事务，事务回滚后 Redis 已补，库存虚高 → 超卖。故 Redis 回补必须在事务提交之后。
3. 退款是外部调用，必然可能失败。先固化不可逆的本地状态（订单转退款中 + 回补库存），再调渠道；渠道失败靠重试/对账兜底，**不做回滚**（已经卖出去的座位不可能收回）。

## 三、数据模型改动

### 3.1 新表 `refund_record`（`sql/10_refund_record.sql`）

```sql
DROP TABLE IF EXISTS `refund_record`;
CREATE TABLE `refund_record` (
    `id`                 BIGINT        NOT NULL AUTO_INCREMENT COMMENT '自增主键',
    `refund_no`          VARCHAR(64)   NOT NULL COMMENT '退款单号（雪花）',
    `order_no`           VARCHAR(64)   NOT NULL COMMENT '原订单号',
    `payment_no`         VARCHAR(64)   DEFAULT NULL COMMENT '原支付流水号',
    `user_id`            BIGINT        NOT NULL COMMENT '下单用户',
    `amount`             DECIMAL(10,2) NOT NULL COMMENT '原票款金额',
    `fee`                DECIMAL(10,2) NOT NULL COMMENT '手续费',
    `refund_amount`      DECIMAL(10,2) NOT NULL COMMENT '实退金额 = amount - fee',
    `status`             VARCHAR(16)   NOT NULL COMMENT '退款中/退款成功/退款失败',
    `channel_refund_no`  VARCHAR(64)   DEFAULT NULL COMMENT '渠道退款单号，回调成功才回填',
    `reason`             VARCHAR(128)  DEFAULT NULL COMMENT '退票原因',
    `callback_count`     INT           NOT NULL DEFAULT 0 COMMENT '回调到达次数',
    `create_time`        DATETIME      NOT NULL,
    `update_time`        DATETIME      NOT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_refund_no` (`refund_no`),
    UNIQUE KEY `uk_order_no` (`order_no`),
    UNIQUE KEY `uk_channel_refund_no` (`channel_refund_no`),
    KEY `idx_status_update` (`status`, `update_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '退款流水表';
```

**要点**：

- `uk_order_no` 是**幂等第一道闸门**：一单只能有一条退款流水，并发重复退票在数据库层直接冲突。
- `uk_channel_refund_no` 防止渠道重复回调插入。

### 3.2 `order` 表状态枚举扩展（无需改 DDL）

`OrderRecord` 新增两个常量：

```java
public static final String STATUS_REFUNDING = "退款中";
public static final String STATUS_REFUNDED  = "已退款";
```

### 4.1 `RefundRecordMapper` 方法

```java
int insert(RefundRecord record);                                  // 新增退款流水
```

## 五、核心流程（定稿，不得改动顺序）

### 5.1 `applyRefund(orderNo, reason)`

```
① 校验（全部通过才继续）
   - 订单存在
   - 归属当前用户（order.getUserId() == currentUserHelper.currentUserId()）
   - order.getStatus() == "已支付"
   - 已有支付成功流水（paymentRecordMapper.selectSuccessByOrderNo(orderNo) 非空），取其 paymentNo

② 计算金额
   - fee = order.getAmount() * refundFeeRate（BigDecimal，保留 2 位，HALF_UP）
   - refundAmount = order.getAmount() - fee
   - 若 refundAmount <= 0 → 抛 BizException("退款金额异常")

③ 事务内（TransactionTemplate，必须真事务）
   a. insert refund_record：
      refundNo = 雪花，status = "退款中"，amount/fee/refundAmount，paymentNo，userId，reason，callbackCount=0
      —— uk_order_no 冲突会抛 DuplicateKeyException，必须显式捕获并转成
         BizException("该订单已提交退票，请勿重复操作")，整个事务回滚
   b. orderMapper.casUpdateStatus(orderNo, "已支付", "退款中")
      —— 返回 0 说明状态已被并发改掉 → status.setRollbackOnly()
   任一步失败，事务回滚，退款流水不落库

④ 事务提交后（不可逆状态已固化，以下失败只告警不回滚）
   a. redisLuaService.rollback(trainNo, seatNo, passengerId, orderNo, segments)
      segments = fromSeq..toSeq-1，与下单扣减完全一致
   b. stockService.restoreRealStock(trainNo, seatNo, segments)
   失败 → alarmService.send("退票库存回补失败 orderNo=... " )，继续往下
   —— 理由：rollback.lua / restoreRealStock 均幂等，可由后续对账重试

⑤ 调渠道退款
   channel.refund(record)  // 异步，不阻塞
   返回 RefundResponse（status = "退款中"）
```

**④ 为什么在事务外**：Redis 不参与 DB 事务。若在事务内回补 Redis，事务回滚后 Redis 已 +1 → 库存虚高 → 超卖。

**④ 失败的后果**：订单已"退款中"但库存没回 → 少卖（不是超卖），由对账补偿。这是可接受的降级方向。

### 5.2 `handleNotify(rawBody, signature)`

```
① HmacSignUtil.verify(hmacSecret, rawBody, signature) 失败 → return false（不做任何业务）

② 解析：refundNo / orderNo / channelRefundNo / amount

③ 加载 refund_record + order；任一为空 → alarmService.send + return false（挂起等重试）

④ 校验：
   - refund_record.refundAmount 与回调 amount 一致
   - 否则 alarmService.send("退款回调金额不符") + return false

⑤ 幂等：refund_record.status 已是"退款成功" → incrCallbackCount + return true（重复回调，应答 SUCCESS）

⑥ 事务内：
   - incrCallbackCount
   - refundRecordMapper.casSuccess(refundNo, channelRefundNo)；返回 0 → setRollbackOnly
   - orderMapper.casUpdateStatus(orderNo, "退款中", "已退款")；返回 0 → setRollbackOnly
   （此时库存早已在 5.1 第④步回补，回调里不再碰库存）

⑦ 成功 return true；失败 alarmService.send + return false
```

### 5.3 `status(orderNo)`

返回 `RefundResponse`：从 `refund_record` 取 status / amount / fee / refundAmount / reason；无退款记录返回 null 或状态"未退票"。

## 六、幂等三重保险（必须全部落地）

| 层 | 手段 | 拦截什么 |
|---|---|---|
| DB | `refund_record.uk_order_no` 唯一索引 | 并发重复提交退票 |
| DB | `casUpdateStatus(已支付→退款中)` 返回 0 | 状态已被改过（重复提交/已被关单） |
| 渠道 | `uk_channel_refund_no` + `casSuccess` 条件更新 | 渠道重复回调 |

**禁止**：用 `if (refundRecord != null) return;` 这种先查后写的方式做幂等（并发下会双写）。必须靠唯一索引 + CAS。

## 八、禁止事项（6 条）

1. 禁止把 Redis 回补放进 DB 事务内。
2. 禁止"先回补库存、后切状态"的顺序。
3. 禁止退款失败时回滚订单状态到"已支付"（座位已放出，回滚就是超卖）。
4. 禁止用"先查后写"做幂等，必须唯一索引 + CAS。
5. 禁止在 `handleNotify` 验签失败时返回 SUCCESS。
6. 禁止改动现有 `cancel`（未支付取消）的逻辑与 `rollback.lua` 脚本内容。

## 十一、已知缺口（本轮不做，必须记录，不得假装已解决）

1. **库存回补失败无自动补偿**：5.1 第④步若 `rollback.lua` 或 `restoreRealStock` 失败，订单已是"退款中"，库存没回，用户钱也照退——结果是少卖（不是超卖）。本轮只发告警，不做对账任务，需下一轮加 `RefundReconcileTask`（扫描"退款中"超时订单，重试回补）。
2. **退款长时间停留在"退款中"**：Mock 渠道回调必到，无超时场景；真实渠道需加主动查询补偿。
3. **手续费固定费率**：`Train` 无日期维度，做不了开车前阶梯，用 `refund.fee-rate` 固定比例（默认 0）。

## 十二、面试讲法要点（交付时附一段）

- **这条链路的核心矛盾**：钱（外部渠道，不可控）与座位（内部库存，必须准确）要一起处理，而外部调用一定会失败。
- **解法**：先固化内部不可逆状态（订单转退款中 + 回补库存），再调外部；失败方向单向（最多钱晚到），永不产生超卖。
- **为什么不用 XA/Seata**：Redis 与 MySQL 不在一个事务域内，2PC 覆盖不到；且秒杀场景要求高吞吐，最终一致 + 幂等 + 对账才是正确架构。
- **幂等三重保险**：唯一索引、CAS 条件更新、渠道单号唯一。

### 一句话面试版

> "退票这条链路的关键是顺序：订单状态是『是否占座』的唯一判据，所以必须在同一个本地事务里把订单从已支付切到退款中，事务提交之后才回补 Redis 和 DB 库存，最后才调渠道退款。这样最坏情况只是钱晚到，永远不会出现两笔已支付占同一座位。幂等靠唯一索引 + CAS + 渠道单号三重拦截，实测并发两个线程同时退同一单，只有一个能成功。"
