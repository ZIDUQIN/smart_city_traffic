# 车票预订系统前端重构规划

> 目标：把现在这个「接口演示页」改造成能走完整购票流程的真实产品界面。
> 依据：本项目实际的 6 个 Controller、27 个端点、6 种订单状态。

---

## 一、现有接口清单

| 方法 | 路径 | 入参 | 出参 | 鉴权 |
|---|---|---|---|---|
| POST | `/login` | `{username, password}` | `{accessToken, refreshToken, expiresIn}` | 否 |
| POST | `/register` | `{username, password, ...}` | null | 否 |

### 2. 乘车人 `/api/passengers`（4 个）

| 方法 | 路径 | 入参 | 出参 |

| GET | `/` | - | `PassengerVO[]` |

### 3. 查票 `/api/ticket`（1 个）

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|

### 4. 订单 `/api/orders`（7 个）

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/` | `{passengerId, trainNo, travelDate(可选), seatNo, fromSeq, toSeq}` | `{orderNo, status, message}` |
| GET | `/{orderNo}` | - | `{orderNo, passengerId, trainNo, seatNo, status, message}` |
| POST | `/preheat` | `trainNo, travelDate(可选), seatNo(可选)` | 预热条数 |
| POST | `/{orderNo}/cancel` | - | null |
| GET | `/my` | - | `OrderRecord[]` |
| POST | `/{orderNo}/refund` | `reason(可选)` | `RefundResponse` |
| GET | `/{orderNo}/refund` | - | `RefundResponse` |

### 5. 支付 `/api/pay`（6 个，前端用 3 个）

| 方法 | 路径 | 入参 | 出参 | 前端用 |
|---|---|---|---|---|
| POST | `/prepay` | `orderNo` | `{paymentNo, orderNo, amount, payToken}` | 是 |
| POST | `/mock/confirm` | `payToken` | "支付处理中" | 是 |
| GET | `/status/{orderNo}` | - | `{orderNo, orderStatus, paymentStatus}` | 是（轮询） |
| POST | `/notify` | 原始报文 + 签名 | 渠道应答 | 否（渠道回调） |
| POST | `/refund/notify` | 同上 | 同上 | 否 |
| POST | `/mock/refund-result` | `channelRefundNo, result` | 调试结果 | 否（调试） |

### 6. 实例管理 `/api/instances`（4 个，运维用）

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/window` | `trainNo, days(默认7)` | `TrainInstanceRecord[]` |
| POST | `/ensure` | `days` | 新建实例数 |
| POST | `/{instanceNo}/preheat` | - | boolean |
| POST | `/cleanup` | `delayDays` | 清理数 |

### 订单状态枚举（前端必须全部覆盖）

| 状态值 | 含义 | 前端可做的操作 |
|---|---|---|
| 待确认 | 订单已建，库存未确认 | 轮询，通常瞬间转「已确认」 |
| 已确认 | 抢票成功，待支付 | 支付、取消 |
| 已支付 | 支付完成（终态） | 退票 |
| 退款中 | 已提交退票，等渠道回调 | 查看退款进度 |
| 已退款 | 退款完成（终态） | 无 |
| 已取消 | 订单关闭 | 无 |

## 二、现有前端的问题

1. **是接口演示页，不是产品**：三个并排的表单（库存预热 / 余票查询 / 抢票下单），对应三个接口，用户不知道怎么"买一张票"。
2. **必须手输车次号**：查票要先知道 `G1001`，真实用户只知道"我要从西安去北京"。
3. **看不到车次列表**：没有比价、比时间的地方，没法"选"。
4. **下单不选乘车人**：要手填乘车人 ID，真实的购票必须从乘车人列表里挑。
5. **支付流程完全缺失**：下单成功后订单停在「已确认」，没有收银台，也没有轮询支付结果。
6. **我的订单 / 退票没有界面**：接口写好了，前端没接。

## 三、必须先补的后端接口（关键缺口）

**问题**：现有查票接口只接受 `trainNo`，没有「按站点查车次列表」的能力，真实界面的第一屏就做不出来。

**要新增**：

```
GET /api/ticket/search?fromStation=西安北&toStation=北京西&travelDate=2026-11-17
```

返回该 OD 在该日期所有可售车次，每条带三个席别的余票和票价：

```json
[
  {
    "trainNo": "G652",
    "instanceNo": "G652-20261117",
    "fromStation": "西安北",
    "toStation": "北京西",
    "fromSeq": 1,
    "toSeq": 3,
    "departTime": "08:35",
    "arriveTime": "16:30",
    "durationMinutes": 475,
    "seats": [
      {"seatNo": "SECOND_CLASS", "seatName": "二等座", "remain": 50, "price": 680.00},
      {"seatNo": "FIRST_CLASS",  "seatName": "一等座", "remain": 20, "price": 1080.00},
      {"seatNo": "BUSINESS",     "seatName": "商务座", "remain": 5,  "price": 2040.00}
    ]
  }
]
```

实现要点：
- 按站名查 `station.id`
- 找出 `train_station` 里同时包含两站、且 `from.seq < to.seq` 的车次，得到 `fromSeq/toSeq`
- 只取 `train.status = 1` 的车次
- 该日期实例不存在或未预热，返回空（前端提示"该日期暂无可售车次"）
- 席别固定三种：二等座 / 一等座 / 商务座
- 按出发时间升序
- 不做中转（本项目暂不支持）

## 四、目标信息架构

```
未登录
 └─ 登录页（账号密码，注册入口）

已登录
 └─ 主框架（顶部导航：订票 / 我的订单 / 乘车人 / 运维）
     ├─ 订票页（核心）
     │   ├─ 搜索区：出发站 · 到达站 · 日期(7天条) · 查询
     │   ├─ 结果区：车次列表（每车 3 个席别可点）
     │   ├─ 下单弹窗：行程摘要 + 选乘车人 + 金额 → 抢票
     │   └─ 支付弹窗：模拟收银台 + 倒计时
     ├─ 我的订单（列表 + 支付/取消/退票/查进度）
     ├─ 乘车人管理（增删改查）
     └─ 运维面板（默认折叠：实例窗口、预热、清理）
```

**为什么把「库存预热」从主界面拿掉**：它是后台运维动作，真实用户永远不需要点。放进折叠的运维面板，演示时能展开，平时不干扰。

## 五、页面详细设计

### 5.1 登录页

- 居中卡片，标题「智慧城市交通 · 车票预订」
- 两个输入框（账号、密码）+ 登录按钮
- 底部「没有账号？注册」切换
- 登录成功后存 token 到 localStorage，进入订票页
- 失败时输入框下方红字显示后端 `message`
- 演示账号提示：`admin / 123456`（灰字小提示）

### 5.2 订票页（核心）

**搜索区**（一张卡片）：

- 出发站、到达站：两个可输入下拉（输入即过滤 `station` 列表）。数据来源：`/api/instances/window` 不够，需要新增一个 `GET /api/ticket/stations` 返回全部车站，或前端写死常用站。**方案：新增 `GET /api/ticket/stations`，返回 `[{id, stationName, city}]`。**
- 交换按钮（左右箭头），一键对调出发/到达
- 日期：7 天横向日期条，第一天标「今天」，其余标「11/18 周二」
- 「查询」主按钮
- 快捷线路：6 个胶囊按钮，写死真实有车的 OD（西安北→北京西、西安北→上海虹桥、北京西→广州南、上海虹桥→南京南、成都东→重庆北、广州南→长沙南），点击即填充并查询

**结果区**：

- 表头行：车次 / 出发-到达 / 历时 / 席别余票（三列）
- 每个车次一行卡片：
  - 左：车次号（大字）+ 车型小标签（G/D/C → 高铁/动车/城际）
  - 中：`08:35` 西安北 → `16:30` 北京西，中间一条细线标「7小时55分」
  - 右：三个席别块，每块显示「席别名 / ¥价格 / 余票状态」，可点击选中
- 余票三级标识（对齐 12306 的规则）：
  - `remain > 5`：绿色「余票 50」
  - `1 ≤ remain ≤ 5`：橙色「仅剩 3」
  - `remain = 0`：灰色「无票」，不可点
  - 无票价配置：不显示价格，块置灰不可点
- 排序：按出发时间升序；顶部给「上午/下午/全部」三个筛选标签
- 空态：`该日期暂无可售车次` + 提示换日期或换线路

### 5.3 下单弹窗

- 标题「确认订单」
- 行程摘要卡：车次号 · 日期 · 出发站→到达站 · 时刻 · 席别 · 单价
- 乘车人选择：单选列表（姓名 + 脱敏身份证 + 乘客类型标签）；「+ 新增乘车人」按钮跳到乘车人页
- 无乘车人时：整块替换为引导文案「还没有乘车人，先去添加」
- 底部：合计金额（大字）+「提交订单」
- 提交后状态机（**下单接口同步返回最终状态**，不要盲目轮询）：
  1. `提交中`：按钮转圈，禁用
  2. `POST /api/orders` 一次拿到 `{orderNo, status, message}`
  3. `status = 已确认` → 弹窗切换到「抢票成功」，显示订单号，按钮变「去支付」
  4. `status = 已取消` → 直接显示 `message`（余票不足 / 该乘车人已购买此车次车票 / 该行程暂未配置票价），按钮变「重新选择」
  5. 只有返回 `status = 待确认` 时才需要轮询兜底（正常流程不会出现）

### 5.4 支付弹窗

- 显示：应付金额、订单号、倒计时（15 分钟，从前端下单成功时刻算）
- 「确认支付」：调 `/api/pay/prepay` 拿 `payToken` → 调 `/api/pay/mock/confirm` → 轮询 `/api/pay/status/{orderNo}`
- 轮询：每 800ms 一次，最多 15 次；`orderStatus = 已支付` 即成功
- 成功：绿色对勾 + 「支付成功」+ 「查看订单」
- 失败/超时：提示「支付处理中，请稍后在订单列表查看」
- 「取消支付」：关闭弹窗，订单保留在「已确认」状态，可回到订单页继续支付

### 5.5 我的订单

- 顶部状态筛选标签：全部 / 待支付(已确认) / 已支付 / 退款中 / 已退款 / 已取消，每个标签带数量
- 列表卡片，每条：
  - 第一行：车次号 · 日期 · 席别 · 状态徽标（不同颜色）
  - 第二行：出发站→到达站（从 `fromSeq/toSeq` 只能拿到序号，**后端 `OrderRecord` 不含站名，需新增字段或前端按 instanceNo 反查**）
  - 第三行：订单号（可复制）、金额、创建时间
  - 操作区按状态：
    - 已确认：`去支付` `取消订单`（取消接口走 `paymentService.userCancel`，**对已确认订单有效**，会回补库存）
    - 已支付：`申请退票`
    - 退款中：`查看退款进度`
    - 其他：无
- 退票弹窗：显示票款、手续费、实退金额、状态；提交后进入「退款中」，可轮询进度
- **手续费当前配置为 0**（`refund.fee-rate` 默认 `0.00`），所以实退金额等于票款。不要在前端自己乘比例，直接用接口返回的 `fee` / `refundAmount`
- 分页：本项目订单量小，直接全部返回，超过 20 条前端滚动

**关于站名缺口**：`OrderRecord` 只有 `fromSeq/toSeq`，没有站名。两个选择：
- A. 后端在 `/api/orders/my` 返回时补 `fromStation/toStation`（需要在 `OrderMapper` join `train_station`）
- B. 前端展示「第 1 段 → 第 3 站」

**选 A**，否则用户看不懂订单。改动很小：`OrderMapper.xml` 的 `selectByUserId` 加两个 join 字段。

### 5.6 乘车人管理

- 列表卡片：姓名 + 脱敏证件号 + 类型标签（编码 1 成人 / 2 学生 / 3 儿童，后端只认这三个值）
- 新增/编辑弹窗：姓名、证件号、类型
- 删除二次确认
- 空态引导

### 5.7 运维面板（默认折叠）

- 「实例窗口」：选车次 + 天数 → 表格显示日期、实例号、状态、是否预热
- 「手工补齐窗口」按钮
- 「手工预热某实例」输入框 + 按钮
- 「清理过期实例」
- 每个操作显示返回结果

## 七、交互细节与边界

1. **token 过期**：任何接口返回 401 → 清 localStorage → 跳登录页并提示「登录已过期」。
2. **抢票并发**：提交按钮点击后立即禁用，防重复提交。
3. **余票实时性**：查票结果不自动刷新，用户点「刷新」重查。
4. **日期条只有 7 天**：因为窗口就是 7 天滚动。第 8 天实例不存在，查票会返回空。日期条不生成第 8 天，避免用户点到空日期。
5. **热门线路必须真实有车**：6 条写死的 OD 必须都在抓取过的线路里，否则点了没结果。
6. **支付倒计时**：15 分钟是后端超时关单阈值，前端倒计时到 0 就提示「订单可能已超时，请在订单页确认」。
7. **所有金额保留两位小数**。
8. **所有接口失败都要有可见反馈**，不能静默。
9. **移动端**：主流程在 768px 以下改为单列，车次卡片竖排；不追求完美适配，但不能横向溢出。

## 八、技术约束

- 只用原生 HTML + CSS + 原生 JS，不加构建工具、不引第三方库
- 文件就三个：`static/index.html`、`static/css/style.css`、`static/js/app.js`
- 版本号 `?v=5`，避免浏览器缓存
- 所有请求走 `fetch`，统一封装 `api()` 处理 token、401、错误提示
- 代码里不写死 IP，同源相对路径
