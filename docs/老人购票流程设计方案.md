# 老人购票主流程设计方案

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-11-17 |

| 关系 | 修订 `方言语音购票设计.md` 第 8 章的"三重确认"与车次展示；其余章节不变 |
| 状态 | 设计已确认，待编码 |

---

## 1. 要解决的问题

M3 实测的真实行为：老人说完一句话，`/api/voice/interpret` 一次性返回意图、站名候选和**全部车次**，每趟车还带二等/一等/商务三种席别的余票与票价。前端把车次渲染成卡片。一个方向 6~12 趟 × 3 席别 = 最多 **36 条信息**压在一屏。

| 谁在看 | 结果 |
|---|---|
| 年轻人 | 信息齐全，挑一趟就行 |
| 只会说方言的老人 | 看不懂（不知道 7:07 和 9:20 该选哪个）、不会选（不知道"上午走"还是"下午走"好）、不敢点（点错了怕买错票扣钱） |

根子不在"信息不够"，而在**让本该被照顾的人做选择题**。

本方案只改交互，不加功能。

**三条原则**

1. **能少一个选项就少一个**：不是给他更多信息，是替他把信息砍到能看懂。
2. **能用嘴回答就不用手指点**：老人点不准小按钮，但说"上午"很顺口。
3. **每一步都要有"我不懂，你帮我"的退路**：不能让人卡在选择页上出不来。

## 2. 主流程（七步）

| 步 | 系统做什么 | 老人看到 | 老人听到 | 老人要做的 |
|---|---|---|---|---|
| ① | 录音 → 讯飞转文字 | 大字显示识别到的原话 | — | 说话："我明天要去北京" |
| ② | 站名纠错：内存打分 → 试通车 → 定站 | 定不住则出候选卡片；定住直接进下一步 | "西安北 到 北京西，对吗？" | 若出候选：点一下站名 |
| ③ | 定日期（说"明天"就明天，不说就是今天） | "11月18日" | 播报里带"明天" | 无 |
| ④ | 查这天全部班次（时刻来自 MySQL，余票票价来自 Redis） | 班次列表（一行一趟，见第 3 节） | — | 无 |
| ⑤ | 同屏问出发时间 | 列表下方一句大字"您大概什么时候走？" + 6 个时段按钮 | "明天有六趟车，您大概什么时候走？" | 说"上午/九点/早点"；或点时段按钮 |
| ⑥ | 按回答挑一趟 → 推荐 | 被推荐那趟放大，其余折叠成"还有 5 趟" | "给您推荐七点零七分这趟，二等座三百八十块，还有十二张" | 说"就这个"；或点"就这趟" |
| ⑦ | 确认 → 重查余票 → 建待支付订单 → 跳选乘车人 | 收银台 + 乘车人列表 | "一共三百八十块，选好坐车的人就可以付钱了" | 自己勾乘车人 → 支付 |

**为什么"先说站、后问时间"**：站搞错了后面全错；日期和时间是同一批数据的两个维度——"明天"多半在话里，"几点走"多半不在话里。所以站和日期先定，时间用一问补上。

**为什么不做"直接推一个"**：那样老人没有任何选择余地，系统猜错就全错。保留列表 + 一问收敛，等于"选项还在，但你不用挑"。

## 3. 班次列表怎么摆

| 项 | 做法 |
|---|---|
| 趟数 | 一趟一行，**不展开席别** |
| 一行内容 | `出发时刻 → 到达时刻`，后跟"二等座 ¥380 余12" |
| 排序 | 按发车时刻升序 |
| 一行高度 | ≥ 64px，字号 ≥ 20px |
| 席别详情 | 点这一行才展开三种席别；不点不显示 |
| 推荐之后 | 被推荐那趟放大到整行宽、字号 +30%，其余折叠为一行小字"还有 5 趟，点开看" |

**一行长这样**

```
7:07  →  11:23        二等座 ¥380  余12
9:20  →  13:36        二等座 ¥380  余 8
14:05 →  18:21        二等座 ¥420  余23
```

**为什么这么摆**

- 36 条（趟 × 席别）是"给懂的人看的档案"，不是"给老人看的菜单"。一行一趟，他只需要知道有几趟、大概几点。
- 席别默认二等座——最便宜、最常见，他不说就按它，说"要一等座/卧铺"才换。**三种席别并排，等于逼他做一次他做不了的决定。**
- 时刻大字号、席别余票小字：先让他认出"几点走"，价格是第二层信息。

## 4. "什么时候走"怎么听懂

### 4.1 具体时刻

| 说法 | 解析 |
|---|---|
| 九点、9点、九点半、7点07 | 取当天该时刻**之后最近的一趟** |
| 下午三点、晚上八点 | 先按"下午/晚上"换算成 24 小时制，同上 |

### 4.2 时段（取范围内第一趟有票的）

| 说法 | 范围 |
|---|---|
| 大清早、凌晨 | 05:00 – 07:00 |
| 早上、早晨 | 06:00 – 09:00 |
| 上午 | 08:00 – 12:00 |
| 中午、晌午 | 11:00 – 13:30 |
| 下午、后晌 | 12:00 – 18:00 |
| 傍晚、天擦黑 | 17:00 – 19:30 |
| 晚上 | 18:00 – 24:00 |

### 4.3 模糊说法

| 说法 | 解析 | 为什么这样定 |
|---|---|---|
| 早点走、早一点、尽量早 | 取最早有票的一趟 | 说的是"越早越好" |
| 晚点走、不着急、晚一点 | 取最晚有票的一趟 | 说的是"越晚越好" |
| 尽快、马上、现在就走 | **取当前时间之后最近的一趟** | 和"最早"不同：现在 10 点，14:00 才算"现在就走"，9:00 已经开走了 |
| 都行、随便、你定 | 取最早有票的一趟 | 他放弃决定了，就替他定 |

### 4.4 否定说法

| 说法 | 解析 |
|---|---|
| 别太早 | 排除 06:00 之前，从 06:00 起取第一趟 |
| 不要太晚 | 排除 20:00 之后，取 20:00 前最后一趟 |

### 4.5 一句都没沾上

不追问第二遍。直接按"最早有票的一趟"推荐，并且**把理由说出来**：

> "那给您按最早的一趟来，七点零七分走，行吗？"

老人只需要回答"行"。**追问"您几点走"第二次，比替他定更让他慌。**

## 5. 怎么挑那一趟（推荐优先级）

从上到下，命中就停：

| 优先 | 条件 | 动作 |
|---|---|---|
| 1 | 说了具体时刻 | 该时刻之后最近一趟 |
| 2 | 说了时段 | 该时段内第一趟 |
| 3 | 说了模糊词 | 按 4.3 映射 |
| 4 | 说了否定词 | 排除区间后取第一趟 |
| 5 | 都没沾上 | 最早一趟 |

**两条硬约束**

1. **只推有票的**。余票 = 0 的趟直接跳过，不推荐。
2. **该时段一趟都没有**，不硬凑，明说并给替代：

> "上午没有车了，最近的一趟是十二点四十，行吗？"

**为什么不推"综合最优"**：年轻人会算"这趟快但贵、那趟慢但便宜"，老人不会。对他只有三种有效标准：早点走、晚点走、都行。

## 6. 推荐怎么念（播报文案）

**模板**

```
"给您推荐{时刻}这趟，{席别}，{价格}块，{余票}。"
```

| 数据 | 播报 |
|---|---|
| 7:07 发车，二等座 ¥380，余 12 | "给您推荐七点零七分这趟，二等座，三百八十块，还有十二张。" |
| 余 3 | "……二等座，三百八十块，只剩三张了。" |
| 余票充足（> 5） | "……还有票，够买。" |
| 价格为空 | "……票价还没出来，先给您占个位。"（**绝不念数字**） |

**四条禁令**

1. **不念车次号**：老人不记 "G1234"，念了只是噪音。
2. **不念历时**：不说"历时四小时十六分"，只说"七点零七走，十一点二十三到"。
3. **不念席别代码**：不出现 `SECOND_CLASS`，只说"二等座"。
4. **不念"余票 12 张"这种机械说法**，换成"还有十二张""只剩三张""够买"。

## 7. 确认之后发生什么（确认 ≠ 已经买到票）

老人点"就这趟"或说"就这个"，系统认定的是**意图**：这趟车、这个席别、这些张数、这个日期。不是"票已经到手"。

**必须走完这三步**

```
① 重新查一次余票
      ↓ 还有票
② 建待支付订单（沿用现有下单接口，锁座）
      ↓ 成功
③ 跳选乘车人 + 收银台
```

**为什么必须重查**：列表上的余票是几分钟前的快照。老人犹豫两分钟再点"就这个"，那趟可能已经卖完了。

**卖完了怎么办（不能报错）**

| 情况 | 系统行为 | 播报 |
|---|---|---|
| 该趟卖完 | 自动换下一趟（按第 5 节同一套规则再挑） | "这趟刚卖完了，我给您换一趟，九点二十那趟还有票，行吗？" |
| 连换 3 趟都卖完 | 停止换，建议改日期 | "这个点真没票了，要不要看看后天？" |
| 全部卖完 | 停止，建议换日期 | "明天这条线没票了，换个日子试试？" |

**为什么不能直接报错**：老人看到"操作失败，请重试"会以为是自己按错了，然后反复点、越点越乱。系统要**接住这次失败并继续往下走**。

**一处顺序细节**：语音链路不预先查余票（见第 11 节第 5 项的试通车轻量化），只有走到第 ⑦ 步才真正锁座。所以列表上的余票是"参考值"，判定以第 ⑦ 步的重查为准。

---

## 8. 乘车人：用户自己选

**结论**：语音确认之后，跳到一个"选乘车人"步骤，**让用户在列表里自己勾**。系统不做任何自动勾选、不猜"他要带谁"、不取最近一次。

**只有两条约束**

| 约束 | 处理 |
|---|---|
| 勾选人数必须等于买票张数 | 不一致提示"您说要两张，这里只勾了一个人"，不自动补齐、不自动删 |
| 至少勾一个 | 不勾不能进支付 |

**为什么这么定**：谁出行是事实问题，不是能推导出来的偏好。系统替用户决定"带不带孩子""用谁的身份证"，一旦猜错就是实名校验失败，比让他自己点两下麻烦得多。这一块**保持简单**，是设计选择不是遗漏。

## 9. 前端状态机

| 状态 | 进入时机 | 屏幕上 | 出口 |
|---|---|---|---|
| `IDLE` | 打开面板 / 重新说 | 按住说话大按钮 | 按下 → `RECORDING` |
| `RECORDING` | 按住 | 计时 + 声波动效 | 松开 → `INTERPRETING` |
| `INTERPRETING` | 提交后 | "听着呢…" | 返回 → `ASK_STATION` 或 `ASK_TIME` |
| `ASK_STATION` | `needStationConfirm=true` | 站名候选卡片 | 点站名 → `ASK_TIME` |
| `ASK_TIME` | 站与日期已定、车次已查出 | 班次列表 + "您什么时候走？" + 时段按钮 | 回答/点按钮 → `RECOMMENDING`；30s 无动作 → `RECOMMENDING`（取最早并说明） |
| `RECOMMENDING` | 挑出一趟 | 该趟放大 + "就这趟 / 换一趟 / 你帮我选" | 确认 → `CONFIRMING` |
| `CONFIRMING` | 点了就这趟 | "正在给您占座…" | 成功 → `PICK_PASSENGER`；卖完 → 回 `RECOMMENDING` 并播报换趟 |
| `PICK_PASSENGER` | 建单成功 | 乘车人列表 + 收银台 | 勾人 → 支付 |

**关键约束**（沿用主设计文档，不放宽）：`needStationConfirm=true` 时**禁止**展示班次卡片，必须先选站。

## 10. 异常与兜底

| 情况 | 系统行为 | 播报/提示 |
|---|---|---|
| ① 没听清 | 回 `IDLE`，保留打字入口与 6 个句式按钮 | "没听清，您再说一遍，或者点下面的话" |
| ② 站名定不住 | 进 `ASK_STATION`，只出候选卡片 | "您说的是从哪儿走？点一个" |
| ③ 这个时段没车 | 给最近一趟，不硬凑 | "上午没有车了，最近的一趟是十二点四十，行吗？" |
| ④ 全部没票 | 建议换日期（限 7 天窗口内） | "明天这条线没票了，换个日子试试？" |
| ⑤ 播报想停 | 关面板 = 立刻掐断（`pause → cancel → resume`） | 已修（2026-11-17） |
| ⑥ 老人 30 秒没动作 | 主动递话，不干等 | "是不是不太好操作？要我帮您挑一趟吗？" |
| ⑦ 被限流（6 次/分钟） | 不报技术错误 | "说得有点急，歇一下再说" |
| ⑧ 识别服务异常 | 切打字兜底 | "识别服务歇会儿，您先打字或点下面的句子" |

**第 ⑥ 条的动机**：老人不会主动求助。卡住时他会沉默、反复戳屏幕，或者干脆走开。系统必须主动递一句"要我帮你吗"，这比任何文案优化都有效。

| # | 位置 | 改什么 | 为什么 |
|---|---|---|---|
| 1 | `IntentParser` | 新增"出发时间偏好"解析：具体时刻 / 时段 / 模糊词 / 否定词四类映射（第 4 节） | 现在的 `TextNormalizer` 会把"上午"当废话**剥掉**，必须单独留一份给推荐用 |

| 5 | `StationCorrector.probeHasTrain` | 试通车改轻量查询（只判"有没有车"，不算票价余票） | 一次语音现在最多打 9 次完整查票（含每趟 × 3 席别的余票），只为回答"通不通车" |
| 6 | `voice.js` `renderTrains` | 按第 3 节重排：一行一趟、默认列二等座、推荐后放大其余折叠 | 36 条信息压屏，老人看不懂 |
| 7 | `voice.js` | 新增 `ASK_TIME` 阶段的 6 个时段按钮 + 30 秒无动作计时器 | 4.5 与第 10 节第 ⑥ 条 |
| 8 | `voice.js` | 新增"就这趟 / 换一趟 / 你帮我选"三个按钮，替换席别小按钮 | 席别从"让他选"改成"默认二等座，他说了才换" |
| 9 | `index.html` / `style.css` | 班次行样式、时段按钮、放大态 | 同上 |
| 10 | 资源版本 | `?v=8` → `?v=9` | 静态资源改了就升版本，否则浏览器拿旧的 |

**不改的部分**：订单、库存、支付、退款、MQ 链路一律不动；下单仍走现有接口。

## 12. 明确不做的事

| 不做 | 理由 |
|---|---|
| 家人远程代付 / 远程指导 | 主设计文档 16.4 已否决，列入远期 |
| 把下单决策交给大模型 | 既定原则：模型只读，写操作必须人点 |
| 自动推断乘车人 | 第 8 节：谁出行是事实，不能猜 |
| "综合最优"推荐（速度/价格加权） | 老人没有这个判断标准 |
| 记住上次席别并自动套用 | 会让"上次买了商务座"污染这次，宁可每次默认二等座 |
| 多轮指代（"第二个""那个便宜的"）本轮不铺开 | 先做"第几趟/头一个"这类序数指代，够用；复杂指代留到下一轮 |

## 13. 怎么验收

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | 从"说话"到"收银台"，**点击 ≤ 6 次、说话 ≤ 3 次** | 实机走一遍，数点击 |
| 2 | 老人全程不看屏幕、只听播报也能走完 | 遮住屏幕只靠语音走一遍 |
| 3 | 说"上午/下午/九点/早点/都行"五种说法，都能挑出正确时段的车 | 语料 5 条 |
| 4 | 该时段没车时给最近一趟并说明，不是报错 | 语料 1 条（如"凌晨三点走"） |
| 5 | 列表显示"余 1"但第 ⑦ 步已卖完，能自动换一趟且不报错 | 并发脚本把余票扣到 0 再点确认 |
| 6 | 播报被关面板打断立刻停，不拖尾 | 点"就这趟"后立刻关面板 |
| 7 | 30 秒无动作，系统主动递话 | 停在 `ASK_TIME` 等 30 秒 |
| 8 | 乘车人必须自己勾，人数与张数不一致时有明确提示 | 说"两张"只勾一个人 |

**顺带记一笔**：第 11 节第 5 项（试通车轻量化）不改变交互，只是让这套交互在高并发下不会拖垮数据库——把一次语音的 MySQL 查询从"最多 9 次联表 + 上百次余票"降到"最多 9 次只查一行的判定"。
