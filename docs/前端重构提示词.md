## 二、前置：必须先补的三个后端接口

### 1. `GET /api/ticket/search`

按出发站 + 到达站 + 日期查车次列表。

**入参**：`fromStation`（站名，如「西安北」）、`toStation`（站名）、`travelDate`（`yyyy-MM-dd`，可选，默认今天）

**出参**：

```json
[
  {
    "trainNo": "G652",
    "instanceNo": "G652-20261117",
    "fromStation": "西安北",
    "toStation": "北京西",
    "fromSeq": 1,
    "toSeq": 3,
    "departTime": "08:35",
    "arriveTime": "16:30",
    "durationMinutes": 475,
    "seats": [
      {"seatNo": "SECOND_CLASS", "seatName": "二等座", "remain": 50, "price": 680.00},
      {"seatNo": "FIRST_CLASS",  "seatName": "一等座", "remain": 20, "price": 1080.00},
      {"seatNo": "BUSINESS",     "seatName": "商务座", "remain": 5,  "price": 2040.00}
    ]
  }
]
```

**实现步骤**（不新建 Mapper，直接在 `TrainMapper` + `TrainMapper.xml` 加两个方法）：

1. `selectAllStations()`：`SELECT id, station_name, city FROM station ORDER BY station_name`
2. `selectByStations(fromStation, toStation)`：

```sql
SELECT t.train_no,
       tsa.station_seq  AS from_seq,
       tsb.station_seq  AS to_seq,
       tsa.depart_time  AS depart_time,
       tsb.arrive_time  AS arrive_time
FROM train t
JOIN train_station tsa ON tsa.train_id = t.id
JOIN station sa       ON sa.id = tsa.station_id
JOIN train_station tsb ON tsb.train_id = t.id
JOIN station sb        ON sb.id = tsb.station_id
WHERE t.status = 1
  AND sa.station_name = #{fromStation}
  AND sb.station_name = #{toStation}
  AND tsa.station_seq < tsb.station_seq
ORDER BY tsa.depart_time
```

3. **必须用上车站的发车时刻 `tsa.depart_time`**，不能用 `t.depart_time`（那是全程始发站的时间，用户看到的应该是他上车的时刻）
4. `durationMinutes` 由 Java 侧 `arrive_time - depart_time` 计算（跨天时补 24 小时）
5. `instanceNo = InstanceNoUtil.of(trainNo, travelDate)`
6. 每个席别调 `ticketService.queryRemain(...)` 拿余票与票价，保证**价格口径和下单一致**（两者都查 `ticket_price`）
7. `price` 为 `null`（缺价）的席别标记为不可售，前端置灰；`remain = 0` 也返回
8. 按 `departTime` 升序
9. 实例不存在或未预热时，该车次仍返回，但 `seats` 全部 `remain = 0`（前端显示"无票"，不要让整条车次消失）

### 2. `GET /api/ticket/stations`

返回全部车站，供前端下拉。

**出参**：`[{"id": 1, "stationName": "西安北", "city": "西安"}, ...]`

### 3. 订单列表补站名

`GET /api/orders/my` 现在返回 `OrderRecord`，只有 `fromSeq/toSeq`，用户看不懂"第几段"。

**方案**：给 `OrderRecord` 加两个**非数据库字段**（不写进 resultMap）：`fromStation`、`toStation`。在 `OrderController.my()` 返回前，用 `train_station` + `station` 按 `(trainNo, seq)` 填充。

若嫌逐个查慢，可一次性把该用户订单涉及的车次经停站全查出来放 Map。

## 四、接口对照表（前端必须严格按这个调）

| 前端动作 | 方法 | 路径 | 关键字段 |
|---|---|---|---|
| 登录 | POST | `/api/auth/login` | body `{username,password}` → `data.accessToken` / `data.refreshToken` |
| 当前用户 | GET | `/api/auth/me` | `data.username` |
| 退出 | POST | `/api/auth/logout` | body `{refreshToken}` |
| 注册 | POST | `/api/auth/register` | body `{username,password,nickname}`（**必须有 nickname，后端字段**） |
| 车站列表 | GET | `/api/ticket/stations` | `data[].stationName` |
| 查车次 | GET | `/api/ticket/search` | `fromStation,toStation,trainDate` → `data[].seats[]` |
| 下单 | POST | `/api/orders` | `{passengerId,trainNo,travelDate,seatNo,fromSeq,toSeq}` |
| 查订单状态 | GET | `/api/orders/{orderNo}` | `data.status` |
| 我的订单 | GET | `/api/orders/my` | `data[]`（需含 `fromStation/toStation`） |
| 取消订单 | POST | `/api/orders/{orderNo}/cancel` | 内部走 `paymentService.userCancel`，**已确认订单可取消并回补库存** |
| 退票 | POST | `/api/orders/{orderNo}/refund` | `?reason=` |
| 退款进度 | GET | `/api/orders/{orderNo}/refund` | `data.status` |
| 预支付 | POST | `/api/pay/prepay` | `?orderNo=` → `data.payToken` |
| 确认支付 | POST | `/api/pay/mock/confirm` | `?payToken=` |
| 支付状态 | GET | `/api/pay/status/{orderNo}` | `data.orderStatus` |
| 乘车人列表 | GET | `/api/passengers` | `data[].id/passengerName/idCard/passengerType` |
| 新增乘车人 | POST | `/api/passengers` | `{passengerName,idCard,passengerType}` |
| 修改乘车人 | PUT | `/api/passengers/{id}` | 同上 |
| 删除乘车人 | DELETE | `/api/passengers/{id}` | - |
| 实例窗口 | GET | `/api/instances/window` | `?trainNo=&days=7` |
| 补齐窗口 | POST | `/api/instances/ensure` | `?days=7` |
| 预热实例 | POST | `/api/instances/{instanceNo}/preheat` | - |
| 清理过期 | POST | `/api/instances/cleanup` | `?delayDays=2` |

**统一响应格式**：`{code, message, data}`。`code=200` 才是业务成功；`data.status` 才是订单/支付的真正状态。

**鉴权约定（两种 401 必须分开处理）**：
- 未登录 / 令牌过期：**HTTP 401** + body `{code:401, message:"未认证或登录已过期"}` → 清 token、跳登录页
- 登录时账号或密码错：**HTTP 200** + body `{code:401, message:"用户名或密码错误"}` → 这是业务失败，只在登录框下红字提示，绝不能跳转

## 五、状态机（必须全覆盖）

### 订单状态 → 界面

| status | 徽标颜色 | 可用操作 |
|---|---|---|
| 待确认 | 灰 | 无（自动轮询） |
| 已确认 | 蓝 | 去支付 / 取消订单 |
| 已支付 | 绿 | 申请退票 |
| 退款中 | 橙 | 查看退款进度 |
| 已退款 | 深绿 | 无 |
| 已取消 | 灰 | 无 |

### 抢票提交（同步返回，不轮询）

```
点提交 → 按钮禁用"提交中"
   → POST /api/orders 一次拿到 {orderNo, status, message}
      → status=已确认 → 切"抢票成功"，显示订单号 + 去支付
      → status=已取消 → 显示 message（余票不足 / 该乘车人已购买此车次车票 / 未配置票价）
```

下单接口内部是 RocketMQ 事务消息 + 本地事务同步执行，**返回时状态已经确定**，不存在"提交中"的中间态。只有返回 `待确认` 才需要兜底查一次 `GET /api/orders/{orderNo}`。

### 支付

```
点去支付 → POST /api/pay/prepay?orderNo= → 拿 payToken
   → POST /api/pay/mock/confirm?payToken=
   → 轮询 GET /api/pay/status/{orderNo}（15 次 × 800ms）
      → orderStatus=已支付 → 成功态
      → 超时 → 提示去订单页确认
```

### 退票

```
点申请退票 → 确认框（显示金额、手续费、实退）
   → POST /api/orders/{orderNo}/refund
   → 状态变退款中 → 可轮询 GET /api/orders/{orderNo}/refund
```

## 六、验收步骤（按顺序跑）

1. `mvn compile` 通过，无编译错误
2. 重启 8081，打开 `http://localhost:8081`
3. 未登录 → 只看到登录页；用 `admin/123456` 登录 → 进订票页
4. 快捷线路点「西安北 → 北京西」，日期选今天 → 出车次列表，至少 3 条，每条 3 个席别有价
5. 点「二等座」→ 确认订单弹窗出现，能选中乘车人，金额正确
6. 提交 → 3 秒内显示「已确认」+ 订单号
7. 点「去支付」→ 收银台 → 确认支付 → 5 秒内「已支付」
8. 切到「我的订单」→ 该订单显示「已支付」，行程显示真实站名
9. 点「申请退票」→ 提交 → 状态变「退款中」
10. 「乘车人」页能新增一个乘车人，列表刷新出现
11. 「运维」面板展开，能查到实例窗口
12. 浏览器控制台无报错

## 七、禁止事项

1. 不改 Service / Mapper 里已有的业务 SQL（除了新增接口需要的查询）
2. 不在前端硬编码车次号、站 ID、乘客 ID
3. 不用 `alert()` 做主要交互，用页面内弹窗和 toast
4. 不把 `remain`、`price` 当字符串直接显示，统一转数字后格式化
5. 不省略错误分支：每一处 `fetch` 失败都要有用户可见的提示
6. 不修改 `?v=` 版本号以外的缓存策略

## 八、三次复检记录

### 第 1 次复检：接口与字段对齐（对照源码逐项核查）

| # | 发现 | 处置 |
|---|---|---|
| 1 | `RegisterRequest` 有 `username/password/nickname` 三个字段，原提示词的注册流程漏了 `nickname` | 已补进接口对照表 |
| 2 | `PassengerServiceImpl#validate` 校验 `type ∈ [1,3]`，文案是「1 成人、2 学生、3 儿童」，规划原写成「成人/儿童/学生」，顺序错 | 已改 |
| 3 | 401 有两种形态：`SecurityConfig` 的 entryPoint 写 HTTP 401；`GlobalExceptionHandler` 对 `BadCredentialsException` 返回 HTTP 200 + code 401 | 已补「鉴权约定」，避免前端把密码错当成登录过期去跳转 |

确认无误：`Result.code` 是 `int`，`code === 200` 判断成立；`pay.mock.timeout-seconds = 900`，前端 15 分钟倒计时与后端关单阈值一致。

### 第 2 次复检：状态与流程分支

| # | 发现 | 处置 |
|---|---|---|
| 4 | 下单接口内部用的是 RocketMQ 事务消息 + 同步本地事务，`OrderServiceImpl` 直接返回 `已确认` 或 `已取消`，**没有中间态** | 原设计「轮询 5 次 × 400ms」多余，改为直接读返回的 `status`，只对 `待确认` 兜底查一次 |
| 5 | `OrderController` 的取消接口实际调 `paymentService.userCancel(orderNo)`，而 `orderService.cancelOrder` 只处理 `待确认 → 已取消` | 已确认订单**确实可以取消并回补库存**，订单页给「已确认」配取消按钮是对的，已在文档注明走的是哪条链路 |
| 6 | 退款手续费 `refund.fee-rate` 默认 `0.00`，实退金额 = 票款全额 | 明确前端不得自乘比例，一律用接口返回的 `fee` / `refundAmount` |
| 7 | 缺价时 `PriceService` 抛 `BizException` 拒绝下单（fail-close），`ticketService` 的 price 会置 `null` | 要求 search 接口把缺价席别标记为不可售，前端置灰，避免用户点了才在下单时被拒 |

### 第 3 次复检：可执行性与边界

| # | 发现 | 处置 |
|---|---|---|
| 8 | 项目里没有 `StationMapper`，但 `TrainMapper` 已存在 | 两条按站查询的 SQL 直接加进 `TrainMapper` + `TrainMapper.xml`，不新建文件，改动面最小 |
| 9 | 车次时刻必须取经停站表的 `tsa.depart_time` / `tsb.arrive_time`，`train.depart_time` 是全程始发时刻 | 已在 SQL 里显式指定，否则用户会看到错误的上车时间 |
| 10 | `OrderRecord` 没有站名字段，`my()` 只返回 `fromSeq/toSeq` | 补两个非数据库映射字段 `fromStation/toStation`，在 `my()` 返回前填充，否则订单页只能显示「第 1 段 → 第 3 站」 |

补充边界：日期条只渲染 7 天（实例滚动窗口上限），第 8 天必然查不到实例，不渲染可避免用户误以为系统故障。

**结论**：三轮共修正 10 处，接口契约、状态分支、实现路径、展示口径均与真实代码对齐，可以进入执行。
