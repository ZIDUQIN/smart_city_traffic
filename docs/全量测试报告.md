## 二、缺陷清单（原始发现记录）

> 以下为修复前的原始记录，当前修复状态见第一节表格。

### D-01【中】三个读接口无归属校验，可越权读他人订单 / 支付 / 退款
- 用例：D11 / E10 / G8
- 复现：用户 B 持合法 token 调 `GET /api/orders/{A的订单号}`、`GET /api/pay/status/{A的订单号}`、`GET /api/orders/{A的订单号}/refund`，均返回 200 及完整数据。
- 根因：三个查询只按订单号查库，未比对当前登录用户。写接口（取消 / 退款 / prepay）都有归属校验，读接口漏了。
- 影响：订单状态、支付金额、退款金额可被任意登录用户遍历读取（订单号为雪花 ID，可枚举）。
- 修复：三处查出记录后比对 `userId == 当前用户`，不符返回 400/403，与写接口口径一致。

### D-02【中】缓存缺失时回补凭空造出"幻影库存"
- 用例：C5（实测 remain=1，DB 实际 49）
- 复现证据链：库存 Redis key 被清（DEL 返回 0）→ 22:57 一笔超时关单触发 `rollback.lua` → 脚本对不存在的 key 直接 `HINCRBY`，造出只含区段 1、值为 1 的 Hash → 单区段查询信任该 Hash，返回 1；直到一次多区段查询走 DB 回源 `putAll` 才自愈。
- 根因：`rollback.lua` 未检查 `EXISTS KEYS[1]`。生产可达路径：实例清理删缓存后仍发生退款 / 超时回补；Redis eviction / 故障切换丢 key。
- 连带问题：若"已扣减集合"也丢失，`SREM` 返回 0 → 脚本整体返回 0 → 乘车人占位不释放，该乘车人被锁最长 3 天（占位 TTL 259200s），而 DB 回补经幂等表仍会进行。
- 影响：余票显示错误（常见偏低 → 假售罄 / 少卖）；扣减闸也读幻影值。正常流程下幻影 ≤ 真实余票，超卖风险低，但一致性被破坏。
- 修复：`rollback.lua` 在 `SREM==1` 分支内加 `EXISTS` 判断——key 存在才 `HINCRBY`，不存在则跳过 Redis 回补（DB 为准，下次查询回源）；**占位释放不受 key 是否存在影响，必须执行**。或把回补路径统一改为"删缓存令其回源"。

### D-03【中】管理 / 调试端点无角色控制，普通用户可调
- 用例：K4
- 复现：普通用户 load001 调 `POST /api/instances/ensure`、`/api/instances/cleanup`、`/api/orders/preheat`、`/api/pay/mock/refund-result`，全部 200。
- 影响：任意登录用户可触发实例批量创建 / 清理 / 预热；`mock/refund-result` 可注入渠道退款结果，配合 D-01 读到的他人退款单号，可操纵对账把他人退款置为成功 / 失败（演示环境危害有限，生产必须杜绝）。
- 修复：加轻量角色标识（如 sys_user 增 admin 标志）+ 拦截器校验；`mock/*` 端点至少用 profile 限制仅 dev 生效。

### D-04【中】注册无长度校验，超长用户名 500 且泄露内部细节
- 用例：A9
- 复现：注册 200 字符用户名 → 500，响应体直接返回 MyBatis 异常，含 Mapper 文件绝对路径与 INSERT SQL。
- 根因：register 未校验 username/nickname 长度，DB 截断报错；`GlobalExceptionHandler.handleException` 把 `e.getMessage()` 原样拼进响应。
- 影响：拒绝服务式脏请求 + 信息泄露（路径 / 表结构 / SQL）。
- 修复：register 增字段长度与字符校验（如 username≤32）；兜底异常处理只返回通用文案，细节写日志。

### D-05【低】支付回调金额解析无防御，与退款回调不对称
- 用例：E9
- 复现：合法签名但缺 `amount` 的支付回调 → HTTP 200 `{"code":400,"message":null}`，而非渠道契约的 `{"code":"FAILURE"}`。
- 根因：`new BigDecimal(node.path("amount").asText())` 缺字段抛 `NumberFormatException`（继承 `IllegalArgumentException`）→ 被 400 处理器接住、message 为 null。退款回调有 try/catch 返回 FAILURE，支付侧没有。
- 影响：渠道按非 SUCCESS 重试 3 次均无效；行为与退款侧不一致。
- 修复：支付回调金额解析包 try/catch，失败返回 false（FAILURE），与退款侧对齐。

## 五、观察项（非缺陷，建议跟进）

1. D4：不存在车次下单提示"库存未预热"，文案误导，应区分"车次不存在"。
2. C10：窗口外日期查询仍返回车次但余票全 0，前端日期选择应限制（语音侧已拦）。
3. K1：actuator health 匿名返回磁盘路径 / DB 细节，metrics 匿名开放——生产应 `show-details=never` 并加鉴权。
4. 历史"每单重复回补"的触发源仍未定位；三层防护已验证能兜住（F2/F6/G10/H3），建议保留告警日志继续观察。
5. 语音验收脚本收尾会清缓存并保留测试订单——这正是 D-02 的前置条件，修复 D-02 后此路径才安全。

## 六、本轮未测及原因

| 项 | 原因 |
|---|---|
| 雪花 worker 编号竞争 | 需多实例同时启动，单机无法复现 |
| 真实方言识别准确率 | 需人工方言语音样本，非接口层可测 |
| TTS 音质 / 打断 | 主观体验项，此前已实机验证 |
| 多实例分布式锁 | 需双实例部署，单机 cron 锁无竞争 |
| CSRF | 纯 Bearer token 架构，非 Cookie 会话，不适用 |
| MQ broker 宕机 | 需停 RocketMQ，影响面大，事务消息四步已在代码与正常链路验证 |
