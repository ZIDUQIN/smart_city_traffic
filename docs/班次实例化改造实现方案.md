## 0. 事实基座

方案中的每个判断都基于以下已核实事实，不是假设：

| 编号 | 事实 | 出处 |
|---|---|---|
| F1 | 预热是覆盖式的：先 `DEL` 再 `putAll` | `OrderServiceImpl#preheat` 第 301-302 行 |
| F2 | 预热按 `segment_no` 分组，多日期数据会互相覆盖 | `OrderServiceImpl#preheat` 第 293-294 行 |
| F3 | `deduct.lua` 在库存 field 不存在时返回 -2，安全失败 | `deduct.lua` 第 22-25 行 |
| F4 | DB 库存在下单事务内同步扣减（`remain>0` 才扣） | `StockServiceImpl#deductRealStock` |
| F5 | 下单走 RocketMQ 事务消息，本地步骤有完整补偿链 | `OrderServiceImpl#executeLocalSteps` |
| F6 | 库存表存在唯一索引 `uk_train_seat_segment(train_no, seat_no, segment_no)` | `SHOW INDEX FROM stock` |
| F7 | Redis key 在 Java 侧构造，Lua 只接收 KEYS | `RedisLuaServiceImpl` 第 110-117 行 |

F7 带来一个好消息：**Lua 脚本本身零改动**，只改 Java 侧 key 构造。

## 1. 设计决策

二十轮推导后的结论，每条都写清"放弃了什么"：

| 决策 | 内容 | 理由 | 放弃了 |
|---|---|---|---|
| D1 | 实例编号 = `{班次号}-{yyyyMMdd}` | 可读、可解析、天然幂等 | 流水号（不可读，需要额外发号器） |
| D2 | Redis hash tag 用实例编号 | 不同日期分散到不同槽（实测 7 个不同槽），同日原子性保住 | 用班次号当 tag（7 天堆一槽） |
| D3 | 对外接口传"班次号 + 日期"，内部全用实例编号 | 前端和 AI 都按"哪天哪班"表达，不暴露内部编号 | 对外暴露 instanceNo（前端要自己拼，易错） |
| D4 | 票价、容量挂模板；库存挂实例 | 票价和容量是线路属性，不随日期变 | 全部挂实例（每张多份冗余） |
| D5 | 预热用 `HSETNX` 逐字段写 | 天然幂等，绝不覆盖已售数据，不需要先判 key 存在 | 复用现有 `DEL + putAll`（会超卖） |
| D6 | 窗口任务每分钟检查完整性，不是每天加一天 | 停机后自动补齐；单次失败下一分钟自愈 | 每天 0 点只跑一次（失败即断档） |
| D7 | 过期实例延迟 2 天清理 | 覆盖"23:50 下单、00:10 取消"的回补窗口 | 立即删（回补会造孤儿 key） |
| D8 | 防重购 key 设 TTL | 清理时不用 SCAN 枚举（集群下 SCAN 麻烦） | 永久 key + 手动清理 |
| D9 | 重建接口允许 `DEL` 覆盖 | DB 是权威源，重建就是"用 DB 覆盖 Redis" | 重建也用 HSETNX（DB 为准时必须能覆盖） |
| D10 | 订单表同时存 `train_no` 和 `instance_no` | 统计查询便利，避免解析字符串 | 只存 instance_no（字符串解析不可靠） |

## 2. 数据库

### 2.1 新增三张表

```sql
-- 班次实例
CREATE TABLE train_instance (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  instance_no   VARCHAR(48)  NOT NULL COMMENT '实例编号，格式 班次号-yyyyMMdd',
  train_no      VARCHAR(32)  NOT NULL,
  travel_date   DATE         NOT NULL COMMENT '运营日期',
  status        TINYINT      NOT NULL DEFAULT 1 COMMENT '1=正常 2=停运',
  stock_preheated TINYINT    NOT NULL DEFAULT 0 COMMENT '0=未预热 1=已预热',
  create_time   DATETIME     NOT NULL,
  update_time   DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_instance_no (instance_no),
  UNIQUE KEY uk_train_date (train_no, travel_date),
  KEY idx_travel_date (travel_date),
  KEY idx_train_date_status (train_no, travel_date, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='班次实例';

-- 容量表（模板层）
CREATE TABLE stock_capacity (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  train_no       VARCHAR(32) NOT NULL,
  seat_no        VARCHAR(32) NOT NULL,
  segment_no     INT         NOT NULL,
  total_capacity INT         NOT NULL COMMENT '该段总座位数',
  PRIMARY KEY (id),
  UNIQUE KEY uk_capacity (train_no, seat_no, segment_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='班次容量（模板层）';

-- 票价表（模板层）
CREATE TABLE ticket_price (
  id        BIGINT        NOT NULL AUTO_INCREMENT,
  train_no  VARCHAR(32)   NOT NULL,
  from_seq  INT           NOT NULL,
  to_seq    INT           NOT NULL,
  seat_no   VARCHAR(32)   NOT NULL,
  price     DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_price (train_no, from_seq, to_seq, seat_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='票价（按起讫站对）';
```

`uk_train_date` 是幂等的核心：同一班次同一天只允许一个实例，重复插入必然冲突，任务据此判断"已存在"。

### 2.2 改造两张表

**库存表**：必须先删旧唯一索引，否则第二天的数据插不进去（F6）。

```sql
ALTER TABLE stock DROP INDEX uk_train_seat_segment;
ALTER TABLE stock
  ADD COLUMN instance_no  VARCHAR(48) NULL COMMENT '班次实例编号' AFTER id,
  ADD COLUMN train_no_v2  VARCHAR(32) NULL COMMENT '冗余班次号，便于统计';
-- 用新列承载数据，旧列先保留，迁移完成后再删（回滚友好）
UPDATE stock SET instance_no = CONCAT(train_no, '-', DATE_FORMAT(NOW(), '%Y%m%d')),
                 train_no_v2 = train_no
                 WHERE instance_no IS NULL;
ALTER TABLE stock
  MODIFY instance_no VARCHAR(48) NOT NULL,
  MODIFY train_no_v2  VARCHAR(32) NOT NULL;
ALTER TABLE stock ADD UNIQUE KEY uk_instance_seat_segment (instance_no, seat_no, segment_no);
ALTER TABLE stock ADD KEY idx_train_no_v2 (train_no_v2);
```

**订单表和流水表**：加实例编号，允许为空（历史数据兼容）。

```sql
ALTER TABLE `order`
  ADD COLUMN instance_no VARCHAR(48) NULL COMMENT '班次实例编号' AFTER train_no,
  ADD COLUMN travel_date DATE NULL COMMENT '运营日期，冗余便于查询' AFTER instance_no;

ALTER TABLE ticket_deduct_record
  ADD COLUMN instance_no VARCHAR(48) NULL AFTER train_no,
  ADD COLUMN travel_date DATE NULL AFTER instance_no;
```

**历史数据修正**（50 条订单 + 对应流水）：

SET instance_no = CONCAT(train_no, '-', DATE_FORMAT(create_time, '%Y%m%d')),
    travel_date = DATE(create_time)
WHERE instance_no IS NULL;

UPDATE ticket_deduct_record
SET instance_no = CONCAT(train_no, '-', DATE_FORMAT(create_time, '%Y%m%d')),
    travel_date = DATE(create_time)

### 2.3 迁移执行顺序

顺序错了会失败，必须按这个走：

1. 建三张新表
2. 从现有 `stock` 表灌 `stock_capacity`（`total_capacity = remain`，因为此刻还没卖过，remain 就是初始容量）
3. 从现有票价逻辑灌 `ticket_price`（先按旧规则填，后续爬取数据再覆盖）
4. 删 `stock` 旧唯一索引
5. `stock` 加新列、回填、加新唯一索引
6. `order` / `ticket_deduct_record` 加列并回填
7. 生成今天起 7 天的实例和库存（用迁移脚本，不是靠任务，避免首次启动时任务还没跑）

第 2 步的假设"remain 就是初始容量"只在迁移这一刻成立。迁移后容量以 `stock_capacity` 为准，不再从 `stock` 推。

## 4. 核心算法

### 4.1 窗口任务（每分钟）

```java
@Scheduled(cron = "0 * * * * *")   // 每分钟第 0 秒
public void guardWindow() {
    LocalDate today = LocalDate.now();
    LocalDate end = today.plusDays(6);
    // 轻量判断：窗口内实例数是否齐全
    int expected = activeTrainCount() * 7;
    int actual = instanceMapper.countInRange(today, end).intValue();
    if (actual >= expected) {
        cleanupExpired();   // 数量齐了也照常清理过期
        return;
    }
    if (!lock.tryLock("instance:window:lock", instanceId, 120)) return;
    try {
        for (LocalDate d = today; !d.isAfter(end); d = d.plusDays(1)) {
            for (String trainNo : activeTrainNos()) {
                ensureInstance(trainNo, d);   // 幂等
            }
        }
        cleanupExpired();
    } finally {
        lock.unlock("instance:window:lock");   // 只删自己持有的锁
    }
}
```

关键点：

- **不判断"今天补 D+7"，而是"确保窗口内每一天都存在"**（D6）。停机 3 天后重启，一次补齐 3 天
- 锁 TTL 120 秒，大于任务耗时（首次生成 20 班次 × 7 天约 140 次插入 + 420 次 Redis 写，1 核机器约 30-60 秒）
- 数量齐全时只做清理，不做全量遍历，避免每分钟 140 次查询

### 4.2 确保实例存在（幂等）

```java
public void ensureInstance(String trainNo, LocalDate date) {
    String instanceNo = trainNo + "-" + date.format(BASIC_ISO_DATE);
    TrainInstanceRecord ins = instanceMapper.selectByInstanceNo(instanceNo);
    if (ins == null) {
        try {
            instanceMapper.insert(newInstance(instanceNo, trainNo, date));
            ins = instanceMapper.selectByInstanceNo(instanceNo);
        } catch (DuplicateKeyException e) {
            ins = instanceMapper.selectByInstanceNo(instanceNo);   // 并发安全
        }
    }
    if (ins.getStatus() == STOPPED) return;       // 停运，不生成库存
    if (ins.getStockPreheated() == 1) return;     // 已预热，绝不碰

    // 生成缺失的库存行（有唯一索引，重复插入会冲突，用 INSERT IGNORE）
    for (StockCapacityRecord cap : capacityMapper.selectByTrainNo(trainNo)) {
        stockMapper.insertIgnore(instanceNo, trainNo, cap.getSeatNo(),
                                 cap.getSegmentNo(), cap.getTotalCapacity());
    }
    preheatInstance(instanceNo);
    instanceMapper.markPreheated(instanceNo);
}
```

### 4.3 实例预热（防覆盖，这是 P0-1 和 P0-2 的修法）

```java
public void preheatInstance(String instanceNo) {
    List<StockRecord> rows = stockMapper.selectByInstanceNo(instanceNo);  // 按实例查，不是按车次
    Map<String, Map<String, String>> bySeat = groupBySeat(rows);
    for (var entry : bySeat.entrySet()) {
        String key = stockKey(instanceNo, entry.getKey());
        // HSETNX：字段不存在才写，存在就跳过 —— 天然幂等，绝不覆盖已售
        for (var field : entry.getValue().entrySet()) {
            redis.opsForHash().putIfAbsent(key, field.getKey(), field.getValue());
        }
        redis.expire(key, Duration.ofDays(10));   // 与窗口 + 清理窗口对齐
    }
}
```

三条不可违反的约束：

1. **按实例查**（`selectByInstanceNo`），不能按车次查（F2 的问题）
2. **用 `putIfAbsent`（HSETNX）**，不能 `DEL + putAll`（F1 的问题）
3. 现有 `OrderServiceImpl#preheat(trainNo, seatNo)` **保留但加保护**，方法名改成 `preheatTemplateForDebug`，内部断言"仅用于无实例的老数据"，并在注释里写明禁止用于已售实例

### 4.4 下单流程（改造后）

顺序和现有完全一致（F5），只换参数和加一次校验：

```
1. 限流（不变）
2. 参数解析：trainNo + travelDate → instanceNo
3. 实例校验（新增）：
   - 实例不存在 → "该日期尚未开售"
   - status=停运 → "该班次已停运"
   - travelDate 超出 7 天窗口 → "仅可预订 7 天内"
4. 乘客归属校验（不变）
5. 预检 check（参数换 instanceNo）
6. 事务消息 → executeLocalSteps：
   1) 写流水（加 instance_no）
   2) Lua 扣 Redis（key 用实例编号）
   3) CAS 已扣减
   4) 建订单（加 instance_no）
   5) DB 扣库存（按 instance_no 条件 UPDATE）
   6) 订单 CAS 待确认 → 已确认
   7) 流水 CAS → 已建单
7. COMMIT
```

**步骤 3 放在预检之前**，因为实例不存在是"快速失败"，不该消耗限流令牌和 Redis 调用。

### 4.5 过期清理（P0-3 的修法）

```java
public void cleanupExpired() {
    LocalDate cutoff = LocalDate.now().minusDays(2);   // 延迟 2 天
    List<TrainInstanceRecord> expired = instanceMapper.selectExpired(cutoff);
    for (TrainInstanceRecord ins : expired) {
        // 有活跃订单就跳过，下一轮再试
        if (orderMapper.countActiveByInstance(ins.getInstanceNo()) > 0) continue;

        List<String> seats = stockMapper.selectSeatsByInstance(ins.getInstanceNo());
        for (String seat : seats) {
            redis.delete(stockKey(ins.getInstanceNo(), seat));
            redis.delete(deductedKey(ins.getInstanceNo(), seat));
        }
        // 防重购 key 靠 TTL 自动过期，不枚举删除（D8）
        stockMapper.deleteByInstance(ins.getInstanceNo());
        instanceMapper.deleteByInstanceNo(ins.getInstanceNo());
    }
}
```

"活跃订单"的定义：`status` 属于（待确认、已确认未支付、已支付未完成）的三类。已取消、已退款、已完成不算活跃。

### 4.6 重建（D9）

```java
// 仅管理接口调用，DB 是权威源，允许覆盖
public int rebuild(LocalDate from, LocalDate to) {
    int count = 0;
    for (LocalDate d = from; !d.isAfter(to); d = d.plusDays(1)) {
        for (TrainInstanceRecord ins : instanceMapper.selectByDate(d)) {
            List<StockRecord> rows = stockMapper.selectByInstanceNo(ins.getInstanceNo());
            Map<String, Map<String,String>> bySeat = groupBySeat(rows);
            for (var e : bySeat.entrySet()) {
                String key = stockKey(ins.getInstanceNo(), e.getKey());
                redis.delete(key);                       // 允许覆盖
                redis.opsForHash().putAll(key, e.getValue());
                redis.expire(key, Duration.ofDays(10));
                count++;
            }
            instanceMapper.markPreheated(ins.getInstanceNo());
        }
    }
    return count;
}
```

重建前建议先跑一次对账，把 DB 修准。否则重建出来的是"错的数据的镜像"。

## 6. 一致性保证

### 6.1 锁

| 锁 | key | TTL | 说明 |
|---|---|---|---|
| 窗口任务 | `instance:window:lock` | 120 秒 | 独立锁，不复用现有三把 |
| 对账 | `reconcile:lock` | 55 秒 | 不变 |
| 支付超时 | `payment:timeout:lock` | 55 秒 | 不变 |
| 退款对账 | `refund:reconcile:lock` | 55 秒 | 不变 |

四把锁的 value 都是 `端口:随机码`（现有 `InstanceId`），释放时校验 value 再删，避免删掉别人的锁。

**时间错峰**：窗口任务每分钟触发，对账/支付超时是整分钟触发，会撞在同一秒。建议把对账改成 `30 * * * * *`（每分钟第 30 秒），错开 30 秒。

### 6.2 事务边界

不变。仍然是"事务消息 + 本地步骤 + CAS 状态机 + 补偿"。改造只换参数，**不引入新的分布式事务**。

### 6.3 补偿路径

四条补偿全部要改参数，逻辑不变：

| 场景 | 补偿动作 |
|---|---|
| 步骤 2 扣 Redis 异常 | CAS 流水 → 已取消，不回补 |
| 步骤 3 建订单失败 | 回补 Redis + CAS → 已补偿 |
| 步骤 4 扣 DB 失败 | 取消订单 + 回补 Redis + CAS → 已取消 |
| 步骤 6/7 CAS 失败 | 取消 + 回补 + 抛异常禁止 COMMIT |

### 6.4 对账兼容

`DeductReconcileTask` 改三点：

1. 扫库存时按 `instance_no` 分组，不按 `train_no`
2. 跳过 `stock_preheated = 0` 的实例（刚生成未预热，对比必然不一致）
3. 对比 Redis 时 key 用实例编号

| `instance.stock.gap` | Gauge | DB 有、Redis 无的实例数，>0 告警 |
| `instance.window.task.cost` | Timer | 超过 90 秒告警（说明锁 TTL 快不够用） |

## 10. 风险与回滚

| 风险 | 应对 |
|---|---|
| 迁移中途失败 | 迁移脚本包在一个事务里（DDL 除外），失败即回滚数据变更 |
| 旧索引删错 | 回滚脚本：先删新索引，再重建 `uk_train_seat_segment` |
| 预热被误用于已售实例 | 代码层：旧 preheat 改名为调试专用并加断言；上线后搜一次调用点确认无人使用 |
| 窗口任务卡死 | 锁 TTL 120 秒自动释放；有手动补齐接口兜底 |
| 数据全丢（Redis 清空） | 重建接口按日期区间恢复；DB 是权威源 |
| 代码回滚 | `stock` 旧列（`train_no`、`seat_no`、`segment_no`）**暂不删除**，保留一个版本周期，确认稳定后再清理 |

**保留旧列**是这次改造的回滚保险，不要在第一批就删。
