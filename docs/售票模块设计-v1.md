## 一、整体链路拆成两条（关键认知）

### 读链路（查车次、看余票）

```
浏览器 → CDN（静态资源：页面、JS、CSS、图片）
      → Ajax 拉动态数据（余票、票价）
      → ① 本地缓存 Caffeine（TTL 1 秒，兜底刷新）
      → ② Redis（分布式缓存）
      → ③ MySQL（数据源）
数据变更 → RocketMQ 广播 → 各节点刷新本地缓存（主动更新，阶段 3 实现）
```

要点：本地缓存 TTL 只有 1 秒，是**为了让不同节点最终收敛**的兜底机制；主动刷新靠 MQ 广播。两者配合 = 短 TTL + 主动失效。

### 写链路（提交订单扣余票）

```
提交订单 → 限流（用户/IP 维度）
        → Redis + Lua 原子执行：判重（一人一单）→ 判余票 → 扣减
        → 成功则建订单（状态：待支付）→ 返回订单号
        → 失败直接返回：已购买 / 余票不足
```

**核心差异**：写链路**不用本地缓存**做任何判断，直接打 Redis。余票是强一致数据，本地缓存只服务"展示"，不参与"决策"。

## 二、数据模型：余票按「相邻区段」存

一趟车 A→B→C→D，余票不是存一个总数，而是存相邻区段的余量：

| 区段序号 | 区间 | 二等座余量 |
|---|---|---|
| 1 | A→B | 100 |
| 2 | B→C | 100 |
| 3 | C→D | 100 |

- 查 A→C 的余票 = `MIN(区段1, 区段2)` = 100
- 扣 A→C 的票 = 区段1 和区段2 各减 1
- 好处：A→B 和 B→C 可以卖同一个座位，座位复用，这是 12306 的余票本质

## 四、Redis key 设计

| key | 类型 | 内容 | 用途 |
|---|---|---|---|
| `ticket:{trainId}:{seatType}` | Hash | field = segment_no，value = 剩余票数 | **核心**。一张车次一个席别一个 key，所有区段放在同一个 Hash 里 |
| `order:dedup:{trainId}` | Set | member = userId | 一人一单判重（也可用 `order:lock:{trainId}:{userId}` String NX） |
| `order:wait:{orderId}` | String | 订单摘要，TTL = 支付超时时长 | 待支付订单快速查询 + 超时兜底 |
| `order:pay:delay` | ZSet | score = 支付截止时间戳，member = orderId | 阶段 3 定时扫描超时订单（或换 RocketMQ 延迟消息） |
| `null:train:{trainId}` | String | "1" | 缓存空值，防缓存穿透，TTL 60 秒 |
| `limit:{userId}:{api}` | String | 计数器 | 限流，阶段 2 加 |

### 为什么用 Hash 而不是每个区段一个 key（重要）

Redis Cluster 模式下，**同一个 Lua 脚本里操作的所有 key 必须落在同一个 slot**。如果每个区段一个 key（如 `ticket:1001:1`、`ticket:1001:2`），跨区间扣票要操作多个 key，在集群下会报 `CROSSSLOT` 错误。

用 Hash 把「同一车次同一席别的所有区段」放在一个 key 里：
- 一次 Lua 只操作一个 key，天然同 slot，**集群安全**
- 多区段扣减在一个 key 内原子完成
- 减少 key 数量

这就是本项目值得写进简历的技术细节。

## 五、读链路：查询余票接口

```
GET /api/ticket/remain?trainId=&fromSeq=&toSeq=&seatType=
```

处理顺序：

1. **参数校验**：trainId 存在性、fromSeq < toSeq、席别合法
2. **本地缓存**（Caffeine，TTL 1 秒，key = trainId:fromSeq:toSeq:seatType）
   - 命中 → 直接返回
3. **Redis**：`HGET`/`HMGET` 取 fromSeq 到 toSeq 之间所有区段，取最小值
   - 命中 → 回填本地缓存 → 返回
4. **缓存空值判断**：`null:train:{trainId}` 存在 → 直接返回"车次不存在"，防止穿透
5. **数据库**：查 seat_inventory，取区间最小值
   - 查到 → 回填 Redis（不设过期，由 MQ 主动刷新维护）→ 回填本地缓存 → 返回
   - 查不到 → 写 `null:train:{trainId}`（60 秒）→ 返回"车次不存在"

可讲的技术点：三级缓存、TTL 兜底 + MQ 主动刷新、缓存空值防穿透、（进阶）布隆过滤器。

## 六、写链路：提交订单接口（阶段 2）

```
POST /api/ticket/order
```

Lua 脚本逻辑（单 key 内完成）：

```
输入：KEYS[1] = ticket:{trainId}:{seatType}，ARGV[1] = 上车站序，ARGV[2] = 下车站序，ARGV[3] = 购买数量
1. 遍历 fromSeq 到 toSeq-1 的每个区段，取当前余量
2. 若任一区段余量 < 购买数量 → return 余票不足
3. 每个区段 HINCRBY -数量
4. return 扣减成功后的区段余量
```

一人一单判重放在 Lua 之前的 `SET NX`，或与扣减合并（阶段 2 再定）。

返回状态码约定：
- 0 成功
- 1 余票不足
- 2 已购买（重复下单）
- 3 车次不存在

## 八、已确认决策（v1.1）

1. **余票模型**：采用「相邻区段 + Hash 单 key」，贴近 12306 真实模型。
2. **席别**：二等座 `SECOND_CLASS`、一等座 `FIRST_CLASS`、商务座 `BUSINESS` 三种。
3. **乘车人**：不简化，提前到阶段 1。用户可维护多个乘车人，**同一用户下身份证号不可重复**，下单时选择已有乘车人。

## 九、乘车人模块（v1.1 补充）

### 业务规则

- 一个用户可以有多个乘车人，乘车人属于该用户，**不可跨用户使用**
- 同一用户下，**身份证号唯一**（新增、修改都要校验）
- 乘车人类型：1 成人、2 学生、3 儿童
- 下单时传 `passengerId`，服务端反查乘车人，校验归属后使用

### 表结构：passenger 乘车人

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 雪花 ID |
| user_id | BIGINT | 所属用户 |
| passenger_name | VARCHAR(64) | 姓名 |
| id_card | VARCHAR(32) | 身份证号 |
| passenger_type | TINYINT | 1 成人 2 学生 3 儿童 |
| create_time | DATETIME | 创建时间 |
| update_time | DATETIME | 更新时间 |

约束：`UNIQUE KEY uk_user_id_card (user_id, id_card)` —— 数据库层兜底防重复，业务层提前给出友好提示。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/passengers` | 新增乘车人 |
| GET | `/api/passengers` | 查询当前用户的乘车人列表 |
| PUT | `/api/passengers/{id}` | 修改乘车人 |
| DELETE | `/api/passengers/{id}` | 删除乘车人 |

安全细节：返回给前端时身份证号做脱敏（保留前 4 位和后 4 位）。
