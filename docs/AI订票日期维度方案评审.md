# 方案乙（班次模板 + 班次实例）可行性评审

日期：2026-11-16
评审对象：7 天滚动窗口 + 班次实例化改造
方法：十轮交叉审查，每轮换一个失效视角

---

## 零、评审依据：已核实的代码事实

不先确认事实就评审，结论都是空的。以下五条是读了代码确认的：

| 编号 | 事实 | 出处 |
|---|---|---|
| F1 | **预热是覆盖式的**：先 `DEL` 旧 key，再 `putAll` 写 Hash | `OrderServiceImpl#preheat` 第 301-302 行 |
| F2 | **预热按"车次"查库、按"区段号"分组**：同一个区段号只保留最后一条 | `OrderServiceImpl#preheat` 第 282、293-294 行 |
| F3 | **库存未预热时扣减返回 -2**，属于安全失败（不会误扣） | `deduct.lua` 第 22-25 行 |
| F4 | **DB 库存在下单事务里同步扣减**，不是异步落库 | `StockServiceImpl#deductRealStock` 第 27-31 行 |
| F5 | 三个 key 用同一个 hash tag，同日同班次同槽（实测 1682） | CRC16 实测 |

F1 和 F2 是这次评审里最要命的两条，后面反复用到。

---

## 第 1 轮：数据模型完整性

| 检查项 | 结论 |
|---|---|
| 库存表加日期后，旧唯一索引怎么办 | **缺陷**。现在的唯一约束是 `(train_no, seat_no, segment_no)`，加日期列后必须先删旧索引、再建 `(instance_no, seat_no, segment_no)`，否则第二天的数据插不进去 |
| 订单表加实例编号，历史 50 单怎么办 | **缺陷**。直接加 `NOT NULL` 会失败。要么允许为空，要么批量填一个默认实例 |
| 容量表和库存表会不会不一致 | 会。容量表有、库存表缺某天 → 该天查不到票。需要一致性校验 |
| 实例编号格式 | `G1001-20261118` 可解析。约束：班次号本身不能含 `-`，现实车次号不含，可接受，但要写进文档 |

**级别**：索引问题是 P1（不改就插不进数据），其余 P2。

---

## 第 2 轮：0 点滚动任务（问题最多的一轮）

| 检查项 | 结论 |
|---|---|
| 任务能不能直接调现有 preheat | **不能，这是 P0**。F1 说它是覆盖式的，如果对"已经卖过的日期"调用，会把已售座位重置为满票 → 直接超卖 |
| preheat 能不能直接用在多日期数据上 | **不能，这是 P0**。F2 说它按"区段号"分组，7 天数据混在一起时，同区段号互相覆盖，最后只剩一天的数字。必须改成按实例查、按实例预热 |
| 任务只加 D+7 够不够 | **不够，P1**。服务停 3 天再启动，窗口会缺 3 天。任务逻辑必须是"确保窗口内每一天都有实例和库存"，而不是"每天加一天" |
| 任务跑得完吗 | **风险，P1**。首次生成 20 班次 × 7 天 + 420 次 Redis 写，1 核机器可能超过锁的 55 秒 TTL，锁过期后另一实例会重入 |
| 任务重复跑会不会生成重复实例 | 不会，前提是唯一索引兜底 + `ON DUPLICATE KEY` 或先查后插 |

**这一轮的结论：滚动任务必须是"幂等补齐 + 只对新实例预热"，不能复用现有 preheat。**

---

## 第 3 轮：扣减原子性

| 检查项 | 结论 |
|---|---|
| 同一天三个 key 是否同槽 | 是（实测 1682），原子性保住 |
| 不同日期是否分散 | 是（10076 / 14205 / 1682 / 5811 / 4809 / 744 / 12939） |
| 乘车人判重是否要加日期 | 要。`passenger:dedup:{实例}:{乘客}`，这样同一人能买不同日期的票，但同一天同一班次不能重复 |
| 站数变化后段位连续吗 | 依赖数据质量。段号必须从 1 连续到 n-1，中间断了会导致漏扣一段，**P1**，要有数据校验 |

---

## 第 4 轮：并发与边界时刻

| 检查项 | 结论 |
|---|---|
| 0 点瞬间，D+7 从"不可售"变"可售" | **缺陷，P1**。如果任务慢了几分钟，用户在 00:01 查 D+7 会得到"无票"，以为是售罄。前端要区分"未开售"和"售罄" |
| 双实例锁过期重入 | 锁 TTL 55 秒 < 任务最长耗时，会重入。靠唯一索引幂等兜住，但会浪费资源。**建议把窗口任务单独用一把锁、TTL 提到 120 秒** |
| 同一用户并发买同一天同一班次 | Redis SET 原子，不会重复，OK |

---

## 第 5 轮：Redis 与 DB 一致性

| 检查项 | 结论 |
|---|---|
| Redis 全清后怎么恢复 | **缺能力，P1**。现在只有"对账"（把 Redis 状态修到 DB），没有"重建"（从 DB 回填 Redis）。加日期后是 420 个 Hash，手工预热不现实。需要新增一个按日期区间重建的入口 |
| 预热失败用户看到什么 | 扣减返回 -2，提示"库存未预热"。这是**能让用户看见的故障**，P1。要有自动重试或告警 |
| 对账任务会不会误报 | 会。任务刚生成库存、预热还没完成时，对账会报"DB 有 Redis 无"。**P1**：对账要跳过"生成时间在 N 分钟内"的实例，或按"预热完成标记"过滤 |

---

## 第 6 轮：订单生命周期

| 检查项 | 结论 |
|---|---|
| 超时订单回补到已清理的实例 | **缺陷，P0 级**。23:50 下单、00:10 超时取消，如果 00:00 已把该实例库存删了，回补会写出一个孤儿 key，或直接抛异常 |
| 退票回补同样问题 | 同上 |
| 停运实例上的存量订单 | 文档写了"人工处理"，但没给入口。至少要有"按实例查订单"的管理接口，否则无法操作 |

**这一轮的结论：过期实例不能立刻物理删除，必须保留一段时间（建议 T+2 天），或者清理前检查是否还有活跃订单。**

---

## 第 7 轮：窗口与日期边界

| 检查项 | 结论 |
|---|---|
| 第 7 天边界 | 能查到 D+6，查不到 D+7。前端文案要说"仅可预订 7 天内"，不能说"无票" |
| 0 点瞬间下单 | 跨日时实例可能恰好被清理，和第六轮同一个问题 |
| 时区 | 服务器是 Asia/Shanghai，`LocalDate.now()` 直接可用，不需要 MCP |
| 跨月跨年 | `plusDays` 自动处理，无问题 |

---

## 第 8 轮：查询与展示

| 检查项 | 结论 |
|---|---|
| 查 7 天余票要调几次 Redis | 7 天 × 3 座位 = 21 次 `HGETALL`，**P2**，要上 pipeline 或批量接口 |
| 前端日期条数据从哪来 | 需要新接口：按班次 + 日期区间返回每天的最低余票/最低价 |
| AI 的"明天"怎么落到实例 | 工具层要把日期换成实例编号，模型不参与换算 |

---

## 第 9 轮：多实例与集群

| 检查项 | 结论 |
|---|---|
| 故障域 | 从"整个班次"缩小到"某一天"，是**改善**。某个节点挂了只影响那一天 |
| 一次请求的跨节点次数 | 增加。查 7 天要访问 7 个不同节点，延迟比现在高 |
| 预热能否用单个 Lua 完成 | 不能，跨多个槽。只能逐个 HSET，或者按节点分批 |
| 会话 key 与库存 key 不同节点 | 正常，一次请求两次往返，可接受 |

---

## 第 10 轮：可观测性与恢复

| 检查项 | 结论 |
|---|---|
| 怎么知道窗口是完整的 | **缺监控，P1**。要有指标：窗口内有效实例数 / 期望天数，不等于 7 就告警 |
| 任务失败怎么补 | 要有手动补齐接口，按日期区间 |
| 日志能否追溯实例生命周期 | 需要：创建时间、预热时间、是否可售、停运原因 |

---

## 结论

### 三个必须先修的致命问题（P0）

| 编号 | 问题 | 修法 |
|---|---|---|
| **P0-1** | 现有预热是覆盖式的，用于已售实例会直接超卖 | 新任务只对新生成的实例预热，绝不调用现有 preheat 处理已售日期 |
| **P0-2** | 现有预热按"区段号"分组，多日期数据会互相覆盖 | 预热改造为按实例编号查询、按实例预热，`selectByTrainNo` 换成 `selectByInstanceNo` |
| **P0-3** | 过期实例立刻删库存，导致超时/退款回补失败 | 过期保留 T+2 天再物理删；或清理前检查该实例是否还有未完成订单 |

这三个都在现有代码里能精确定位，不是我推演出来的假设。

### 四个应当修（P1）

| 编号 | 问题 | 修法 |
|---|---|---|
| P1-1 | 旧唯一索引阻止 7 天数据插入 | 先删旧索引再建新索引，写进迁移脚本 |
| P1-2 | 任务只加一天，停机后窗口残缺 | 改成"幂等补齐窗口完整性"，每分钟检查一次 |
| P1-3 | 锁 TTL 55 秒小于任务耗时 | 窗口任务用独立锁，TTL 120 秒；或加心跳续期 |
| P1-4 | 缺"从 DB 重建 Redis"的能力 | 新增按日期区间重建的入口，复用容量 - 已售的计算 |

### 另外三个 P2

- 查 7 天余票的 N+1（上 pipeline）
- 对账任务要排除"刚生成未预热"的实例
- "未开售"与"售罄"的文案要区分

---

## 修正后的最终设计（与初版的差异）

| 点 | 初版 | 修正后 |
|---|---|---|
| 预热 | 复用现有 preheat | **新写按实例预热的逻辑**，只对新实例调用；现有 preheat 保留但加"禁止对已售实例调用"的注释和保护 |
| 任务触发 | 每天 0 点一次 | **每分钟检查窗口完整性，幂等补齐**，避开失败即断档 |
| 过期清理 | 立刻删 | **延迟 2 天**删，或检查活跃订单 |
| 任务锁 | 复用三个任务锁 | **独立一把窗口锁，TTL 120 秒** |
| 会话 | 不变 | 不变 |
