# Redis 单实例切集群：改造与验证

日期：2026-11-15
定位：排期第 4 项。这是整个项目里**唯一一处"只讲过、没做过"**的能力——简历上写"支持 Redis Cluster"，但从来没真的起过集群，也不知道切过去会不会崩。

---

## 一、为什么必须做

Redis Cluster 相关的话术有个致命弱点：**没验证过的能力，一被追问就露馅**。

面试官只要问两个问题：

1. "你切集群之后，Lua 脚本还能跑吗？" —— 集群下脚本里的所有 key 必须同槽，否则直接 `CROSSSLOT`
2. "你怎么证明切过去没坏？" —— 需要真的把单实例换掉、把旧实例关掉，业务还能跑

这两件本项都做了，而且是**关掉旧实例**做的——这是排除"其实还连着老 Redis"的唯一办法。

---

## 二、集群怎么搭的

虚拟机（`192.168.175.100`，CentOS 7，**只有 1 核 CPU**）上原有单实例跑在 `redis1` 容器里。新建 6 个容器：

```
端口 7000~7005，--network host，3 主 3 从
redis-server --port 700x --cluster-enabled yes --cluster-node-timeout 5000 --appendonly no --save ""
```

两个关键选择：

| 选择 | 原因 |
|---|---|
| `--network host` 而不是端口映射 | 容器端口映射时，集群 gossip 会把容器内地址（`172.17.x.x:6379`）通告出去，宿主机外的客户端拿这个地址连不上。host 网络下节点地址就是宿主地址，省掉 `--cluster-announce-ip/port` 一堆参数 |
| `--save ""` 关闭 RDB | 1 核机器，6 个节点同时 fork 持久化会卡；本项目 Redis 是缓存，DB 才是准的，丢了重建即可 |

组集群：

```bash
redis-cli --cluster create 192.168.175.100:7000 ... 192.168.175.100:7005 --cluster-replicas 1
```

结果：`cluster_state:ok`、`cluster_known_nodes:6`、`cluster_size:3`、16384 槽全覆盖。

## 三、最关键的一步：hash tag 验证

这是整项的核心。`deduct.lua` 一次操作三个 key：

```
stock:{G1001}:SECOND_CLASS
deducted:{G1001}:SECOND_CLASS
passenger:dedup:{G1001}:1001
```

集群按 key 的 CRC16 哈希分槽，一个 Lua 脚本里的所有 key 必须落在**同一个槽**，否则报 `CROSSSLOT`。

**花括号 `{G1001}` 就是 hash tag**：Redis 只对花括号内的内容算哈希，所以三个 key 必然同槽。

实测（`CLUSTER KEYSLOT`）：

| key 写法 | 落槽 | 结果 |
|---|---|---|
| `stock:{G1001}:SECOND_CLASS` | 2723 | |
| `deducted:{G1001}:SECOND_CLASS` | 2723 | 三者同槽 ✅ |
| `passenger:dedup:{G1001}:1001` | 2723 | |
| `stock:G1001:SECOND_CLASS` | 1673 | |
| `deducted:G1001:SECOND_CLASS` | 9138 | 分散三槽 ❌ |
| `passenger:dedup:G1001:1001` | 2654 | |

直接执行脚本做对照：

```
# 不带 tag
EVAL "return 1" 3 stock:G1001:SECOND_CLASS deducted:G1001:SECOND_CLASS passenger:dedup:G1001:1001
→ CROSSSLOT Keys in request don't hash to the same slot

# 带 tag
EVAL "return 1" 3 stock:{G1001}:SECOND_CLASS deducted:{G1001}:SECOND_CLASS passenger:dedup:{G1001}:1001
→ 1
```

**这一条就是"设计时就留了后路"的证据**：当初写 key 时加花括号，不是为了好看，是为了集群下 Lua 能跑。

### 代价：同一车次变成单节点热点

hash tag 换来了原子性，代价是**同一车次的所有 key 只能落在一个节点**。实测的数据分布：

| 节点 | 角色 | key 数 | 内容 |
|---|---|---|---|
| 7000 | master | 13 | 全部 G1001 业务 key（stock/deducted/dedup）、三个锁、snowflake |
| 7001 | master | 4 | auth token、`rate:{1}:G1001` |
| 7002 | master | 1 | MQ 去重 key |

也就是说：**G1001 这一个车次的全部抢票压力，只压在一个节点上**。分片只在"不同车次之间"生效，同一车次内部没有分片能力。

要突破这个限制，只能把单车次的库存拆成多个槽（比如按区段拆成 `{G1001:S1}`、`{G1001:S2}`），但那样一次下单涉及多个区段就成了跨槽，Lua 原子性直接没了。**这是"原子性"和"单热点"的取舍，本项目选原子性。**

## 四、配置改动

`application.yml` 的 Redis 段：

```yaml
spring:
  data:
    redis:
      cluster:
        nodes:
          - 192.168.175.100:7000
          - ...（到 7005）
        max-redirects: 3
      timeout: 5000ms
```

单实例的 `host/port/database` 注释保留备查。项目没有自定义 `RedisConnectionFactory`，走 Spring Boot 自动配置，改配置即可，代码零改动。

## 五、验证结果

### 5.1 基础连通（6 项全过，**在关掉 6379 旧实例的前提下**）

| 断言 | 结果 |
|---|---|
| `health` 可访问 | 200 |
| `health` 里 redis 组件 | UP |
| 登录（token 写入集群） | 成功 |
| `preheat` 往集群写库存 | 写入 6 个 key |
| 3 笔下单（执行 `deduct.lua`） | 3/3 成功 |
| 库存按订单数扣减 | 100 → 97，扣 3 张 |

**6379 全程是关闭状态**，业务照常——这是"流量确实走集群"的硬证据。

### 5.2 故障转移（停掉持有该车次数据的主节点）

停掉 7000（G1001 的全部 key 都在它上面）：

```
12 秒后：
  7001 master
  7002 master
  7003 master   ← 原 slave，接管 0-5460 槽
  7004 slave  master_port:7001
  7005 slave  master_port:7002
cluster_state:ok   cluster_slots_fail:0
```

7003 的 `CLUSTER NODES` 显示 `myself,master ... connected 0-5460` —— 槽位完整接管。

**应用层验证**：故障转移期间重新登录下单，成功，库存 97 → 96。

恢复 7000 后，它**自动变成 7003 的从节点**（不抢回主），数据从 7003 全量同步（两边 DBSIZE 都是 14）。

### 5.3 并发抢票（100 个独立账号抢 50 张）

单用户限流是令牌桶（容量 3、每秒补 1），同一个 token 发 100 个请求只会放过 3 个，压不到库存。所以新建了 100 个压测账号（`sql/06_load_test_users.sql`，用户 3001~3100、乘客 5001~5100，密码同 admin），每人发 1 次请求。

结果：

| 断言 | 结果 |
|---|---|
| 抢到票笔数 = 票数 | **50 笔**，票数 50 |
| 未抢到 | 50 笔，全部是"余票不足，抢票失败" |
| 库存扣到 0 | 0 |
| 库存没有变负 | 0 |
| Redis 库存 | 段 1 = 0，段 2 = 0 |
| `deducted` 集合 | 50 个成员 |

耗时 0.58s，QPS≈171（虚拟机只有 1 核，瓶颈在它）。

**这条证明了：切集群没有破坏原子性。**

## 六、过程中踩到和修掉的

### 6.1 `reset_redis.py` 直接失效（已修）

脚本硬编码连 6379，单实例一关就跑不了。改成集群版：

1. `CLUSTER NODES` 解析出所有在线主节点（因为任意节点只持有部分槽，必须逐个 `SCAN`）
2. 处理 `MOVED` 重定向（DEL 发到不持有该槽的节点会返回 `MOVED 2723 host:port`，要跟着跳）

修完实测：自动发现 3 个主节点，清理 54 个 key。

### 6.2 业务失败也是 HTTP 200 + code 200（我自己踩的坑）

第一次压测的脚本用 `code == 200` 判成功，结果报"100 笔成功、库存 0，超卖了 50 张"——**惊吓一场**。

真实情况：本项目所有业务失败都是 `HTTP 200` + 正常包装，失败信息在 `data.status`（"已取消"）和 `data.message`（"余票不足，抢票失败"）。查数据库只有 50 条"已确认"。

**教训**：压测脚本必须以 `data.status` 判成功，不能看 HTTP 状态码或 `code`。这也印证了第 2 项加 `traffic.order.fail` 指标的必要性——HTTP 层根本分不出成败。

### 6.3 故障转移期间对账任务抛 ERROR（可接受，未修）

停 7000 的瞬间，`DeductReconcileTask` 抢锁 `setIfAbsent` 超时：

```
QueryTimeoutException: Redis command timed out
  at ...ValueOperations.setIfAbsent
  at DeductReconcileTask.reconcile(DeductReconcileTask.java:75)
```

原因就是那条节点正好被停，连接被拒。**任务方法整体抛异常，没有兜底捕获**（外层 try 只包了业务循环，抢锁在 try 之外）。

影响：下个整分钟会重新抢锁重试，业务无损，但日志是 ERROR 级。要不要包一层 try 由你定——包了更干净，不包也能自愈。

### 6.4 观察到一次 1 张的库存偏差（未复现、未归因）

第一次压测后，出现过 `DB 段1=0 / Redis 段1=1` 的不一致（段 2 两边都是 0，`deducted` 仍是 50 个成员）。

- 理论排除：`deduct.lua` 内两次 `HINCRBY` 在同一脚本里原子执行，不可能只扣一段；回补走的是 `rollback` Lua，也是原子的
- 实测排除：重置后立刻查 Redis，起点是干净的 50/50；第二次压测前后完全一致（0/0、50 个成员）
- 发生时点：紧接在故障转移实验之后，期间对账任务因为节点被停抛过超时异常

**结论：只观察到一次，未能归因，也未能复现。** 不能拿它当"已知缺陷"，也不能假装没发生。如果后续再出现，排查方向是"故障转移期间某个回补只走了一半"。

### 6.5 无目标断言里少了一项

故障转移后没有验证"数据在切换中是否丢"——`downstream:done` 这类 MQ 去重 key 如果丢了，可能导致下游重复消费。本轮没造这个场景。

## 七、诚实的边界

1. **单机 1 核，性能数字没有参考价值。** QPS≈171 是虚拟机 CPU 限制的结果，不代表集群能力。
2. **没有做真实的"节点间网络分区"。** 只做了 `docker stop`，是进程消失，不是网络断续。
3. **没有压 cluster failover 期间的业务损失。** 只验证了"切换完成后业务恢复"，没测"切换那 10 秒里有多少请求失败"。
4. **hash tag 造成单车次单热点，没有做拆分。** 见第三节的取舍说明，这是有意的设计选择，不是遗漏。
5. **没有接 Prometheus 看节点级指标。** 集群各节点的内存/命中率/槽迁移都没有监控。

## 八、面试话术（一版）

> Redis 这块最初是单实例，简历上写"支持集群"其实没验证过。后来我真的在虚拟机上起了 6 个节点、3 主 3 从，然后把应用切过去，**把原来的单实例关掉**——这是唯一能证明流量真走集群的办法。
>
> 切换前最担心的是 Lua 脚本。集群下脚本里的所有 key 必须落同一个哈希槽，否则直接报 CROSSSLOT。我在设计 key 的时候就用花括号做了 hash tag，`stock:{G1001}:xxx`、`deducted:{G1001}:xxx`，实测三个 key 都落在 2723 槽；把花括号去掉，同样的脚本立刻报错。这一步是设计时就留的后路。
>
> 然后做了故障转移：把持有这个车次全部数据的主节点直接停掉，从节点 12 秒内接管槽位，应用这边重新下单是成功的。节点恢复回来会自动变成从节点，不会抢回主。
>
> 最后用 100 个独立账号并发抢 50 张票——为什么不用一个账号？因为单用户限流是令牌桶，一个 token 发 100 个请求只会放过 3 个，根本压不到库存。结果是正好 50 笔抢到、50 笔余票不足，库存扣到 0，没有超卖。
>
> 这里也有个代价要讲：hash tag 保证了原子性，但同一个车次的所有 key 只能落在一个节点上，等于单车次是单热点。分片只在车次之间生效，车次内部没有分片能力。这是原子性和热点之间的取舍，我选了原子性。
