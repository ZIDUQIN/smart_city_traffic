# 方言语音购票 · 对话化改造设计（v3.0）

> 本文只讲设计，不含代码。落地前需要你确认两件事：DeepSeek 的 API Key、以及第 14 节的落地顺序。

---

## 一、这次要解决什么

现有语音查票能跑通，但有四个硬伤：

1. **推荐是强制的**。查到车次后前端只给一个"是"，用户点了就直接进选座，等于系统替他决定了坐哪趟。
2. **站名判断只靠字面相似度**。语音转文字一旦出现同音错字（"咸阳"→"咸杨"），字面分很低，系统要么排错序，要么让用户在一堆不像的站里点。
3. **查不到时只有一句话**。"没有查到车"分不清是这条线压根没有、还是今天卖完了。
4. **语音只负责查票**。查完之后用户还得自己在屏幕上选车次、选座、选乘车人、下单，语音帮不上忙。

这次要做的是：**把语音从"查票工具"变成"能带着走完全程的售票员"**。

---

## 二、红线：模型能做什么，不能做什么

这是整份设计的地基，先钉死。

### 2.1 模型可以做

| 能做 | 怎么做 |
|---|---|
| 在**候选名单内**选站名 | 系统先给出候选，模型选一个或回答"都不是" |
| 判断"该不该继续追问" | 输出一个追问话术或 null |
| 把已确定的事实组织成人话 | 事实由系统给定，模型只负责措辞 |

### 2.2 模型绝对不能做

| 不能做 | 为什么 |
|---|---|
| 生成候选名单里没有的站名 | 一编就是"咸阳秦都站"这种不存在的名字，用户拿到去错地方的票 |
| 判断"有没有票""多少钱""还剩几张" | 这些是数据库确定答案，模型说的和库里不一致就是事故 |
| 补全用户没说的出发地 | 模型猜一个"上次用过的站"，猜错就是错票 |
| 直接下单 | 写操作必须由用户点按钮触发 |
| 记住对话内容 | 会话状态放前端，服务器不存 |

**一句话原则：模型只做选择题和措辞，不做事实判断和写操作。**

---

## 三、一句话流程

```
说话 → 认出站 → 列出全部车次 → 问几点走 → 推荐一趟（置顶高亮）
     → 用户选中 → 选座 → 问乘车人 → 确认卡片 → 用户点确认下单
     → 跳收银台 → 用户自己付钱
```

跟现在的差别有三处：

- 查完车次**先全部展示**，不直接进选座；
- 推荐只影响"哪一行排在最上面、放大一点"，不影响"其他行看不见"；
- 后面的选座、选人、下单**全在对话窗口里完成**。

## 四、对话状态机

### 4.1 状态定义

状态由**前端持有**，每次请求原样带回，服务器不存。

| 状态 | 含义 | 界面在等什么 |
|---|---|---|
| `IDLE` | 刚打开 | 等用户开口说去哪儿 |
| `NEED_FROM` | 缺出发站 | 等说"从哪儿走" |
| `NEED_TO` | 缺到达站 | 等说"到哪儿" |
| `PICK_STATION` | 站名有歧义 | 等点候选 / 说站名 |
| `SHOW_TRAINS` | 已出全部车次 | 等说时间，或直接点某趟 |
| `PICK_SEAT` | 已选车次 | 等说席别 / 点席别 |
| `ASK_PASSENGER` | 已选席别 | 等说乘车人姓名 |
| `CONFIRM_ORDER` | 信息齐了 | 等点"确认下单" |
| `PAY` | 订单已生成 | 用户在收银台自己付 |
| `DONE` | 出票完成 | 可再来一单 |

### 4.2 转移表

| 当前状态 | 用户动作 | 下一状态 | 系统动作 |
|---|---|---|---|
| `IDLE` | 说"从A到B" | 站点清晰 → `SHOW_TRAINS`<br>站点有歧义 → `PICK_STATION` | 解析、查票、展示 |
| `IDLE` | 只说"我明天想去西安" | `NEED_FROM` | 追问出发地，默认填上次用过的站**但要说出来让用户听见** |
| `NEED_FROM` | 说"从宝鸡走" | `SHOW_TRAINS` / `PICK_STATION` | 同上 |
| `NEED_TO` | 说"到咸阳" | `PICK_STATION` | 列该城市全部站 |
| `PICK_STATION` | 点/说某个站 | `SHOW_TRAINS` | 补全后查票 |
| `PICK_STATION` | 说"都不是" | `NEED_FROM` / `NEED_TO` | 请重说 |
| `SHOW_TRAINS` | 说"七点来钟" | `SHOW_TRAINS` | 出推荐，置顶高亮，其余仍在 |
| `SHOW_TRAINS` | 点某趟车 | `PICK_SEAT` | 高亮该趟 |
| `SHOW_TRAINS` | 说"就第一趟" | `PICK_SEAT` | 按序号选中 |
| `PICK_SEAT` | 说"二等座"/点席别 | `ASK_PASSENGER` | 记下席别 |
| `ASK_PASSENGER` | 说姓名 | 唯一命中 → `CONFIRM_ORDER`<br>多命中 → `ASK_PASSENGER` 列候选 | 匹配乘车人 |
| `ASK_PASSENGER` | 说"我要重新选" | `PICK_SEAT` | 回退 |
| `CONFIRM_ORDER` | 点"确认下单" | `PAY` | **前端直接调下单接口**，不经模型 |
| `CONFIRM_ORDER` | 点"不要了" | `IDLE` | 清空 |
| `PAY` | 付完款 | `DONE` | 播报"票买好了" |

**凡是涉及"退回去改"（改车次、改席别、改人）都要留一条路**，老人在确认页发现不对必须能退，不能只能取消重来。

## 五、后端接口

### 5.1 复用现有接口

`POST /api/voice/interpret` 仍然用，请求和响应都要加字段。

**请求新增**

| 字段 | 类型 | 说明 |
|---|---|---|
| `stage` | String | 前端当前状态，服务器据此决定这轮该干什么 |
| `selectedTrainNo` | String | 已选中的车次号（`PICK_SEAT` 用） |
| `selectedSeatNo` | String | 已选中的席别（`ASK_PASSENGER` 用） |
| `travelDate` | String | 客户端算好的日期，避免服务端猜"明天"是哪天 |
| `dateOffset` | Integer | 0=今天 1=明天…，`travelDate` 缺省时用它 |

**响应新增**

| 字段 | 类型 | 说明 |
|---|---|---|
| `stage` | String | 服务器建议的下一状态 |
| `askText` | String | 需要追问时说的话（可能是模型润色过的，但事实来自系统） |
| `emptyReason` | String | 扩展为 `NO_ROUTE` / `SOLD_OUT` / `STATION_UNCONFIRMED` / `DATE_OUT_OF_WINDOW` |
| `soldOutTrainCount` | Integer | 卖完的车次数，用于"今天 N 趟都卖完了" |
| `canAskTomorrow` | Boolean | 今天没票时是否该问"看明天吗" |
| `modelUsed` | Boolean | 这轮是否调了模型（排查问题用） |
| `modelFallback` | Boolean | 调了但失败，已降级为规则 |

`emptyReason` 原来是 `NO_TRAIN`，现在拆成两个：**`NO_ROUTE`（没这条线）**、**`SOLD_OUT`（有线路但今天没票）**。前端要能分开播报。

### 5.2 乘车人

复用 `GET /api/passengers`，返回当前账号下全部乘车人。

**姓名匹配在前端做，不把列表发给模型**：一是隐私，二是名单没必要离开这台机器。

### 5.3 下单与支付

- 下单：`POST /api/orders`（前端在用户点"确认下单"后直接调）
- 支付：`POST /api/payments/prepay` → 收银台 → `POST /api/payments/mock/confirm`

**全程模型不碰**。

## 六、"拿不准"怎么判定

这是"什么时候该叫模型"的开关。叫得太勤，慢且费钱；叫得太少，错字救不回来。

### 6.1 判定在哪儿做

在 `StationCorrector.correct()` 里，对**每个方向**单独判定，最后取并集。

### 6.2 明确 → 不叫模型

满足任一条即视为明确：

| 条件 | 例子 |
|---|---|
| 第一名 ≥ 0.94 且第二名 ≤ 0.80（分差大） | 用户说"西安北"，精确命中 1.0，第二 0.67 |
| 唯一通车且该组两侧最低分 ≥ 0.85 | 用户说"宝鸡/咸阳"，唯一通车组是 0.94 / 0.88 |

### 6.3 拿不准 → 叫模型

满足任一条：

| 条件 | 例子 |
|---|---|
| 前两名分差 < 0.10 | "咸阳北 0.94 / 咸阳西 0.94" 并列 |
| 候选里没有任何一个 ≥ 0.85 | 全是 0.6~0.8 的模糊命中 |
| 候选数 ≥ 3 且都存在竞争 | "咸阳"的三个站、加拼音噪音 |

### 6.4 叫了也用不上

模型返回的站名**必须能在该方向的候选名单里原样找到**。找不到就当它没说，回退到规则结果。这条是防幻觉的最后一道闸。

### 6.5 开关

`voice.llm.enabled`（默认 true）。线上出问题可以一键关掉，退回纯规则，不影响查票。

## 七、模型调用设计

### 7.1 用哪个

SpringAI 已配好 DeepSeek（OpenAI 兼容协议）：

```
spring.ai.model.chat = openai
spring.ai.openai.base-url = https://api.deepseek.com/v1
spring.ai.openai.chat.model = deepseek-chat
spring.ai.openai.api-key = ${DEEPSEEK_API_KEY}
```

**前置条件：必须先在 `application-local.yml` 或环境变量里配 `DEEPSEEK_API_KEY`，否则一直是占位符，调用会 401。**

### 7.2 一次调用只做一件事

| 场景 | 触发 | 输入 | 输出 |
|---|---|---|---|
| 站名定夺 | 第 6.3 节条件 | 用户原话 + 两侧候选（含分数） | `{from, to, ask, why}` |

**只做这一个场景。** 意图解析、话术润色都不调模型——规则能做的就别花钱。

### 7.3 提示词

**System**

```
你是火车站售票窗口的老售票员，替一位可能不识字、只会说方言的老人办事。

铁律：
1. 你只能从"候选"里选站名。绝对不能自己编站名，也不能改编写。
2. 候选里没有用户真正想去的地方，就填 null，并在 ask 里说一句追问的话。
3. 不要判断有没有票、多少钱，那不是你的事。
4. ask 要用老人听得懂的话，一句话，不超过 25 个字，不要书面语。
5. 只输出 JSON，不要任何解释性文字。

输出格式：
{"from": "候选里的站名或 null", "to": "候选里的站名或 null", "ask": "追问的话或 null", "why": "一句话理由"}
```

**User（模板）**

```
用户原话：{text}

出发侧候选（按相似度排）：
- 宝鸡南（0.94）
- 灵宝西（0.73）

到达侧候选（按相似度排）：
- 咸阳秦都（0.88）
- 咸阳北（0.94）
- 咸阳西（0.94）

已知：这一趟从宝鸡南出发能到咸阳秦都，到咸阳北和咸阳西都没有直达车。
```

最后那句"已知"很关键：**把反查结果告诉模型**，它就能判断"用户说咸阳，虽然咸阳北分更高，但只有咸阳秦都能到，应该选咸阳秦都还是该追问"。

### 7.4 超时与失败

| 情况 | 处理 |
|---|---|
| 超时（默认 3 秒） | 放弃，用规则结果，`modelFallback=true` |
| 返回不是合法 JSON | 同上 |
| 返回的站名不在候选里 | 该方向丢弃模型结果，用规则 |
| 401 / 额度用尽 | 同上，并打 warn 日志 |

**降级后必须仍能给用户一个合理答复**——规则本来就有一条完整路径，模型只是加分项。

### 7.5 成本

一次调用约 300~500 token，DeepSeek 单价极低。按"只有拿不准才调"估算，正常用户十次说话里大概调两三次。

## 八、三种"没票"怎么分

### 8.1 判断依据

`TicketService.search()` 是按**线路**查车次的：某天有没有票只影响余票数字，不影响车次是否出现。所以三种情况能干净分开：

| 情况 | 判据 | `emptyReason` |
|---|---|---|
| 没这条线 | 车次列表为空 | `NO_ROUTE` |
| 有线路，今天全卖完 | 车次非空但每趟每席别余票都是 0 | `SOLD_OUT` |
| 有车有票 | 车次非空且至少一个席别有余票 | null |

### 8.2 播报

- `NO_ROUTE`：「没有找到从宝鸡南到上海虹桥的班次。您是不是站名说得不一样？可以再说一遍。」
- `SOLD_OUT`：「今天从宝鸡南到咸阳北的 2 趟车都卖完了。要不要看看明天的？」

### 8.3 "看明天的"怎么执行

**先问，用户答"看"再查。** 不自动查——自动把明天的票混进今天的列表，老人会看花。

流程：

1. 今天 `SOLD_OUT` → 播报问句，`canAskTomorrow=true`
2. 用户说"看"/"看看明天的" → 前端把 `dateOffset` 改成 1 重新请求
3. 明天也没票 → 「明天也卖完了」+ 继续问后天（最多连问到第 7 天，窗口外就停）
4. 明天有票 → 正常展示

**最多往后问 7 天**，与预售窗口一致。不能无限问下去。

## 九、乘车人怎么选

### 9.1 流程

1. 系统问：「用哪位乘车人的名字买？」
2. 用户说「张三」
3. 前端拿 `GET /api/passengers` 的结果做匹配：

| 匹配结果 | 处理 |
|---|---|
| 命中 1 个 | 直接选中，进确认页 |
| 命中多个（张三 / 张三丰 / 张三维） | 列出这几个让他点，同时播报「有三位，您要哪一位？」 |
| 一个都没命中 | 「没找到这位乘车人。您可以在乘车人里添加，或者换个名字。」 |

### 9.2 为什么在前端匹配

- 乘车人名单是隐私，没必要发给模型
- 名字匹配是确定性字符串比对，不需要模型
- 老人在屏幕上看到"张三""张三丰"两个名字，点一下就行，比让模型猜更可靠

### 9.3 只说"用我的"

「用我的」→ 取当前登录用户自己的乘车人记录（如果存在），否则追问姓名。

## 十、下单与支付

### 10.1 确认卡片

信息齐了之后弹一张卡，必须写全：

```
11月19日 周四
宝鸡南 07:20 → 咸阳秦都 08:02
D2636  二等座
乘车人：张三
金额：30.00 元（成人全价，以付款页面为准）

[确认下单]   [再改改]
```

### 10.2 谁触发下单

**用户点「确认下单」按钮** → 前端调 `POST /api/orders`。

对话里说"确认""就这个"**不直接下单**，只是让系统把这张卡弹出来。这样模型永远没有写权限，也避免用户一句口误就买了票。

### 10.3 支付

订单生成后跳收银台，用户自己完成付款。付款成功才播报「票买好了」，并展示订单号。

**未支付不播报成功。**

## 十一、前端：语音面板改造成对话窗口

### 11.1 结构

```
┌─────────────────────────────┐
│  方言语音购票          [×]  │  ← 顶栏，可关
├─────────────────────────────┤
│  [助手] 您要去哪儿？         │  ← 消息流，向上滚动
│  [用户] 从宝鸡到咸阳         │
│  [助手] 找到 1 趟车，您想…   │
│   ┌───────────────────┐     │
│   │ ★ D2636 07:20     │     │  ← 推荐卡：置顶、放大、高亮边框
│   │   二等 ¥30 余50    │     │
│   └───────────────────┘     │
│   ┌───────────────────┐     │
│   │   D2637 18:26     │     │  ← 其余车次：正常大小，可点
│   │   二等 ¥30 余50    │     │
│   └───────────────────┘     │
├─────────────────────────────┤
│      [方言▼]   ( 🎤 )       │  ← 底部：方言选择 + 按住说话
└─────────────────────────────┘
```

### 11.2 消息流规则

- 语音识别出的文字 → 用户气泡（右侧）
- 系统播报的文字 → 助手气泡（左侧）
- 车次卡片、确认卡片、乘车人选择 → 嵌在助手气泡里
- **播报的同时把文字显示出来**，不光念一遍

### 11.3 关键交互改动

| 现在 | 改成 |
|---|---|
| 查完直接进选座 | 查完全部展示，等用户说时间或点 |
| 推荐行只能点"是" | 推荐行有"就买这趟"，其余行仍可点 |
| 车次列表 + 独立选座弹窗 | 全部塞进对话流，选中后展开席别按钮 |
| 没有乘车人选择 | 对话里问，命中多个列按钮 |
| 播报只念不说 | 文字 + 语音同步 |

### 11.4 保留的东西

- 方言下拉（`auto / sichuan / shaanxi / yue / northeast`）
- 按住说话的录音交互与计时
- 现有 `renderTrains` / `pickTrain` 的选择逻辑骨架，只改"是否强制"

## 十二、失败兜底

| 情况 | 用户看到什么 |
|---|---|
| ASR 没听清 | 「没听清，您再说一遍？」并保持当前状态 |
| 模型超时/失败 | 静默降级为规则，`modelFallback=true` 只进日志 |
| 模型返回的站名不在候选 | 当它没说，用规则结果 |
| 站点无法确定 | 列候选让点，配上「您说的是哪个站？」 |
| 没这条线 | 「没有找到…的班次」，**不给任何车次** |
| 今天全卖完 | 「今天 N 趟都卖完了，要不要看看明天的？」 |
| 明天也卖完 | 「明天也卖完了」，最多问到第 7 天 |
| 乘车人没匹配上 | 「没找到这位乘车人」+ 提示添加 |
| 下单失败（余票不足/并发冲突） | 「这趟票刚被人买走了，帮您重新查一下」，回退到 `SHOW_TRAINS` |
| 支付未完成 | 订单留在收银台，不播报成功 |
| 限流 | 「说得太快了，歇一下再说」 |

## 十三、验收用例

跑一遍这 14 条，全过才算完成。

| # | 输入 | 期望 |
|---|---|---|
| 1 | 从宝鸡到咸阳 | 出 1 趟 D2636，**置顶高亮**；列表里没有别的车次（这条线只有一趟） |
