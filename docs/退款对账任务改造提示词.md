## 一、背景与现状（已核实的代码事实）

**已实现**：

- `RefundServiceImpl.applyRefund`：校验 → 事务内（insert refund_record + CAS 订单已支付→退款中）→ 事务后（rollback.lua + restoreRealStock）→ 调渠道退款。
- `RefundServiceImpl.handleNotify`：验签 → 金额校验 → 幂等 → 事务内（casSuccess + 订单退款中→已退款）。
- `MockPayChannelServiceImpl.refund`：内存生成 `MOCKREFUND+雪花`，HMAC 签名，异步回调 `/api/pay/refund/notify`。

**已知缺口（本次要补）**：

1. 库存回补失败无补偿：`rollback.lua` / `restoreRealStock` 失败只发告警，订单卡在「退款中」。
2. 退款卡在「退款中」无补偿：回调丢失时，本地永远停在「退款中」。
3. `restoreRealStock` 不幂等（`remain + 1`），重复调用会多补库存 → 超卖。

**既有对账模式（必须沿用，保持一致）**：

`DeductReconcileTask`：

```java
@Scheduled(cron = "0 * * * * ?")           // 每分钟
String LOCK_KEY = "reconcile:lock";
redisTemplate.opsForValue().setIfAbsent(LOCK_KEY, "1", Duration.ofSeconds(55));  // 分布式锁
```

**事务传播事实**：

`StockServiceImpl.restoreRealStock` 标了 `@Transactional(rollbackFor = Exception.class)`，在外层 `TransactionTemplate` 内调用时加入外层事务（REQUIRED），因此「回补 DB 库存」和「置 stock_restored=1」可以放进同一个事务，做到原子。

## 二、模块目标

补上退款链路的最终一致闭环：

```
卡住的「退款中」订单
  ├─ 库存没回补   → 重试回补，成功置标记
  ├─ 渠道没受理   → 重发退款
  ├─ 渠道已成功   → 本地修复为已退款（回调丢失场景）
  ├─ 渠道处理中   → 不动，下轮再查
  └─ 渠道明确失败 → 置退款失败 + 告警人工
```

**不做**：退款金额核对（金额在申请时已固定）、通知用户（无推送渠道）、多实例压测。

```sql
    `reason`             VARCHAR(128)  DEFAULT NULL COMMENT '退票原因',
    `callback_count`     INT           NOT NULL DEFAULT 0 COMMENT '回调到达次数',

    UNIQUE KEY `uk_order_no` (`order_no`),
```

**`stock_restored` 是本次的核心改动**：没有它，对账无法判断 DB 库存是否补过，重试就会重复 `remain + 1` 造成超卖。

## 五、对账判定矩阵（核心，不得改动语义）

| 本地状态 | 判定条件 | 含义 | 动作 |
|---|---|---|---|
| `stock_restored = 0` | 库存没补 | 回补失败过 | 事务内：rollback.lua → restoreRealStock → 置 1 |
| `channel_refund_no` 为空 | 渠道没受理 | 调 refund 前就断了 | 过账龄闸门后重发 refund，拿到新单号立刻落库 |
| `channel_refund_no` 有值 + 查 `SUCCESS` | 回调丢了 | 钱已退，本地没更新 | 本地置「退款成功」+ 订单「已退款」 |
| `channel_refund_no` 有值 + 查 `PROCESSING` | 渠道在处理 | **正常态**，不是故障 | **只刷新 update_time**，等下一轮 |
| `channel_refund_no` 有值 + 查 `NOT_EXIST` | 渠道没这笔单 | 请求没到/渠道丢失 | 过账龄闸门后重发 refund，覆盖单号 |
| `channel_refund_no` 有值 + 查 `FAILED` | 渠道明确失败 | 钱退不出去 | 置「退款失败」+ 告警人工 |

**关键约束**：

1. `PROCESSING` 绝不能重发。重发不会让钱更快到账，只会在渠道侧多压一笔申请。
2. `SUCCESS` 绝不能重发，否则**重复退款**。
3. 只有 `NOT_EXIST` 或「没有渠道单号」才允许重发。
4. 判断依据是渠道查询结果，不是「等了多久」。超时只是筛出「值得查一下」的候选。
5. **两个重发入口都必须先过账龄闸门**：退款单创建超过 `max-age-hours`（默认 168 小时）时，"查不到 = 请求没到"这个假设不再成立（渠道流水可能已清理），一律转人工，不重发。见第十七节。

### 6.1 Mapper 新增方法

```java
/** 扫超时仍停在「退款中」的记录 */
List<RefundRecord> listStaleRefunding(@Param("timeoutSeconds") int timeoutSeconds,
                                      @Param("limit") int limit);

/** 置库存已回补（幂等，重复置 1 无副作用） */
```

SQL 要点：

```sql
<select id="listStaleRefunding" resultMap="refundResultMap">
    SELECT ... FROM refund_record
    WHERE status = '退款中'
      AND update_time &lt; NOW() - INTERVAL #{timeoutSeconds} SECOND
    ORDER BY update_time ASC
    LIMIT #{limit}
</select>

<update id="markStockRestored">
    UPDATE refund_record SET stock_restored = 1, update_time = NOW()
    WHERE refund_no = #{refundNo} AND stock_restored = 0
</update>

<update id="updateChannelRefundNo">
    UPDATE refund_record SET channel_refund_no = #{channelRefundNo}, update_time = NOW()
    WHERE refund_no = #{refundNo}
</update>

<update id="touchUpdateTime">
    UPDATE refund_record SET update_time = NOW() WHERE refund_no = #{refundNo}
</update>

<update id="incrRetryCount">
    UPDATE refund_record SET retry_count = retry_count + 1, update_time = NOW()
    WHERE refund_no = #{refundNo}
</update>
```

### 6.2 `applyRefund` 必须同步改的两处

**a. 库存回补改为事务内 + 置标记**（原先是两个独立 try）：

```java
// 事务提交后，此时订单已不是「已支付」，放座安全
try {
    transactionTemplate.execute(status -> {
        redisLuaService.rollback(trainNo, seatNo, passengerId, orderNo, segments);  // 幂等
        stockService.restoreRealStock(trainNo, seatNo, segments);                   // 加入同一事务
        refundRecordMapper.markStockRestored(refundNo);                             // 与回补原子
        return true;
    });
} catch (Exception e) {
    alarmService.send("退票库存回补失败，等待对账补偿 orderNo=" + orderNo, e);
}
```

**b. 落库渠道退款单号**：

```java
String channelRefundNo = channel.refund(record);   // 返回值不再丢弃
if (channelRefundNo != null) {
    refundRecordMapper.updateChannelRefundNo(refundNo, channelRefundNo);
}
```

**为什么必须落库**：对账靠 `channel_refund_no` 是否有值来区分「渠道没受理」和「渠道已受理」，不落库就会把已受理的单子当成没受理，反复重发 → 重复退款风险。

## 七、`reconcileOnce` 实现契约

```java
public int reconcileOnce() {
    List<RefundRecord> list = refundRecordMapper.listStaleRefunding(timeoutSeconds, batchSize);
    int handled = 0;
    for (RefundRecord r : list) {
        try {
            if (reconcileOne(r)) handled++;
        } catch (Exception e) {
            // 单条异常不中断整轮
            alarmService.send("退款对账单条异常 refundNo=" + r.getRefundNo(), e);
        }
    }
    return handled;
}

private boolean reconcileOne(RefundRecord r) {
    // ① 超过最大重试：只告警一次（到达阈值那轮），之后静默等待人工
    if (r.getRetryCount() != null && r.getRetryCount() >= maxRetry) {
        if (r.getRetryCount() == maxRetry) {
            alarmService.send("退款对账超过最大重试次数，需人工介入 refundNo=" + r.getRefundNo()
                    + " orderNo=" + r.getOrderNo() + " channelRefundNo=" + r.getChannelRefundNo());
        }
        refundRecordMapper.touchUpdateTime(r.getRefundNo());
        return false;
    }

    // ② 库存补偿（需要动作，计入重试次数）
    if (r.getStockRestored() == null || r.getStockRestored() == 0) {
        refundRecordMapper.incrRetryCount(r.getRefundNo());
        compensateStock(r);
    }

    // ③ 渠道没受理 → 重发（计入重试次数）
    if (r.getChannelRefundNo() == null || r.getChannelRefundNo().isEmpty()) {
        refundRecordMapper.incrRetryCount(r.getRefundNo());
        return resend(r);
    }

    // ④ 查询渠道，按矩阵处理
    RefundQueryResult result = channel.queryRefund(r.getChannelRefundNo());
    switch (result) {
        case SUCCESS:
            return settleSuccess(r);        // 复用回调落库逻辑
        case PROCESSING:
            // 正常态：不计入重试次数，只刷新时间等下一轮
            refundRecordMapper.touchUpdateTime(r.getRefundNo());
            return false;
        case NOT_EXIST:
            refundRecordMapper.incrRetryCount(r.getRefundNo());
            return resend(r);
        case FAILED:
            refundRecordMapper.casFailed(r.getRefundNo());
            alarmService.send("渠道退款失败，需人工 refundNo=" + r.getRefundNo());
            return true;
        default:
            return false;
    }
}
```

**`PROCESSING` 不计入 `retry_count` 的理由**：真实渠道退款要 3~7 个工作日，如果每轮都计数，5 分钟一轮、5 轮就在 25 分钟内把额度耗尽并告警，而钱其实正在正常清算。`retry_count` 的语义是「需要采取动作却一直失败」，不是「等了多久」。

### 7.1 `compensateStock(r)`

```java
private void compensateStock(RefundRecord r) {
    OrderRecord order = orderMapper.selectByOrderNo(r.getOrderNo());
    if (order == null) {
        alarmService.send("退款对账找不到订单 refundNo=" + r.getRefundNo());
        return;
    }
    // 防御：只有订单确实处在退票态才允许补库存，避免异常数据导致库存虚增
    if (!OrderRecord.STATUS_REFUNDING.equals(order.getStatus())
            && !OrderRecord.STATUS_REFUNDED.equals(order.getStatus())) {
        alarmService.send("退款对账订单状态异常，拒绝补库存 refundNo=" + r.getRefundNo()
                + " status=" + order.getStatus());
        return;
    }
    List<Integer> segments = segmentsOf(order);
    try {
        transactionTemplate.execute(status -> {
            // rollback.lua 幂等：已补过返回 0，不会重复 +1
            redisLuaService.rollback(order.getTrainNo(), order.getSeatNo(),
                    order.getPassengerId(), order.getOrderNo(), segments);
            // restoreRealStock 加入同一事务；markStockRestored 与它原子
            stockService.restoreRealStock(order.getTrainNo(), order.getSeatNo(), segments);
            refundRecordMapper.markStockRestored(r.getRefundNo());
            return true;
        });
    } catch (Exception e) {
        alarmService.send("退款对账库存补偿失败 refundNo=" + r.getRefundNo(), e);
    }
}
```

**风险说明（必须写进代码注释）**：若 `restoreRealStock` 曾经成功、但 `markStockRestored` 因进程崩溃没执行，本轮会再补一次 → 多补 1 张。窗口是「restore 成功到 mark 提交之间」，两者已放同一事务，正常情况下不可能分离。

### 7.2 `resend(r)`

```java
private boolean resend(RefundRecord r) {
    try {
        String newChannelRefundNo = channel.refund(r);
        if (newChannelRefundNo != null) {
            refundRecordMapper.updateChannelRefundNo(r.getRefundNo(), newChannelRefundNo);
        }
        return true;
    } catch (Exception e) {
        alarmService.send("退款重发失败 refundNo=" + r.getRefundNo(), e);
        return false;
    }
}
```

### 7.3 `settleSuccess(r)`（与 `handleNotify` 的 ⑥ 同构）

```java
private boolean settleSuccess(RefundRecord r) {
    Boolean ok = transactionTemplate.execute(status -> {
        int refundRows = refundRecordMapper.casSuccess(r.getRefundNo(), r.getChannelRefundNo());
        if (refundRows != 1) {
            status.setRollbackOnly();
            return false;
        }
        int orderRows = orderMapper.casUpdateStatus(r.getOrderNo(),
                OrderRecord.STATUS_REFUNDING, OrderRecord.STATUS_REFUNDED);
        if (orderRows != 1) {
            // 幂等分支：订单可能已经被别的路径修成「已退款」，此时只补退款流水即可
            OrderRecord latest = orderMapper.selectByOrderNo(r.getOrderNo());
            if (latest == null || !OrderRecord.STATUS_REFUNDED.equals(latest.getStatus())) {
                status.setRollbackOnly();
                return false;
            }
        }
        return true;
    });
    if (!Boolean.TRUE.equals(ok)) {
        alarmService.send("退款对账修复状态失败 refundNo=" + r.getRefundNo()
                + " orderNo=" + r.getOrderNo());
    }
    return Boolean.TRUE.equals(ok);
}
```

**这一段的幂等分支是必须的**：如果订单已经是「已退款」而退款流水还是「退款中」（比如分两次修、第二次被中断），`casUpdateStatus` 必然返回 0。若直接回滚，这条记录永远修不好，对账每轮都失败到告警。

**注意**：`settleSuccess` 不调用 `incrCallbackCount`（对账不是回调，不该污染该指标）。

## 八、定时任务

```java
@Component
public class RefundReconcileTask {

    /** 与 DeductReconcileTask 用不同的锁 key，互不阻塞 */
    private static final String LOCK_KEY = "refund:reconcile:lock";

    @Scheduled(cron = "0 * * * * ?")
    public void reconcile() {
        Boolean locked = redisTemplate.opsForValue()
                .setIfAbsent(LOCK_KEY, "1", Duration.ofSeconds(55));
        if (!Boolean.TRUE.equals(locked)) {
            return;
        }
        try {
            int handled = refundService.reconcileOnce();
            log.info("退款对账完成，处理 {} 条", handled);
        } catch (Exception e) {
            alarmService.send("退款对账任务异常", e);
        }
    }
}
```

## 十、禁止事项（7 条）

1. 禁止对 `PROCESSING` 或 `SUCCESS` 的结果调用 `refund()` 重发。
2. 禁止扫描 `order` 表做退款对账（拿不到 `channel_refund_no`，会把已受理的单子重复重发）。
3. 禁止把 `restoreRealStock` 与 `markStockRestored` 拆到不同事务。
4. 禁止把超过最大重试次数的记录强行改成「退款失败」（钱可能已退，只能告警待人工）。
5. 禁止改动 `DeductReconcileTask`、`rollback.lua`、`deduct.lua`。
6. 禁止在 `reconcileOnce` 里吞掉异常导致整轮中断（单条 try-catch，继续下一条）。
7. 禁止用 `create_time` 做超时判定（必须是 `update_time`，否则 PROCESSING 刷新后仍会被反复扫到）。

## 十一、自检清单（14 项）

1. `refund_record` 有 `stock_restored`、`retry_count` 两列，默认值 0
2. `MockPayChannelService.refund` 返回 String，`applyRefund` 已落库该单号
3. `queryRefund` 对空单号返回 `NOT_EXIST`
4. `applyRefund` 的库存回补在事务内执行，且 `markStockRestored` 与 `restoreRealStock` 同事务
5. 正常退票后 `stock_restored = 1`，对账不会重复补库存
6. 对账扫描条件为 `status='退款中' AND update_time < NOW() - timeout`
7. 每条处理前 `retry_count +1`；达到 `max-retry` 只告警不自动处理
8. `PROCESSING` 只刷新 `update_time`，不重发
9. `SUCCESS` 走 `settleSuccess`，本地置成功且订单转已退款
10. `NOT_EXIST` 走重发并覆盖 `channel_refund_no`
11. `FAILED` 置「退款失败」+ 告警
12. 任务与 `DeductReconcileTask` 使用不同锁 key，锁 TTL 55 秒
13. 单条异常不中断整轮
14. `PROCESSING` 分支不调用 `incrRetryCount`，只 `touchUpdateTime`
15. `compensateStock` 校验订单状态只能是「退款中」或「已退款」，否则告警且不补
16. `settleSuccess` 在订单已是「已退款」时能幂等通过，不会永远失败
17. Maven 编译 exit 0；`resources/lua` 仍 4 个文件

## 十三、已知边界（必须写进文档，不要假装解决）

1. **`restoreRealStock` 语义上仍不幂等**，靠 `stock_restored` 标记兜底；标记与回补已同事务，但极端崩溃场景（restore 提交后进程立即退出、mark 未提交）在本设计下不会发生（同事务），若未来拆事务则会重现风险。

4. **`channel_refund_no` 覆盖风险**：若同一退款单被重发多次，回调携带的是最早那次单号，`casSuccess` 会用回调值覆盖本地单号。Mock 场景不发生；真实渠道需以「重发返回的新单号」为准并做单号版本管理。

### 16.3 场景 F：max-retry 到阈值只告警一次

构造：另起一单 → 手工把 `retry_count` 置 5、`channel_refund_no` 填一个渠道查不到的号 → 等一轮 → 再回退 `update_time` 跑第二轮。

**这里查出一处真实缺陷**：

| | 修复前 | 修复后 |
|---|---|---|
| 第一轮（计数=5） | 告警 1 次，计数停在 5 | 告警 1 次，计数推进到 6 |
| 第二轮（5 分钟后） | 计数仍是 5 → `== maxRetry` 又成立 → **再告 1 次** | 计数是 6 → 不满足 `== 5` → 只刷新 `update_time` |

如果告警接的是短信或电话，这个缺陷的真实后果是值班的人每隔 5 分钟被叫一次，且永远停不下来——比不告警更糟。

### 16.4 场景 G：渠道明确失败 FAILED

FAILED 与 NOT_EXIST 的区别是**请求到了渠道、渠道明确拒绝**（原支付单已关闭、账户异常、风控拦截、超额）。所以它不能重发——重发也是同样结果，只会白耗额度。

|---|---|---|
| 流水改为「退款失败」 | 退款失败 | CAS 成功（`WHERE status='退款中'`） |

### 16.5 补测没覆盖的部分（诚实说明）

1. **`retry_count` 从 0 真实递增到 5 的连续时序没有跑**。跑一遍要 5 轮 × 5 分钟 ≈ 25 分钟，所以是直接把计数置为 5 来验证阈值行为。差别在于：真实递增过程里每一轮的「重发 → 渠道查不到 → 再重发」链路没有连续观测，但单轮的重发逻辑已在场景 C 实测过。
2. **`FAILED` 分支的告警只验证了「发出来」，没验证「人工处理完之后怎么恢复」**——因为没有人工处理入口。流水进了终态「退款失败」之后就没人管了，这一点在 16.4 已说明。
3. **每 5 分钟的实际间隔是 `timeout-seconds=300` 决定的**，不是 cron 间隔。任务本身 `0 * * * * ?` 每分钟醒一次，靠 `update_time` 过滤让同一单 5 分钟内不被重复扫。

## 十七、重复退款防护补强（2026-11-15）

### 17.1 补这块的原因

补测 PROCESSING 分支时，顺着"NOT_EXIST 允许重发"这条规则往下推，发现一个真实缺口：

> 「渠道查不到这笔单」有三种可能：请求没发出去、渠道流水过期被清理、渠道系统异常。代码只看到"查不到"这一个事实，却按第一种处理——直接重发。

如果真相是第二种（钱早就退了，只是记录被清了），重发就是**真的再退一次钱**。

原来的防护全部在本地：状态校验、`uk_order_no`、状态 CAS、回调幂等、库存标记。这些只能保证"我们不轻易发起第二次"，**管不到渠道那边真的退了几次**。

### 17.2 两道新防线

**第一道：渠道幂等键（根治）**

真实渠道退款接口都要求带「商户退款单号」（支付宝 `out_request_no`、微信 `out_refund_no`），规矩是同一个号提交多次只退一次钱。`MockPayChannelServiceImpl` 原来每调一次就生成一个新渠道单号，等于每次都是新退款。

改法：加一张内存幂等表 `refundNo → channelRefundNo`。同一个 `refundNo` 再来，直接把首次的单号还回去，不再执行退款。

```java
String existing = refundIdempotent.get(refundNo);
if (existing != null) {
    return existing;   // 幂等命中，不重复退
}
String winner = refundIdempotent.putIfAbsent(refundNo, channelRefundNo);
if (winner != null) {
    return winner;     // 并发下别人先登记了，用它的单号
}
```

注意幂等键选的是 `refund_no`（我们自己的退款单号），不是 `order_no`。退款单号一笔退款对应一个、且从不变化，是最稳定的幂等标识。

**第二道：账龄闸门（限制重发窗口）**

就算有了幂等键，也要防渠道数据保留期带来的误判。加一条硬规则：退款单创建超过 `max-age-hours`（默认 168 小时 = 7 天）时，不管查到什么结果，都不许重发。

```java
private boolean allowResend(RefundRecord record) {
    long ageHours = Duration.between(record.getCreateTime(), LocalDateTime.now()).toHours();
    if (ageHours <= reconcileMaxAgeHours) return true;
    if (refundRecordMapper.flagManual(record.getRefundNo()) > 0) {
        alarmService.send("退款单账龄超限，禁止重发，需人工核对 ...");
    }
    return false;
}
```

两个重发入口（`channel_refund_no` 为空、查 `NOT_EXIST`）都要先过它。

阈值为什么是 7 天而不是渠道保留期（3 个月）：退款正常几小时到几天就到账，超过 7 天还是「退款中」一定是异常，不是"慢"。阈值压得越短，暴露在重发风险里的窗口越小。

### 17.3 「只告警一次」为什么这次不需要水位线

上一节（16.3）为了只告警一次，被迫在告警那轮把 `retry_count` 从 5 推到 6。这次换了个更干净的做法——把 CAS 放进 SQL：

```sql
UPDATE refund_record
SET retry_count = 999, update_time = NOW()
WHERE refund_no = #{refundNo}
  AND retry_count < 999
```

只有第一次执行会影响 1 行，之后永远是 0 行。Java 侧 `if (影响行数 > 0) { 告警 }`，天然只成立一次，不需要额外的"是否已告警"字段。

`999` 是人工标记值，选它是为了在表里一眼和 5、6 区分开，没有别的含义。它同时干三件事：退出自动对账（`retry_count >= max-retry`）、不再告警（`!= max-retry`）、标记待人工处理。

### 17.4 实测结果（脚本 `jmeter/verify_refund_resend_guard.py`）

| 场景 | 构造 | 断言 | 结果 |
|---|---|---|---|
| **H 账龄闸门** | 退款单 `create_time` 设 10 天前，渠道单号填一个查不到的值 | 渠道单号未被替换（没重发） | `MOCKREFUND_OLD_STALE` 原样保留 |
| | | `retry_count` = 999 | 999 |
| | | 发出账龄超限告警 | `alarm.log` 1 次 |

| **I 渠道幂等** | 账龄内，渠道单号填查不到的值，触发重发 | 第一次重发生成新单号 N1 | `MOCKREFUND380464728712937472` |

### 17.5 仍未覆盖的部分

1. **幂等表是内存的**，应用重启就清空。真实渠道的幂等是渠道侧数据库保证的，跨重启有效。本项目是 Mock，这一点要写进诚实边界：重启后对账可能把"渠道查不到"误判为请求没到。
2. **跨重启的重复退款没有验证**。验证 I 场景必须在同一个应用进程内跑完两轮，重启就测不出来。
3. **账龄闸门只拦重发，不拦补库存**。补库存是本地操作，做多少次都不会多退钱；重发是往外发请求，才需要闸门。

### 17.6 一句话面试版

> 对账里唯一允许重发的分支是"渠道查不到这笔单"，但这个判断是假设不是事实——渠道流水过期也会查不到，那时候重发就是重复退款。我补了两道防线：一是渠道侧幂等键，用我们自己的退款单号做键，同一个号提交多次渠道只退一次；二是账龄闸门，超过 7 天的单子不管查到什么一律转人工。实测同一个退款单重发两次，渠道返回的是同一个单号，说明第二笔根本没产生。
