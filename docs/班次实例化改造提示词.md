## 二、五轮复检结论

每一项都是复检时发现并已修正的真实问题，不是走过场。

### 第 1 轮：SQL 执行顺序

- **发现**：若先加唯一索引再回填 `instance_no`，回填过程中多行 `instance_no` 为 NULL，NULL 不参与唯一约束，回填后可能瞬间产生重复键冲突。
- **修正**：严格按"删旧索引 → 加列 → 回填 → 改非空 → 加新索引"顺序，回填完成后再建索引。

### 第 2 轮：容量数据来源（这条最危险）

- **发现**：方案原写"容量 = 当前 remain"。如果迁移时库存已被卖出，容量会被灌成剩余数，**之后生成的所有新班次都是少票甚至零票**，而且不可见——要等到某天查票才发现。
- **修正**：容量从 `sql/05_b2_unified_stock.sql` 的**初始值**取（二等 50、一等 20、商务 5），不读实时 remain。当前虽然恰好是满票，但不允许依赖这个巧合。

### 第 3 轮：对旧代码的破坏性

- **发现**：如果批一就生成 7 天库存（42 行），旧代码 `preheat` 走 `selectByTrainNo` → 按 `segment_no` 分组 → 7 天数据互相覆盖，预热出来是错的。批一完成后旧接口直接坏掉。
- **修正**：**批一只回填现有 6 行的 `instance_no`，不新增任何库存行**。生成 7 天数据推迟到新代码上线后（批三）。这样批一完成后，旧代码读到的仍是 6 行，预热和下单都正常。

### 第 4 轮：回滚可行性

- **发现**：如果已生成 7 天数据再回滚，恢复旧唯一索引 `(train_no, seat_no, segment_no)` 会直接冲突——同一个 `train_no + segment_no` 有 7 行。
- **修正**：回滚脚本第一步是"只保留今天那一行，删除其余"，再恢复索引。并把这条写进回滚步骤，不能只写"删索引"。

### 第 5 轮：验证覆盖

- **发现**：原验证只看"表条数对不对"，但批一的风险在于"旧接口是否还能用"，条数对了不代表接口没坏。
- **修正**：验证必须包含**回归项**：批一完成后调一次老的下单接口和预热接口，确认仍能成功。这条不通过就立即回滚。

## 四、回滚步骤（按顺序）

1. 删掉新增的 7 天数据（如果批三已执行）：保留 `instance_no = 'G1001-20261116'` 的行
2. `ALTER TABLE stock DROP INDEX uk_instance_seat_segment`
3. 恢复旧唯一索引 `uk_train_seat_segment (train_no, seat_no, segment_no)`
4. 删列 `instance_no`、`train_no_v2`（可选，保留也无害）
5. 删三张新表
6. 恢复订单/流水：删新增两列（或保留，代码回滚后不用）

**注意**：第 1 步不能跳。已生成 7 天数据时直接恢复旧索引必然冲突。
