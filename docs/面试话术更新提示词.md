### 3.3 限流参数与实测

- 单用户桶：capacity 3、refill 1/s，key `rate:{userId}:{trainNo}`
- 全局桶：capacity 500、refill 500/s，key `rate:global:{trainNo}`
- 精确性验证：10 个请求同 token 并发，前 3 个 200、后 7 个 429「操作过于频繁」，精确 3 放 7 拒
- 拒绝语义区分：全局「当前抢票人数过多」、单用户「操作过于频繁」，均 429
- 执行顺序：全局限流在单用户限流之前
- fail-close：限流异常时拒绝而不是放行

### 3.4 支付模块

- 统一下单 → payToken → 模拟收银台确认 → 渠道 HMAC 签名异步回调 → 超时 900 秒关单
- 回调校验：验签 → 金额与订单/流水三方一致 → 幂等 → 事务内 CAS（流水待支付→支付成功、订单已确认→已支付、同订单其余待支付流水批量关闭）
- 金额不匹配：不确认、**不取消**、不应答 SUCCESS，挂起告警
- 边界补测 12 项全过（`jmeter/verify_payment_edge.py`）：多次 prepay 后旧凭证失效、金额篡改被拒且订单不动、超时关单 49 秒命中并精确回补库存

### 3.5 退票退款

- 顺序定论：**状态先切、库存后补**。订单状态是"是否占座"的唯一判据
- `applyRefund` 事务内只做 insert 流水 + CAS（已支付→退款中），事务提交后才回补 Redis/DB，最后调渠道
- 17 项验证全过：10 项主链路 + 7 项边界
- 并发同退一单：一个 200、一个 400「该订单已提交退票，请勿重复操作」，callback_count 1→3 但状态只变一次
- 关键数据：Redis 库存 100/100 → 下单 99/99 → 退票 100/100；DB 二等 100/100 复原

### 3.6 退款对账

- 扫 `refund_record` 而非 `order`（order 只是状态镜像，拿不到 channel_refund_no）
- 四类渠道结果四类动作：`stock_restored=0` 补库存、无渠道单号重发、查 SUCCESS 只修本地状态**绝不重发**、查 PROCESSING 只刷新时间不计数、查 NOT_EXIST 才允许重发、查 FAILED 置失败并告警
- 新增 `stock_restored` 幂等标记，且与 `restoreRealStock` 同事务（restore 是 remain+1 不幂等）
- 7 项断言全过：A 补库存+重发（retry_count 2）、B 回调丢失只修状态（retry_count 0）、C 渠道不存在重发（retry_count 1）、D 正常单不打扰

### 3.7 三个定时任务

| 任务 | 扫什么 | 职责 | 锁 key |
|---|---|---|---|
| `DeductReconcileTask` | `ticket_deduct_record` 中间态超 5 分钟 | 扣减一致性 | `reconcile:lock` |
| `PaymentTimeoutTask` | `order` 已确认超 900 秒 | 超时关单 + 回补 | `payment:timeout:lock` |
| `RefundReconcileTask` | `refund_record` 退款中超 300 秒 | 退款与回补一致性 | `refund:reconcile:lock` |

- 三者 cron 均为 `0 * * * * ?`，锁 TTL 55 秒
- **锁只靠 TTL 释放，不主动 delete**（2026-11-15 统一）：主动 delete 在"执行超过 55 秒"时会删掉别的实例刚拿到的锁，导致下轮两实例并发
- 依赖数据库 CAS 兜底：重叠执行也不会把库存补成 101

### 3.8 技术栈与运行环境

- Spring Boot 4.1.2、JDK 21、MyBatis（原生 XML）、MySQL 8、Redis、RocketMQ 事务消息
- 三级缓存：Caffeine（1 秒 TTL）→ Redis → DB
- 雪花 ID、密码 + Redis 不透明令牌认证
- Hikari 连接池 30、Tomcat 最大线程 400
- 端口 8081，单机部署

## 四、文档结构（必须按此顺序，共八节）

### 第一节：30 秒开场（保持现有内容，仅把"零超卖"数据换成补测后的准确表述）

### 第二节：项目全景（新增）

一张表或几句话讲清规模：模块清单、技术栈、数据规模（演示数据 1 条车次 3 站 2 区段、库存二等 100）、压测数据。

目的：让面试官知道这不是玩具，覆盖了下单、支付、退票、对账、限流五条链路。

### 第三节：六个核心难点（每节四件套：难点 → 我的解法 → 为什么这么解 → 数据佐证）

1. **不超卖**：Lua 原子扣减 + 唯一索引 + 状态机
2. **Redis 与 DB 最终一致**：MQ 事务消息 + 三个定时对账任务
3. **读流量不压垮数据库**：Caffeine 1 秒 → Redis → DB 三级缓存，响应带 source 字段
4. **流量整形**：两级令牌桶，以及"限流不参与正确性"这个认知
5. **钱的部分**：支付回调三方校验 + 超时不取消已付订单
6. **退票与退款对账**：状态先切库存后补、四类渠道结果四类动作、`stock_restored` 幂等标记

（原项目开场讲"解决三个问题"，第三节必须把这三点都覆盖到：不超卖对应难点 1，最终一致对应难点 2，读流量对应难点 3。）

每节结尾必须有一句"如果面试官问，我可以展开……"，给他留钩子。

### 第四节：高频追问 Q&A（扩到 15 题）

在现有 10 题基础上新增 5 题，优先选会被追问的：

1. 限流会不会误杀正常用户？（答：单用户桶 3 是给单个用户防连点，全局 500 是系统容量；实测精确 3 放 7 拒）
2. 为什么限流后压测只成交 3 单？（答：一个 token 打 1000 线程，被单用户桶卡住；放开后 100 单零超卖）
3. 退款为什么不能重发？（答：SUCCESS 重发是重复退款，PROCESSING 重发是多压一笔申请，只有 NOT_EXIST 允许）
4. 库存回补为什么需要 `stock_restored`？（答：restore 是 remain+1 不幂等，对账重试会补成 101）
5. 三个定时任务会不会互相打架？（答：不同表不同锁，CAS 兜底）

### 第五节：数据背诵卡（短句，脱口而出）

只放能在 5 秒内说完的句子，每条带一个数字。至少覆盖：写压测、读压测、限流精确性、退票 17 项、退款对账 7 项、支付 12 项。

### 第六节：诚实边界清单（新增，重要）

列清"哪些是做的、哪些只是方案、哪些没验证"。至少包含：

- 单机部署，Redis 单实例、MySQL 单机、应用单实例；集群方案只停留在方案层
- 支付渠道是 Mock，不是支付宝/微信真实 SDK
- 下单验证码未做
- 库存分桶评估过但没做，原因是热点行拆分后跨行一致性成本高于收益
- `PROCESSING` 分支与"最大重试只告警一次"只有代码路径，Mock 渠道造不出处理中态
- 支付前端由本人手工点验，没有自动化 UI 测试
- 退款对账超过最大重试只发日志告警，没有后台管理界面可以人工改状态
- Mock 渠道的退款结果存在内存里，应用重启后 `refundResults` 清空，对账会把所有在途退款判为 NOT_EXIST 并重发一次（真实渠道不会出现）

写这一节的目的：被追问时能主动说出边界，比被戳穿好。

## 五、写作规范

1. **口述体**：能念出来。短句为主，一句话不超过 40 字
2. **数据必须精确**：451 TPS、2442 TPS、17 项、7 项、12 项、100 单、0/0、55 秒、900 秒、300 秒——照抄，不改写
3. **每个难点都要有"我踩过的坑"**，这是区别于背模板的关键
4. **不加小标题以外的装饰**，不用 emoji，不用 emoji 分隔符
5. **引用块 `>` 用于可背诵的原文**，普通段落用于说明
