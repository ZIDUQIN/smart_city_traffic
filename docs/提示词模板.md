# 接口开发提示词模板

> 用法：每次开发一个接口时，复制下方「主模板」，填空后发给 AI。
> 想不清楚的项可以留空或写"待建议"，AI 会追问补全。一次只提一个接口，逐个闭环。

---

【2. 接口定义】
- 方法 + 路径：
- 是否需登录：
- 入参字段（字段名 : 含义 : 是否必填）：
- 返回内容：

【3. 处理流程】（按顺序写，能用大白话就别用术语）
①
②
③
④

【4. 涉及数据】
- 读哪些表 / 缓存 key：
- 写哪些表 / 缓存 key：
- 需要新增的表或字段（没有就写"无"）：

【5. 失败情况】
每种失败返回什么提示：
（例：已购买该车次 / 余票不足 / 活动未开始）

## 二、变体模板

### A. 修改已有接口

```
【任务】修改已有接口 ___（类名/路径：___），现在的问题是 ___，希望改成 ___。

【约束】
- 只改这个接口相关文件，改动前先列出你会动哪些文件和改什么
- 不要顺带改我没提到的代码
```

### B. 排查报错

```
【任务】启动/调用时出现下面报错，帮我定位并修复：

【完整报错堆栈】
（粘贴）

【我做了什么操作】
（例：刚执行完 mvn compile / 调用了 /api/xxx 接口）

【相关配置 / 相关代码】
（粘贴或指明文件）

【约束】
- 先给原因判断和排查顺序，确认原因后再改代码
- 不要用"注释掉报错代码"这类方式绕过问题
```

### C. 只要设计不要代码

```
【任务】只做设计，不写代码：接口 ___ 的表结构、Redis key 设计、Lua 脚本逻辑、分层结构。

【要求】
- 用大白话解释每个设计为什么这么做
- 给出有哪些替代方案，各自优劣
- 最后给一个你推荐的方案和理由
```

### D. 让 AI 讲解已有代码（补"不会写但要看懂"的短板）

```
【任务】给我讲清楚这段代码 / 这个接口的实现：
（指明文件或粘贴代码）

【要求】
- 按"请求进来后每一步发生了什么"的顺序讲，不要按类的顺序讲
- 指出哪几行是最关键的技术点（如原子扣减、缓存判空）
- 最后给 3 个面试可能问到的问题和参考回答
```

---

## 三、使用要点

1. **【3 处理流程】是最关键的一项**。写不细就多写几遍，这是你唯一必须想清楚的部分；其余项都能靠 AI 补。
2. **【6 技术点】留空没关系**。AI 会把可选方案列出来给你挑，你只需要判断"哪个更简单、哪个更符合现在的进度"。
3. **一次只提一个接口**。不要一次丢五个需求，逐个闭环，你才记得住、讲得清。
4. **先设计后代码**。养成先看方案再让 AI 写代码的习惯，改方案的代价远小于改代码。
5. **报错题不要贴半截**。堆栈、操作、配置三样齐全，定位速度差好几倍。

## 四、填空示例（可直接改字段复用）

> 1. 场景：用户点"提交订单"抢票，接口给我扣余票并生成订单
> 2. 入参：车次编号、出发站、到达站、席别、乘客ID
> 3. 流程：① 校验用户是否已买过该车次（一人一单）② 查余票，不足返回售罄 ③ 够就原子扣减 ④ 生成订单，状态"待支付" ⑤ 返回订单号
> 4. 数据：读 Redis 余票，写订单表，记录已购用户
> 5. 返回：成功给订单号；失败分别提示"已购买/已售罄"
> 6. 技术点：扣减要防超卖，用 Redis + Lua 原子操作

这段就是模板填完后的样子——说的是业务，不是代码。
