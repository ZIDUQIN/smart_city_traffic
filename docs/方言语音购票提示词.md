### 5.2 StationIndex（启动构建）

```java
@Component
public class StationIndex {
    // 61 条，启动时一次性构建
    private List<Entry> all;
    private Map<String, String> pinyinOverride;  // ≤5 条人工指定

    public static class Entry {
        String stationName;     // 西安北
        String city;            // 西安
        String fullPinyin;      // xianbei（无 separators）
        String initials;        // xab
        Set<String> bigrams;    // {西安, 安北}
    }
}
```

要点：

- `@PostConstruct` 调 `TicketService.stations()` 取数据；**不要**直接查 Mapper；
- pinyin4j 格式：`HanyuPinyinOutputFormat` 设置 `WITHOUT_TONE` + `LOWERCASE` + `WITH_V`；
- 单字取拼音数组第一个；`null` 或异常 → 用原字占位；
- 多音字 override 常量表（初始可为空，遇到再加，例如"长沙/重庆"若被误读）；
- 构建日志：`车站拼音索引构建完成，共 61 条`（不打印站名内容）。

### 5.3 StationCorrector（核心）

**方法签名与调用顺序（重要）**

```java
CorrectionResult correct(String rawText, LocalDate date);
```

顺序固定五步：① 切方向 → ② 各自打分 → ③ **先确定日期**（由 `IntentParser` 解析后传入）→ ④ 车次反查（需要日期）→ ⑤ 分档决策。
日期未知时用当天做反查日期——反查只用于"这条线通不通车"，当天无车次不代表站名错。

**打分（单候选对单片段）**

```java
double score(Entry s, String segment) {
    double best = 0.0;
    for (String sub : substringsOfLength(segment, 2, 5)) {   // 长度 2..5 的所有子串
        String py = PinyinUtil.toPinyin(sub);                 // 无 separators 小写
        double pSim = 1 - lev(s.fullPinyin, py) / Math.max(len(s.fullPinyin), len(py));
        double iSim = 1 - lev(s.initials, initialsOf(py)) / Math.max(len(s.initials), len(initialsOf(py)));
        double cSim = 2.0 * bigramIntersect(s.bigrams, bigramsOf(sub))
                    / (s.bigrams.size() + bigramsOf(sub).size());
        double v = 0.60 * pSim + 0.25 * iSim + 0.15 * cSim;
        if (s.stationName.contains(sub) || sub.contains(s.stationName)) v += 0.35;
        if (s.city != null && segment.contains(s.city)) v += 0.10;
        best = Math.max(best, Math.min(1.0, v));
    }
    return round(best, 3);
}
```

**方向切分**

```java
Direction segments = splitDirection(rawText);
// 规则按优先级（见设计 5.5）：
// 1. "从/自/由 A 到/去/往 B" → from=A, to=B
// 2. "去/往/到 B"（无出发词）  → to=B, from=null
// 3. "A 到 B"                   → from=A, to=B
// 4. 单地名无方位词             → to=该地名, from=null
// 5. 多地名无法判定             → 全部候选，from/to 都标记待确认
```

**分档（返回决策）**

| 条件 | 决策 |
|---|---|
| top1 ≥ 0.85 且 top1 - top2 ≥ 0.05（同方向） | `AUTO`，直接采用 |
| top1 ≥ 0.85 但差距 < 0.05 | `CONFIRM`，强制点选 |
| 0.60 ≤ top1 < 0.85 | `CONFIRM`，给 Top3 |
| top1 < 0.60 或无候选 | `MISSING`，进入兜底 |

**缺站处理**：`from` 或 `to` 为 `MISSING` → `needStationConfirm=true`、`missingStations` 标注、**不查票**。

**车次反查（在分档后、返回前）**

```java
// 组合 ≤ 3×3 = 9
for (combo : fromCandidates × toCandidates) {
    List<TrainSearchVO> r = ticketService.search(combo.from, combo.to, date);
    if (!r.isEmpty()) combo.hasTrain = true;   // 置信度 +0.15（封顶 1.0）
}
// 仅一组 hasTrain=true 且为 AUTO/CONFIRM → 直接采用该组，needStationConfirm=false
```

注意：反查仅在 `date` 已知（有默认日期）时做；日期未知先解析日期再反查。

### 5.4 IntentParser

**字段**：`fromStation, toStation, travelDate, seatPreference, passengerCount, parserSource`

**规则正则（按顺序，全部命中则不调模型）**

```java
// 日期
(今天|今日|今儿|今儿个)                → today
(明天|明日|明儿|明儿个|明儿天)          → today+1
(后天|后儿|后儿个)                      → today+2
(大后天)                                → today+3
(这周|本周|这个礼拜)(一|二|三|四|五|六|日|天) → 本周对应日（若已过则下一周，需提示）
(下周|下礼拜)(一|二|三|四|五|六|日|天)  → 下周对应日
(\d{1,2})月(\d{1,2})(号|日)             → 当年该日期（跨年按未来最近一次）
(\d{1,2})(号|日)                        → 本月该日（已过则下月）
// 人数
(\d+|[一二两三四五六])\s*(张|个|位|人|口)
// 席别
最便宜|便宜|省钱          → SECOND_CLASS
一等|一等座                → FIRST_CLASS
商务|商务座|头等           → BUSINESS
```

中文数字映射：`一1 二2 两2 三3 四4 五5 六6`。

**默认值与校验**

| 情形 | 处理 |
|---|---|
| 无日期 | 当天；当天无票**不自动跳明天**，提示 |
| 无人数 | 1 |
| 人数 > 5 | 拒绝，提示"一次最多 5 张" |
| 无席别 | `SECOND_CLASS` |
| 日期 < 今天 或 > 今天+7 | 拒绝，提示"只能买 7 天以内的票" |

**模型兜底**

- 触发条件：规则未解析出日期、或站名缺失且文本长度 > 6；
- 调用 `ChatClient`（Spring AI 2.0.1），要求输出严格 JSON；
- 提示词内注入：今天日期、7 天窗口、61 个站名清单、三个席别枚举；
- **输出白名单校验**：站名必须在 61 条内、日期必须在窗口内、人数 1–5；任一不合法 → 丢弃该字段用默认值，不整条丢弃；
- JSON 解析失败 → 全部用规则默认值，`parserSource=rule`；
- 模型调用超时 2s，超时即降级。

### 5.5 AsrService 三实现

```java
public interface AsrService {
    /** @return 识别结果；绝不返回 null，失败抛 BizException */
    AsrResult recognize(byte[] wav, String dialect, String mockText);
    String provider();
}
```

| 实现 | 行为 |
|---|---|
| `MockAsrService` | 返回 `mockText`（为空时返回 `""`），`provider=mock`，`confidence=0.9`，耗时 0 |
| `XfyunAsrService` | 见下；未配置 key 时 `provider()` 返回 `xfyun` 但 `recognize` 直接抛 `BizException("未配置讯飞密钥")` |
| `AliyunAsrService` | **不实现**，方法抛 `UnsupportedOperationException`；仅占位，供后续切换 |

**选型方式**：新增 `AsrServiceRouter`，注入三个实现，`@PostConstruct` 时按 `voice.asr.provider` 选定一个并对外提供 `AsrService` 能力。不要用 `@ConditionalOnProperty` 逐个装配——mock 实现需要始终存在，便于随时切换与测试。

`AsrServiceFactory`（或 `@Primary` 选择）按 `voice.asr.provider` 返回对应 bean。

**讯飞一句话听写（IAT）要点**（M4 阶段实现，M1 用 Mock）：

- 鉴权：对 `host + date + request-line` 做 HMAC-SHA256，**不要自己造算法，按官方文档实现**；
- 音频：`audio/L16;rate=16000`，base64 分段发送；
- 参数：`domain=iat`、`language=zh_cn`、`accent` 按设计 6.3 映射、`vad_eos=10000`、`dwa=wpgs` 关（一句话模式）；
- 超时 5s，失败抛异常由 Controller 转 500 + 前端降级。

### 5.6 VoiceController

```java
@RestController
@RequestMapping("/api/voice")
public class VoiceController {

    @PostMapping("/recognize")
    public Result<AsrResult> recognize(
        @RequestParam(value = "audio", required = false) MultipartFile audio,
        @RequestParam(value = "dialect", defaultValue = "auto") String dialect,
        @RequestParam(value = "debugText", required = false) String debugText,
        @RequestParam(value = "sessionId", required = false) String sessionId,
        Authentication auth) { ... }

    @PostMapping("/interpret")
    public Result<VoiceInterpretResponse> interpret(@RequestBody VoiceInterpretRequest req, Authentication auth) { ... }
}
```

要点：

1. 两个接口都需登录（沿用现有 JWT 配置，不额外加 `permitAll`）；
2. `VoiceRateLimiter.tryAcquire(userId)`，超限返回 `code=429`；
3. `recognize`：mock 模式允许 `audio == null`；非 mock 必须校验 `size ≤ maxBytes`、`duration`（WAV 头解析）`1–30s`；
4. 日志只记：`sessionId、字节数、耗时、文本长度、provider`，**不记文本内容**；
5. `interpret`：不写库，只调 `StationCorrector` / `IntentParser` / `TicketService.search`；
6. `VoiceRateLimiter`：MVP 用 `ConcurrentHashMap<Long, ArrayDeque<Long>>` 实现"单用户 60 秒滑动窗口"，超限返回 429。**已知局限**：多实例部署时各实例独立计数，额度不准；需要精准时换 Redis `INCR + EXPIRE`，列为 P2，不进 MVP。

### 5.7 DTO 字段表

`AsrResult`：`rawText, dialect, provider, confidence, elapsedMs`

`StationCandidate`：`stationName, city, score, matchedText`

`DirectionalCandidates`：`from: List<StationCandidate>, to: List<StationCandidate>`

`VoiceIntent`：`fromStation, toStation, travelDate(String yyyy-MM-dd), seatPreference, passengerCount, parserSource`

`VoiceInterpretRequest`：`text, fromStation, toStation, lastUsedFrom, todayHint`

`VoiceInterpretResponse`：`correctedText(String), stationCandidates(DirectionalCandidates), intent(VoiceIntent), needStationConfirm(boolean), missingStations(List<String>), trains(List<TrainSearchVO>), speech(String), emptyReason(String)`

```js
  function showConfirmText(data) {}   // 大字回显
  function speak(text) {}             // SpeechSynthesis
  function onConfirmYes() {}          // 进入选车次

  // 选车次 → 复用 app.js
  function pickTrain(trainIdx, seatIdx) {
    // state 是 app.js 的全局对象（const 声明，属性可写），其他 script 可直接读写
    state.searchDate = vstate.intent.travelDate;  // 必做，否则按页面原日期下单
    state.trains = vstate.trains;                 // 结构已与 /api/ticket/search 一致
    const n = vstate.intent.passengerCount;
    if (n && n > 1) {
      toast('您说的是 ' + n + ' 张，请在下面选 ' + n + ' 位乘车人');
    }
    openOrderModal(trainIdx, seatIdx);
  }
})();
```

**关键约束**

1. `pickTrain` 必须先写 `state.searchDate` 再调 `openOrderModal`——`app.js` 的 `submitOrder` 用 `state.searchDate` 下单，漏了就会按页面原日期下单；
2. `vstate.ts` 与 `state.trains` 是两个对象，赋值后再调，不改 `app.js`；
3. 选择席别：车次卡片上点某个席别 chip → `pickTrain(idx, seatIdx)`；若该席别 `price=null` 则置灰不可点；
4. 所有动态文本（站名、车次号、播报文案）渲染时必须套全局 `esc()`，不拼裸字符串；
5. 语音面板不依赖 `app.js` 的 `openModal/closeModal`，用自带的 `hidden` 切换，避免耦合。

### 7.2 pcm-worklet.js

```js
class PcmProcessor extends AudioWorkletProcessor {
  process(inputs) {
    const ch = inputs[0] && inputs[0][0];
    if (ch) this.port.postMessage(ch);   // 传 Float32Array
    return true;
  }
}
registerProcessor('pcm-processor', PcmProcessor);
```

采集端：`AudioContext({sampleRate:16000})` → `audioWorklet.addModule('/js/pcm-worklet.js')` → 收集 Float32 → 停止后转 Int16 → 拼 44 字节 WAV 头。

长度校验：`1s ≤ duration ≤ 30s`，超过 30s 自动停。

## 12. 复检记录

| 轮次 | 检查重点 | 发现的问题 | 处置 |
|---|---|---|---|
| 第 1 次 | 接口契约与前端复用方式 | ① `openOrderModal` 接的是索引不是对象；② `submitOrder` 依赖 `state.searchDate` 下单；③ 语音返回的 trains 必须与 `/api/ticket/search` 同构，否则塞不进 `state.trains` | 契约明确"trains 结构同 search 返回"；`pickTrain` 强制先写 `state.searchDate`；补张数提示 |

2. 任何跨文件集成点都要写清"谁、在什么时候、写哪个全局变量"，否则集成时必然出错。

### 14.2 实测中发现并修掉的 9 个问题

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 用户点"对，就是这个"之前，面板只有车次号和时刻，**看不到被纠正成哪个站、哪一天** | 只把原文塞进 `voice-text`，没展示后端 `correctedText` | 新增 `#voice-understood`，显示"我听懂了：从西安北到北京西，11月17号，周二，1 张，二等座" |
| 2 | 说"我要去北京"，候选里混出**宝鸡南 / 高碑店东 / 保定东** | 后端 `MIN_CANDIDATE=0.40` + `MAX_CANDIDATES=5` 把长尾都吐给了前端，前端 `slice(0,3)` 照收 | 前端按 `top1 - 0.15` 过滤分数差太远的，再取前 3 |
| 3 | 站名没定时，界面显示"我听懂了：从哪里到哪里，…" | `correctedText` 在站名缺失时用"哪里"占位 | `needStationConfirm` 为 true 时清空这一行 |
| 4 | **点了"北京西"之后，界面还显示"到达站：北京南 / 北京西"，永远走不到车次** | 后端 `stationCandidates` 即使该方向已定仍原样返回；前端也没判断 `intent.toStation` | `renderCandidates` 跳过 `intent.fromStation`/`toStation` 已定的方向（后端未收口，前端兜住） |
| 5 | **只说"我要去北京"时无路可走**：出发站候选为空，界面只能选到达站，选完还是没出发站 | M1 里 `stationCandidates.from` 在文本无出发信息时返回空数组，设计 5.7 的"常用站选择"没落地 | 用 `localStorage.lastFrom` 给出"上次是从这儿走的 → 西安北"按钮（**只提供选项，不替用户决定**）；连这个都没有时给句式让用户重说一句 |
| 6 | 用户已点选出发站后，播报仍是"您是要从哪儿出发？" | Controller 用 `correction.getMissing()` 判断，而 correction 不知道用户已点过 | 判断改为 `missing.contains("from") && isBlank(request.getFromStation())` |
| 7 | 按得很快松手后**录音一直跑到 30 秒**；录音中滑出圆钮会被误判成"说完了" | `wantStop` 在 `getUserMedia` 成功之后才重置，把 STARTING 期间松手的意图抹掉了；`pointerleave` 也当成结束 | 拆 `wantStop`/`wantCancel` 两个标志并在开始前清空；删掉 `pointerleave`；**window 上补 `pointerup`/`pointercancel` 兜底**（pointer capture 失效时 up 会落到别处）；`tick()` 发现 phase 已变就自清计时器 |
| 8 | 换页内容后正文停在半截，提示行被滚到看不见 | 候选/车次重渲染后没重置滚动位置 | 新增 `scrollBodyTop()`，两处渲染后调用 |
| 9 | 日期超窗时会误入候选分支，多出一排句式按钮 | `DATE_OUT_OF_WINDOW` 时后端 `needStationConfirm=true`，前端先判了 needConfirm | `doInterpret` 先单独处理 `DATE_OUT_OF_WINDOW` 再判 needConfirm |

前 3 条是观感与信任问题，第 4、5 条是**功能性死路**（不修就买不成票），第 6 条说错话会让老人以为按钮没生效，第 7 条是会持续录音的隐私问题。

## 15. 后端收口（2026-11-17，关闭 14.4 遗留 2、3）

### 15.1 改了什么

**① `lastUsedFrom` 真正参与解析（原来是死字段）**

`VoiceController` 注入 `StationIndex`，在拿到纠错结果后补一步：

- 条件：`from == null`（没定下来）且请求里没带 `fromStation`、`lastUsedFrom` 非空且**是 61 站里的真实站名**；
- 动作：把该站塞进 `stationCandidates.from`，分数 `0.55`，`matchedText="上次"`；
- 脏数据（"火星站"这种）一律丢弃，靠 `StationIndex` 白名单拦。

分数定 0.55 的理由：`AUTO_SCORE=0.85` 是"系统自己敢定"的门槛，0.55 明确压在门槛之下——这个候选的语义只是"多给一个选项"，最终必须用户点一下。

记忆的来源仍是浏览器 `localStorage`（会话不落服务端，这是既定裁决），区别是它现在由**后端**统一变成候选，任何客户端只要把 `lastUsedFrom` 带上就能享受同一套逻辑，不用各自造按钮。

**② 候选按"已定方向"收口**

请求带了 `fromStation` → `stationCandidates.from` 置空；带了 `toStation` → `to` 置空。

原因：后端原来会把已确定方向的候选原样吐回，客户端必须自己判断"这个方向定没定"才不至于原地打转。现在由后端保证语义——**候选列表里有东西，就代表这个方向确实需要用户选**。

**③ 顺带**：前端限流提示去掉多余后缀。"说得太快了，歇一下再说，可以重说"改成"说得太快了，歇一下再说"，后端已经说完了，前端不该再接一句。

# 17 M5：语料集与量化评测（2026-11-17）

到这一章为止，前面所有结论都是**手工挑几条试**得出的：M1 试三条、M4 试两条。手工试能证明"这条路通"，但证明不了"这条路有多准"。M5 要回答的是一个数字：**30 条真实说法里，系统能听懂多少条**。

## 17.1 先查真数据，再定期望值

语料最容易出的错不是"句子不像人说的"，而是**期望值是自己设想的**。所以写每一条之前先问数据库：

```sql
SELECT s1.name AS from_station, s2.name AS to_station, COUNT(*) AS trains
FROM train_station s1
JOIN train_station s2 ON s1.train_id = s2.train_id AND s1.station_seq < s2.station_seq
JOIN station a ON a.id = s1.station_id
JOIN station b ON b.id = s2.station_id
...
```

实测真实跑着的线路（2026-11-17）：西安北→华山北 12、北京西→石家庄 11、西安北→郑州东 9、西安北→上海虹桥 8、西安北→太原南 8、北京西→郑州东 7、西安北→兰州西 7、郑州东→武汉 7、西安北→广州南 7、西安北→成都东 7、西安北→北京西 6……共 100 车次 / 61 站。

这一步的价值在一条反例上：列表里**没有"西安北→北京南"**。所以"我要去北京"这条用例（14 号）的期望值是 `STATION_UNCONFIRMED`（必须问出发站），不是我拍的——是真没这条线。

## 17.2 30 条的分布

| 类别 | 条数 | 想验什么 |
|---|---|---|
| full | 7 | 说的是人话，能不能一条不差地解析出来 |
| typo | 6 | 同音错字（红/虹、正州/郑州、兰洲/兰州、太远/太原、北金/北京、西岸/西安）能不能纠回来 |
| missing_from | 4 | 只说目的地时，出发站会不会被静默默认 |
| date | 3 | "下个月10号"要拦（超 7 天窗口）、"这周五""11月20号"要进 |
| count | 2 | 6 张要回 400、2 张正常 |
| seat | 3 | 一等座 / "最便宜的" / 商务座 |
| noise | 3 | 完全没方向的话，要进兜底而不是胡说 |
| dialect | 2 | 关中话写法（`额明儿个`、`额要去`），音频留空等录 |

12 个字段：`id/category/dialect/text/audio/expect_outcome/expect_from/expect_to/expect_day/expect_count/expect_seat/note`。

两条约定：

- **`expect_day` 用相对今天的天数偏移**（0/1/2/3），不写死日期。否则这份语料过一周就全过期，变成一个只能当日跑的测试。
- **`expect_站名` 结尾带 `#` 表示"同城任一站"**。14 号对到达站只要求"候选里出现北京南或北京西"，因为它本来就该问用户是哪一个——用前缀匹配表达"这两个都算对"。

## 17.3 跑批脚本怎么判

`tools/voice-eval.ps1`：登录取 token → 逐条解析 `audio` 列（非空先走 `/api/voice/recognize` 端到端，空则直接用 `text`）→ 送 `/api/voice/interpret` → 从响应**反推**到底发生了什么，而不是读代码里的剧本：

| 响应特征 | 判为 |
|---|---|
| `code != 200` 且 message 含"最多买" | `TOO_MANY` |
| `emptyReason = DATE_OUT_OF_WINDOW` | `DATE_OUT_OF_WINDOW` |
| `emptyReason = STATION_UNCONFIRMED` | `STATION_UNCONFIRMED` |
| `emptyReason = NO_TRAIN` | `NO_TRAIN` |
| `trains.Count > 0` | `OK` |

然后比对 5 个字段。**`OK` 与空态的比对策略不同**：判为 `OK` 时 intent 里的值必须严格相等；判为空态时 intent 本来就是空的，只校验"候选列表里有没有这个站"。不这么分开，两类用例会互相污染判定。

## 17.4 第一次跑只有 3/30：评测被限流打残了

首跑结果 3/30（10%），而且 27 条 FAIL 的说明是同一句：

```
OTHER(说得太快了，歇一下再说)
```

这句话来自 `VoiceRateLimiter`——按人 6 次/分钟的滑动窗口。脚本 1 分钟连打 30 条，从第 4 条起全被拦。

**这是评测方式的问题，不是业务缺陷。** 判断依据：报错文案是限流文案，不是识别错、不是查不到车；前 3 条全 PASS 说明链路本身是通的。

处理上不动代码——`per-user-per-minute` 本来就是可外部注入的配置，给评测实例单独放开即可（Spring Boot 系统属性优先级高于 yml，`-Dspring-boot.run.jvmArguments` 里传进去就生效）：

```
-Dserver.port=8083 -DLOG_HOME=logs-8083 -Dvoice.rate-limit.per-user-per-minute=200
```

**为什么不去改生产默认值**：6 次/分钟是给真实老人用的节奏，一次订票 2~3 次请求，6 次够用且能挡住误触。为了跑测试把线上限流调到 200，是把测试需求写进了业务配置。

## 17.5 28/30：两条 FAIL 要分开处理

放开限流后重跑，28/30（93.3%）。剩下两条性质完全不同：

| 编号 | 现象 | 性质 |
|---|---|---|
| 25 | `席别 expect=BUSINESS_CLASS actual=BUSINESS` | **语料写错了** |
| 09 | `从西安北去上海红桥` → `STATION_UNCONFIRMED` | **真实算法缺陷** |

25 号的判定依据是查库，不是看代码：

```sql
SELECT DISTINCT seat_no FROM stock_capacity;   -- BUSINESS / FIRST_CLASS / SECOND_CLASS
```

`stock_capacity` 里根本没有 `BUSINESS_CLASS` 这个值，`IntentParser.parseSeat` 返回的 `BUSINESS` 是对的。语料的期望值按真实取值改成 `BUSINESS`。**这正是评测该有的作用：它会先把写语料的人抓出来。**

## 17.6 09 号：半截字也能拿满分

`上海红桥` 的候选实测（修复前）：

```
上海松江 0.94  matchedText="上海"
上海虹桥 0.94  matchedText="上海"     ← 并列，gap=0，过不了 AUTO_GAP=0.05
```

两个上海站的最优窗口都落在 `"上海"` 这两个字上。为什么这 2 个字能拿满分：

- "上海"是 `"上海红桥"` 的子串，滑动到它时 `win.equals(sub)` 成立 → `+0.20`
- `上海虹桥` 的 `city="上海"` 在片段里命中 → `+0.08`
- 原始分 0.95 + 0.20 + 0.08 = 1.23 → 封顶到 `FUZZY_CAP=0.94`

而真正对上的整词 `"上海红桥"` vs `"上海虹桥"`（红/虹同音）也是 0.94。**封顶把"整词命中"和"半截前缀命中"抹成同一个分**，于是并列、`gap=0`、AUTO 失效。

这和 M4 那个"西安"缺陷同源：**短窗口因为加成和封顶，反而赢过完整匹配**。

修复思路不是调权重（调权重会连带影响另外 29 条），而是加一条**准入门槛**：窗口覆盖率低于 0.6 的，这个窗口不参与打分。

```java
private static final double MIN_WINDOW_COVERAGE = 0.6;
```

含义是"匹配到的字数至少占站名六成才算证据"。`"上海"` 对 `"上海虹桥"` = 2/4 = 0.5 → 掐掉；`"西安"` 对 `"西安北"` = 2/3 = 0.67 → 保留（所以 14/15 号那种"只说城市"的用例不受影响）。

修复后实测：

```
09: needConfirm=false  from=西安北  to=上海虹桥  trains=8
  to候选 上海虹桥 0.94  matched="上海红"
  to候选 上海松江 0.872 matched="上海红"
```

gap = 0.068 > 0.05，越过门槛，`上海虹桥` 被自动采用。

同时 `score()` 的排序加了第二关键字：同分时**先比实际匹配到几个字，再比站名长度**。分数并列时，"对上 4 个字"比"对上 2 个字"可信。

| 阶段 | 通过 | 说明 |
|---|---|---|
| 首跑 | 3/30 | 限流打断，非业务问题 |
| 放宽限流 | 28/30 | 两条 FAIL 性质不同 |
| 改语料 + 修窗口门槛 | **30/30** | 8 个类别全部满通过 |

## 17.8 顺手发现的两处脏数据

1. `上海松江` 的 `city` 字段值写成了 `"上海松江"`（应该是 `"上海"`）。后果是城市加成的判定 `segment.contains(city)` 对它失效——这次是帮了忙（少加 0.08），但方向是错的，属于数据录入问题。
2. 语料 25 号的席别期望值。已修。

## 17.9 仍然开着的口子

1. **方言音频一条都没有**：`audio` 列 30 条全空。29/30 是关中话写法，08~13 是通用错字——这两类现在跑的都是**文本层**，验证的是纠错和解析，不是方言识别本身。本机 TTS 只有普通话（Huihui/Zira/Kangkang/Yaoyao），造不出四川话/关中话，这一列只能靠真人录音填。
2. **热词没有对照实验**：`voice.xfyun.hotwords` 能开关，但没有"开/关跑同一批音频"的对比数字。
3. **评测实例的限流是放开的**：8083 用 200 次/分钟跑批，与线上 6 次/分钟不同。这份通过率代表的是"解析能力"，不代表"限流下的用户体验"。
4. **样本偏小**：30 条能暴露明显缺陷（这次暴露了 09），但给不出"95% 置信区间"这种统计结论。要报数字给简历，样本量得到 100+。
