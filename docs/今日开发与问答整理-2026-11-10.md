## 三、B2 统一库存改造

### 3.1 为什么要改：读写两套库存并存的问题

改造前存在两套互不相通的库存：

- **读链路**：读 `seat_inventory` 表 + `ticket:` Hash（区段模型）
- **写链路**：写 `stock` 表 + `stock:` String（扁平模型）

问题：下单扣减的是写链路的库存，读链路的余票数字不会变，**下单后页面余票不动**；两套模型不同，数据对不上，面试时容易被问穿。

### 3.2 12306 的真实做法

- 库存只有**一份真相**：席位库。
- 席位库跑在**分布式内存数据网格**上（早期 Pivotal GemFire，后铁科院自研），余票从席位占用情况实时算出。
- 读服务、写服务分离，但**数据同源**，不是两套独立库存。
- 席位复用：A→B 下车后，B→C 可以再卖给别人，所以按"相邻区段"管理。

### 3.3 扁平库存 vs 区段库存

- **扁平模型**：一个车次一个总数字，不区分区段，无法表达席位复用，只适合"起点到终点"一种票。
- **区段模型（本项目采用）**：把线路切成相邻区段，每个区段独立维护余量；跨区段购票取经过区段的最小值，扣减时每个区段各减 1。

### 3.4 数据模型

- `stock`：带 `segment_no`，唯一约束 `(train_no, seat_no, segment_no)`。
- `order`、`ticket_deduct_record`：带 `from_seq`、`to_seq`。
- 演示 G1001：西安北(1) → 咸阳秦都(2) → 宝鸡南(3)，两区段 × 三席别共 6 行。

### 3.5 下单完整流程（B2）

1. 用户下单，生成订单号。
2. **先写订单流水**，状态"扣减中"，流水带起点、终点。
3. Redis 执行 `deduct.lua`（原子）：
   - 判重：检查乘车人是否已买（返回 -3）。
   - 逐区段检查库存：key/field 不存在 -2、库存不足 -1。
   - 逐区段 `HINCRBY -1`。
   - 在"已扣标记"集合记录订单号；设置乘车人占位。
4. 创建订单并插入订单表（待支付/已确认）。
5. 扣减 DB 真实库存（每区段条件 UPDATE）。

### 3.6 Redis 里的三个 key（同一车次用 hash tag 保证同槽）

| key | 类型 | 作用 |
|---|---|---|
| `stock:{G1001}:SECOND_CLASS` | Hash | 各区段实时余量，field 是区段号 |
| `deducted:{G1001}:SECOND_CLASS` | Set | 已扣标记，记录"哪些订单已在 Redis 扣过库存" |
| `passenger:dedup:{G1001}` | String | 乘车人判重占位，防止同一身份证重复购票 |

- **第二个 key（deducted Set）的含义**：它是订单维度的"已扣标记"。Lua 扣完库存后把订单号 `SADD` 进去，回补时用 `SREM`（幂等），对账时用 `SISMEMBER` 判断这笔到底扣没扣。
- 判重走的是第三个 key（passenger:dedup），不是第二个。
- **hash tag 的作用**：Redis Cluster 下 key 分布在不同哈希槽，跨槽无法在一个 Lua/事务里同时操作多个 key。用 `{G1001}` 把同一车次的 key 强制映射到同一个哈希槽，就能在一个脚本里原子操作。

### 3.7 回补

- 用区段数组，和扣减时完全一致：`from_seq .. to_seq-1` 逐段 `HINCRBY +1`。
- `rollback.lua`：`SREM` 返回 0 表示已补过/从未扣，直接幂等返回；返回 1 才逐段回补并释放乘车人占位。

### 5.1 关键演进

1. **200 线程首次 36.5% Connection refused**：连接队列不足。加 Tomcat 调优（线程 400、accept-count 500、max-connections 1000）后 0 错误。

4. **Hikari 10→30**：TPS 无变化，证明连接池不是瓶颈（瓶颈在 DB 行锁串行）。
5. **Lua 预检改造**：新增只读 `check.lua`，下单时在发 MQ 前先预检，不通过直接返回已取消，不进 MQ/流水/DB，挡住无效请求。
6. **GUI vs 非 GUI 定论**：裸 socket 多线程对照（1000 连接 0 错误），非 GUI 实跑 1000 线程 0 错误。证明 GUI 渲染与压测线程同 JVM 抢资源才是错误来源，**正式压测必须用非 GUI**。

## 七、支付模块（企业级架构，本地 Mock）

### 7.1 企业真实链路

1. 校验订单（归属、状态、金额）。
2. 服务器对服务器调第三方**统一下单**（带签名），拿到 `prepay_id`。
3. 重签名返回前端，前端拉起收银台。
4. 用户付款，第三方**异步回调** notify（服务器到服务器，不是前端通知）。
5. 后端：验签 → 金额校验 → 幂等改已支付。
6. 必须返回成功应答，否则第三方按递增间隔重试。
7. 前端轮询 + 关单前主动查单，双保险。

### 7.2 四个关键点的实现

| 关键点 | 实现方式 |
|---|---|
| 验签防伪造 | HMAC-SHA256（共享密钥，重算比对，恒定时间比较）；头 `X-Mock-Signature` |
| 金额/订单校验 | 用回调订单号查本地订单，回调金额必须与订单、流水一致 |
| 幂等改已支付 | 第三方交易号唯一索引 + 条件 UPDATE（待支付→已支付），看影响行数 |
| 成功应答 | 先落库再应答；成功返回 SUCCESS，否则 FAILURE 触发重试 |

### 7.3 验签机制

- **HMAC-SHA256（本项目）**：双方持同一密钥，对原始报文用密钥算摘要，重算比对。密钥不传输。
- **RSA2（非对称）**：平台用私钥签名，商户用公钥验签，公钥无法伪造签名。
- 官方 SDK 本质是把密码学运算封装成工具类方法，例如支付宝 `AlipaySignature.rsaCheckV1(报文, 公钥, ...)` 返回 true/false，失败直接拒绝、不做业务。
- 验签时机：收到回调的第一步，验不过直接拒绝。

### 7.4 商户号与沙箱

- 商户号需要营业执照 + 对公账户，个人无法开通。
- 支付宝有免费沙箱可体验真实 SDK；微信无个人沙箱。所以本项目用 Mock 渠道。
- AppId 是应用标识，不是"微信=1、支付宝=2"这种自定义编码。

### 7.5 金额不匹配的处理（重点）

- 原则：**不确认、不取消、不返回 SUCCESS、告警挂起**，等人工/对账。
- 原因：用户已经真的付了钱，绝不能取消真实付款的订单。

### 7.6 幂等细节

- 第三方交易号加唯一索引，防止重复插入。
- 订单条件 UPDATE：只有"已确认（待支付）"才能改成"已支付"，看影响行数是否为 1。
- 重复回调：订单已支付则幂等返回 SUCCESS，回调计数 +1。
- 同一订单多次 prepay：一条成功后，其余待支付流水自动关闭。

### 7.7 超时关单

- `PaymentTimeoutTask`：cron 每分钟，分布式锁，扫描超过支付时限（900 秒）的已确认订单。
- **关单前先查单**：已支付成功则跳过，不能误关。
- 取消订单 → 回补 Redis（rollback.lua）→ 回补 DB → 关闭待支付流水。

### 7.8 支付模块实测结果

| 验证项 | 结果 |
|---|---|
| 下单 → prepay → confirm → 回调 → 已支付 | 通过，订单已支付、流水支付成功、渠道交易号回填 |
| 订单金额 | 二等实测 100.00 |
| 伪造签名 | 返回 FAILURE |
| 重复回调 | 幂等 SUCCESS，回调计数 2 |
| 用户取消 | 库存 98→99，Redis/DB 精确回补 |
| 已支付订单取消 | 拒绝（400） |
| notify 匿名、其他接口 401 | 符合 |
| 我的订单 | 仅返回当前用户 |

代码确认未实跑：金额不匹配挂起分支、15 分钟超时任务（其原语均已单独验证）。

## 八、关键问答整理（Q&A）

### 8.1 库存与 Lua

**Q：为什么不能把扣减拆成"先查再改"两条命令？**
A：两条命令之间有时间差，多个线程可能同时查到同一余量，再各自扣减，导致一个数据被扣多次、超卖。所以要在一个 Lua 脚本里原子完成"判断 + 扣减"。

**Q：Lua 预检（check.lua）和真正扣减分开，会不会又有时间差？**
A：会。预检不参与业务，只用来提前挡无效请求；预检时有票，可能在真正扣减前被别人买完。最终正确性仍由 deduct.lua 里的真实库存判断保证，预检只是优化，不替代扣减校验。

**Q：下单成功后还要往 Redis 的 key 里插订单号吗？**
A：要。扣完库存后在 deducted Set 里记录订单号，标记"这笔已在 Redis 扣过库存"，回补和对账时据此判断。

**Q：回补为什么也要用区段数组？**
A：扣减时经过哪些区段，回补就要逐段加回去，方向相反、区段完全一致，否则会出现某段库存对不上。

**Q：12306 的席位库是不是像阿里云 PolarDB 那样，靠 RDMA 做内存间高速传递？**
A：思路类似但不是一回事。PolarDB 是"计算存储分离"的数据库集群，RDMA 是它的物理网络加速手段；12306 的席位库是一个**分布式内存数据网格**（内存里的对象/网格数据库），余票直接在内存里从席位占用实时算出，核心是"内存计算 + 数据同源"，而不是传统磁盘数据库。两者都在追求内存级速度，但产品形态不同。

**Q：那 Lua 预检（check.lua）到底保留还是不保留？**
A：保留。它是只读的，不写数据、不改变正确性，却能在发 MQ、写流水、动 DB 之前就把无票/重复的无效请求挡掉，节省下游资源。最终防超卖仍由 deduct.lua 保证，预检只是低成本的前置优化，没有副作用。

**Q：B2 改造具体把流程从什么变成了什么？**
A：原来写链路是"扁平库存"（一个车次一个总数字，stock 用 String），读链路是"区段 Hash"，两套模型对不上。B2 之后写链路也改成区段模型：扣减从"减一个总数"变成"逐区段 HINCRBY -1"，流水和订单都带上 from_seq/to_seq，读写共用同一份 stock 数据。

### 8.2 对账与补偿

**Q：主流程慢了一步，订单流水被定时任务先扫到、改成"补偿中"并做了补偿，这个过程是怎么回事？**
A：这是"Redis 已扣减、但订单还没生成/没改成功"的兜底场景。定时任务扫描到这种异常流水后，先用 CAS 把流水从"扣减中"抢占改成"补偿中"（抢到才处理，保证只有一方执行），再做补偿（回补库存、把订单置为失败/取消）。如果主流程稍后也想改这条流水，会因为状态已经不是"扣减中"而 CAS 失败，不会重复处理。这一步要记录流水状态变更，方便对账追溯。核心原则：**谁先 CAS 抢到流水谁负责，另一方自动让位**，避免重复补偿。

**Q：deducted Set 在对账时怎么用？**
A：对账时用 SISMEMBER 判断某订单到底有没有在 Redis 真正扣过：在集合里说明扣过，需要回补；不在说明没扣，不能回补（否则超卖）。这就是"先记账后动钱"留下的判定依据。

### 8.3 事务消息与回查

**Q：本地事务回滚时为什么不能直接把半消息取消了事？**
A：半消息取消后消费者收不到消息；而 MQ 回查可能查到新的订单已经走到该状态，直接回滚会把本来在走正常流程的订单误杀。

**Q：回查返回 true 和 false 分别怎么处理？**
A：true 表示已经扣减了库存，需要走回补；false 表示还没扣库存，直接返回失败。只有确实扣过库存才能回补，否则会造成超卖。

### 8.4 压测

**Q：怎么从浏览器找到 token？**
A：浏览器登录后按 F12 打开开发者工具 → Application（应用）标签 → Local Storage（本地存储）→ 选本站点，里面存的 token 字段就是；也可以在 Network（网络）标签里看任意请求的请求头 `Authorization: Bearer xxx`，后面那串就是 token。

**Q：压测时怎么看数据/结果？**
A：两种方式。一是 JMeter 里加 View Results Tree（结果树）、Summary Report（汇总报告）看每次请求和汇总；二是用非 GUI 跑，结果写进 .jtl 文件，再用 `-e -o 文件夹` 生成 HTML 报告。数据库里的订单/库存变化则用 mysql 客户端查表确认。

**Q：线程池数量在哪里调？**
A：分两类，都在 `application.yml`：
- Tomcat 工作线程：`server.tomcat.threads.max/min-spare`、`accept-count`、`max-connections`。
- 数据库连接池 Hikari：`spring.datasource.hikari.maximum-pool-size/minimum-idle`。
另外 MQ 事务回调线程池在 `config` 里的 `mqTransactionExecutor` Bean（core 8、max 16）。

**Q：压测报告上面的指标都是什么？性能好看哪个？**
A：常见指标：
- **Samples**：总请求数；**Error%**：错误率（越低越好，目标 0）。
- **Throughput / TPS**：每秒处理事务数，**衡量吞吐的核心指标，越高越好**。
- **Average / Min / Max**：平均/最小/最大响应时间（毫秒）；**90th/95th/99th pct**：百分位延迟，比平均值更能反映真实体验。
判断性能先看 TPS 和 Error%，再看 P95/P99 延迟，平均值只作参考。

**Q：为什么之前有错误、现在没了，改了什么？**
A：错误来自连接槽被裸连接占满和 TIME_WAIT 堆积，清理连接后恢复；代码逻辑本身没有问题。GUI 模式的错误则是界面渲染与压测线程抢 JVM 资源，非 GUI 模式可消除。

**Q：平均延迟 1 秒是不是太慢、性能差？**
A：写链路在 1000 线程同时压满时，DB 行锁串行处理，平均延迟自然升高，这是极端压力下的结果，不代表单次用户请求慢。判断性能主要看 TPS、错误率和零超卖，而不是只看延迟。

**Q：是不是只能抗 130 个请求？**
A：不是。130 是某个瞬时并发口径的误读；实测 1000 线程全部有响应、0 错误、451 TPS。能承受的并发量取决于连接配置和 DB 处理速度。

**Q：那单机最高能抗多少并发？还有什么改进空间？**
A：当前写链路实测稳定在 451 TPS、1000 线程 0 错误，瓶颈是 MySQL 行锁串行，不是连接池或 Redis。单机上的改进方向：让更多请求在 Redis/Lua 层被拦截（预检、判重）、减少每个事务持锁时间、把对账和超时处理异步化。再往上的量级（几十万并发）只能靠水平扩展 + 集群，不是单机优化能解决的。

**Q：这个秒杀到底做对了吗？和"要提高吞吐"的目标矛盾吗？**
A：做对了。正确性（零超卖、零错误、最终一致）是秒杀的生死线，已经过压测验证；之前说的"牺牲吞吐"是指为了正确性引入了行锁串行，这是单机写链路的固有取舍，不是方向错误。读链路 2442 TPS 已经体现了高吞吐，写链路在保证不超卖的前提下做到 451 TPS。

**Q：非 GUI 怎么测？数据是真实的吗？**
A：命令见第五章，`jmeter.bat -n -t 计划 -l 结果.jtl`，全程无界面。结果是真实压测产出，TPS、错误率、延迟都由 JMeter 统计并落在文件里，不是估算。

### 8.5 支付

**Q：我们自己的订单号会传给微信/支付宝吗？**
A：会。统一下单时把商户订单号传过去，第三方同时生成自己的渠道交易号；本地用第三方交易号唯一索引做幂等。

**Q：一定能确定回调对应的订单存在吗？**
A：不一定。若订单/流水查不到，挂起等重试/对账并告警，不返回成功，不做盲目更新。

**Q：成功应答是答给谁的？**
A：答给第三方。先完成数据库处理再应答 SUCCESS，告诉第三方"我已处理，不用再重试"；否则第三方会按策略反复回调。

**Q：验签到底谁来用、什么时候验？SDK 那句工具类调用看不懂？**
A：验签是**商户后端**在收到回调的第一时间做的，不是前端、也不是用户操作。以 HMAC 为例：商户用共享密钥对收到的原始报文重新算一次摘要，和回调头里带的签名用恒定时间比较，一致才放行。真实项目里不用自己手写算法，引入官方 SDK 后它把运算封装成工具类方法，例如 `AlipaySignature.rsaCheckV1(报文, 公钥, 编码, 签名类型)`，你只要把报文和公钥传进去，它返回 true/false；返回 false 就直接拒绝、不做任何业务。

**Q：HMAC 和 RSA2 有什么区别？**
A：HMAC 是对称的，双方持同一把密钥，密钥要严格保密；RSA2 是非对称的，平台用私钥签名、商户用公钥验签，公钥即使泄露也无法伪造签名，安全性更高，也是支付宝/微信的主流方式。本项目 Mock 用 HMAC 是因为实现简单、便于演示。

**Q：商户号难弄吗？AppId 是什么？**
A：商户号需要营业执照和对公账户，个人开通不了，有一定门槛；支付宝提供免费沙箱可体验真实 SDK，微信没有个人沙箱。AppId 是支付平台给每个接入应用分配的唯一标识，用来识别"是哪个应用"，不是我们自己定义的"微信=1、支付宝=2"。

**Q：第三方的订单号是我们定的还是它定的？**
A：两个号并存。统一下单时我们把**商户订单号**（本地 order_no）传过去，第三方受理后再生成自己的**渠道交易号**（channel_trade_no）。回调时两个号都会带回来，本地用渠道交易号的唯一索引保证幂等。

**Q：回调金额或信息对不上怎么办？用户已经付钱了，不能取消订单吧？**
A：对，绝不能取消。处理原则是"不确认、不取消、不返回 SUCCESS、告警挂起"，把订单/流水保持在待处理状态，等人工核查或定时对账，同时应答 FAILURE 让第三方先别停。这样既不会误确认，也不会把真实付款的订单抹掉。
