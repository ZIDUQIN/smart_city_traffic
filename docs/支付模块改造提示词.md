# 支付模块改造提示词（Mock 支付渠道，企业级架构）

> 本文件是执行依据。执行者必须严格按本提示词修改，不得自行扩展、不得引入提示词之外的依赖或方案。
> 所有代码加中文注释，分层位置与现有项目保持一致。

## 一、目标与边界

### 1. 目标

在现有抢票链路上补齐"支付闭环"，采用企业通用的"统一下单 + 异步回调 + 主动查询兜底 + 超时关单"架构。因无真实微信/支付宝商户号，用本地 Mock 支付渠道替代外部渠道，但**链路结构、幂等、验签、状态机与真实企业方案一致**。

### 2. 本轮范围（只做后端）

- 订单金额落地、订单状态机扩展
- 支付流水表与支付链路（统一下单、模拟回调、验签、幂等）
- 用户主动取消、我的订单列表
- 支付超时自动关单（含 Redis/DB 回补）
- 安全配置放行回调地址

### 3. 明确不做（禁止）

- 不接入真实微信/支付宝 SDK、不引入新的外部支付依赖
- 不做 XA/TCC/Seata
- 不物理删除任何数据
- 不写通用 catch 兜底吞异常；不做无条件 UPDATE
- 不改写已有的扣减 Lua、预检 Lua、事务消息主流程（只允许在订单创建处补金额）
- 前端页面本轮不改

## 二、数据模型改造

### 1. 修改 `sql/05_b2_unified_stock.sql`（保持重置流程一致）

- `order` 表增加列：`amount DECIMAL(10,2) NOT NULL COMMENT '订单金额（元）'`，放在 `status` 之前
- 订单状态注释更新为：待确认/已确认/已支付/已取消
- 其余表结构与演示数据不变

### 2. 新建 `sql/09_payment_record.sql`（可重复执行）

```sql
DROP TABLE IF EXISTS `payment_record`;
CREATE TABLE `payment_record` (
    `id`               BIGINT       NOT NULL AUTO_INCREMENT COMMENT '自增主键',
    `payment_no`       VARCHAR(64)  NOT NULL COMMENT '支付单号（雪花），一次支付尝试一条',
    `order_no`         VARCHAR(64)  NOT NULL COMMENT '商户订单号',
    `channel`          VARCHAR(16)  NOT NULL COMMENT '支付渠道，固定 MOCK',
    `amount`           DECIMAL(10,2) NOT NULL COMMENT '支付金额，与订单金额一致',
    `status`           VARCHAR(16)  NOT NULL COMMENT '待支付/支付成功/支付失败/已关闭',
    `channel_trade_no` VARCHAR(64)  DEFAULT NULL COMMENT '模拟渠道交易号，回调成功才回填',
    `callback_count`   INT          NOT NULL DEFAULT 0 COMMENT '回调到达次数',
    `create_time`      DATETIME     NOT NULL COMMENT '创建时间',
    `update_time`      DATETIME     NOT NULL COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_payment_no` (`payment_no`),
    UNIQUE KEY `uk_channel_trade_no` (`channel_trade_no`),
    KEY `idx_order_no` (`order_no`),
    KEY `idx_status_update` (`status`, `update_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '支付流水表';
```

说明：`channel_trade_no` 待支付时为 NULL，MySQL 唯一索引允许多个 NULL，不影响多次发起支付。

### 3. 重置流程更新

引入支付表后，标准重置顺序变为：**05 SQL → 09 SQL → reset_redis.py → 预热 → 压测**（09 重建空支付流水表，避免旧支付数据干扰）。

## 四、新增代码清单与职责

### 1. 实体 `entity/PaymentRecord.java`

- 字段与表一一对应（map-underscore-to-camel-case 已开启）
- 定义状态常量：`STATUS_WAITING="待支付"`、`STATUS_SUCCESS="支付成功"`、`STATUS_FAILED="支付失败"`、`STATUS_CLOSED="已关闭"`；渠道常量 `CHANNEL_MOCK="MOCK"`

### 2. Mapper

- `mapper/PaymentRecordMapper.java` + `resources/mapper/PaymentRecordMapper.xml`，方法：
  - `int insert(PaymentRecord record)`
  - `PaymentRecord selectByPaymentNo(String paymentNo)`
  - `PaymentRecord selectSuccessByOrderNo(String orderNo)`：查该订单是否已有支付成功记录
  - `List<PaymentRecord> selectWaitingByOrderNo(String orderNo)`
  - `int casSuccess(...)`：条件更新 `WHERE payment_no=? AND status='待支付'`，置支付成功、回填 channel_trade_no
  - `int incrCallbackCount(String paymentNo)`：每收到一次回调 +1
  - `int casClose(String paymentNo)`：待支付 → 已关闭
- `OrderMapper` 增加：
  - `int insert` 之外补 `selectByUserId(Long userId)`：我的订单列表
  - `List<OrderRecord> listTimeoutConfirmed(...)`：查"已确认 + 距创建时间超过 900 秒"的订单，供超时任务逐单处理（再用 PaymentRecordMapper 判该单是否已支付成功）
- `OrderRecord` 增加 `amount` 字段与 `STATUS_PAID="已支付"` 常量；`OrderMapper.xml` 的 resultMap、insert、select 全部补 amount
- 新增 DTO 一律放 `dto` 包：`PrepayResponse`、`PaymentStatusVO`
- `StockMapper` 增加 `int restoreOneSegment(...)`：`UPDATE stock SET remain=remain+1, update_time=NOW() WHERE train_no=? AND seat_no=? AND segment_no=?`；XML 同步

### 3. Service

- `service/PaymentService.java` + impl，方法与处理规则：
  - `PrepayResponse prepay(String orderNo)`：
    1. 查订单，校验存在、属于当前登录用户、状态为已确认
    2. 校验金额非空
    3. 雪花生成 payment_no，插入待支付流水
    4. 调 MockPayChannel 生成 payToken，返回（paymentNo、orderNo、amount、payToken）
  - `String handleNotify(String rawBody, String signature)`：见第六节回调处理
  - `PaymentStatusVO status(String orderNo)`：返回订单状态 + 支付状态，供前端轮询
  - `void userCancel(String orderNo)`：见第七节
- `service/MockPayChannelService.java` + impl：
  - `String createPayToken(String paymentNo)`：生成并返回模拟支付凭证（可用 UUID 或雪花字符串），内部维护 payToken→paymentNo 映射（用 ConcurrentHashMap）
  - `void confirm(String payToken)`：校验 token 有效；生成 channel_trade_no（`MOCK`+雪花）；构造回调 JSON（orderNo、paymentNo、channelTradeNo、amount）；用 HMAC 工具对**原始报文**签名；在独立异步线程中用 JDK 自带 `java.net.http.HttpClient` POST 到 `http://localhost:8081/api/pay/notify`，请求头 `X-Mock-Signature`
  - 收到非 SUCCESS 应答时，最多重试 3 次（间隔 1 秒），同一报文同一签名
- `common/HmacSignUtil.java`：基于 JDK `javax.crypto.Mac`，HMAC-SHA256，方法 `sign(String secret, String content)` 与 `verify(...)`，不引入新依赖
- `StockService` 增加 `restoreRealStock(trainNo, seatNo, segments)`：`@Transactional` 内逐区段 `restoreOneSegment`，与扣减方向相反

### 4. Controller `controller/PaymentController.java`（前缀 `/api/pay`）

- `POST /prepay?orderNo=`：调 prepay，返回支付凭证
- `POST /mock/confirm`：入参 payToken，调 channel.confirm，立即返回"支付处理中"（模拟异步，不阻塞）
- `POST /notify`：接收原始请求体与 X-Mock-Signature 头，调 handleNotify，返回渠道要求的纯文本/JSON 应答
- `GET /status/{orderNo}`：返回支付状态
- `OrderController` 增加：
  - `POST /api/orders/{orderNo}/cancel`：用户主动取消
  - `GET /api/orders/my`：当前用户订单列表（OrderMapper 增加 selectByUserId）

## 五、订单状态机（改造后）

```
待确认 ──DB库存扣减成功──> 已确认 ──支付回调成功──> 已支付（终态）
  │                         │
  └──失败/对账取消──> 已取消   ├──用户主动取消/支付超时──> 已取消（终态，回补 Redis+DB）
```

- 支付只允许在"已确认"状态发起
- 已支付为终态，不可取消、不可重复支付
- 所有状态变更必须条件 UPDATE，靠影响行数判定

## 六、回调处理规则（handleNotify，严格按序）

1. **验签**：控制器用 `@RequestBody String rawBody` 接收原始报文（禁止先反序列化成对象再重算签名，避免字符串不一致）；用配置密钥重算 HMAC-SHA256 与 X-Mock-Signature 比对，失败直接返回 FAILURE，不做任何业务
2. 解析报文，按 paymentNo 查支付流水、按 orderNo 查订单；任一不存在 → 不返回 SUCCESS，告警并挂起，等重试/对账
3. **金额与订单校验**：回调金额必须同时等于订单金额与流水金额；channel、订单归属一并校验
4. 不匹配：不确认、不取消、不返回 SUCCESS，告警挂起（用户已付款，绝不能取消订单）
5. **幂等处理**：
   - 订单已为已支付：直接返回 SUCCESS（重复回调幂等）
   - 否则在一个事务内：支付流水条件 UPDATE（待支付→支付成功，回填 channel_trade_no）+ 订单条件 UPDATE（已确认→已支付）
   - 同订单其他待支付流水在本事务内一并条件关闭，避免残留
   - 影响行数为 0 视为已被处理，幂等返回
6. 事务提交成功后返回 `{"code":"SUCCESS"}`；先落库后应答

## 七、用户主动取消（userCancel）

1. 查订单，校验归属当前用户
2. 仅"已确认"可取消；已支付/已取消直接拒绝或幂等返回
3. 条件 UPDATE 订单 → 已取消
4. 回补 Redis（复用现有 rollback.lua，按 fromSeq..toSeq-1 区段）
5. 回补 DB（restoreRealStock，同区段）
6. 该订单全部待支付流水条件关闭
7. 任一步失败抛异常并告警，不伪装成功

## 八、支付超时关单定时任务 `task/PaymentTimeoutTask.java`

- `@Scheduled` 每分钟执行，分布式锁（SETNX + 过期，风格同 DeductReconcileTask）
- 用 `OrderMapper.listTimeoutConfirmed` 扫描"已确认 + 距创建时间超过 900 秒"的订单，每轮上限 200；时间基准统一为 order.create_time（演示口径，待确认阶段为秒级，对支付窗口影响可忽略）
- 逐单先用 PaymentRecordMapper 判该单是否已支付成功（模拟关单前查单），已成功则跳过；再处理其待支付流水
- 处理：条件 UPDATE 已确认→已取消 → 回补 Redis → 回补 DB → 关闭待支付流水
- 单条异常不中断，记录 + 告警继续

## 十一、运行时补测（2026-11-15，脚本 `jmeter/verify_payment_edge.py`）

自检清单第 6、8、11 项此前只有代码路径，没有运行时证据，本轮补测，12 项断言全过。

**项 6 —— 多次 prepay 关闭其余流水**

订单 `380385237328203776` 连续 prepay 两次，生成两条「待支付」流水（`...336064` / `...582272`）。用第一张凭证确认后：

| 流水 | 状态 |
|---|---|
| ...336064 | 支付成功 |
| ...582272 | 已关闭 |

再用第二张凭证确认 → `http=200, msg=支付单不存在或已处理`。说明「同订单只留一条能付的流水」是靠回调事务里的批量 `casClose` 完成的，不是靠 prepay 时拦截。

**项 8 —— 金额不匹配挂起**

订单 `380385239626682368`（真实金额 100.00），用真实 secret 签名但把 `amount` 改成 `0.01` 伪造回调：

- 应答 `{"code":"FAILURE"}`，不返回 SUCCESS
- 订单仍「已确认」、流水仍「待支付」——没有取消，也没有确认
- 紧接着用真实凭证支付 → 正常变「已支付」，证明挂起没有把订单锁死

这条最关键的是「**不取消**」：用户钱已经付了，只是我们校验不过，取消订单等于把用户的票抢走。

**项 11 —— 超时关单**

订单 `380385241883217920` 下单后库存 98→97，把 `create_time` 回退 20 分钟让 `PaymentTimeoutTask`（900 秒阈值）命中，49 秒后（下一个整分）关单完成：

- 订单 → 已取消
- 待支付流水 → 已关闭
- 库存 97→98 精确回补 1

**锁释放已统一（2026-11-15 修改）**：`PaymentTimeoutTask` 原来在 `finally` 里主动 `delete` 锁，`DeductReconcileTask` 同样如此，而 `RefundReconcileTask` 只靠 TTL 过期。三处行为已统一为**只靠 TTL、不主动删除**。

原因：`delete(LOCK_KEY)` 只认 key 名字、不认持有者。若本轮执行超过 55 秒，锁已过期并被另一实例持有，`delete` 删掉的是别人的锁，会导致下一轮出现两个实例并发——超时关单这条路径尤其危险，重复执行会把同一订单的库存回补两次。三个任务都是每分钟触发一次，锁多占几十秒没有实际代价，纯 TTL 是风险最低的选择。

（生产级若确实需要主动释放，正确做法是 value 存随机持有者标识、delete 前用 Lua 原子校验 value 再删；本项目未采用。）
