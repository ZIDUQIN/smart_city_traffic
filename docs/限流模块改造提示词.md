# 限流模块改造提示词（全局限流层）

> 执行依据文档。写完后自检两次，通过后严格按本文件执行。
> 项目：`D:\IDEAproject\smart-city-traffic`，包根 `com.smartcity.traffic`

---

## 一、背景

下单接口已有**单用户限流**（令牌桶，key `rate:{userId}:{trainNo}`，容量 3/每秒补 1），
作用是防单个用户反复刷单。

但它不解决另一个问题：**万人级洪峰同时涌入时，系统入口会被打穿**。

实测数据基线：

| 链路 | 实测能力 |
|---|---|
| 写链路（完整走完下单主流程） | 451 TPS |
| 读链路（三级缓存） | 2442 TPS |
| Tomcat accept-count | 500 |
| Tomcat 最大线程 | 400 |

结论：若出现 1 万 QPS 瞬时涌入，连接队列会先满，大量请求 Connection refused。
需要在**最外层加一道全局限流**，把超量请求在入口快速拒绝，不让它占用 Tomcat 线程。

## 三、设计规范

### 3.1 两层限流的定位

| 层 | key | 容量/速率 | 保护对象 | 拒绝语义 |
|---|---|---|---|---|
| 外层：全局 | `rate:global:{trainNo}` | 500 / 每秒补 500 | 系统容量（Tomcat/DB） | 当前抢票人数过多 |
| 内层：单用户 | `rate:{userId}:{trainNo}` | 3 / 每秒补 1 | 业务公平（防单人刷单） | 操作过于频繁 |

执行顺序：**外层全局 → 内层单用户 → 后续业务**。
理由：容量闸门优先，容量不够后面的判断都没有意义。

### 3.2 阈值依据

- 全局限流阈值 500/秒，参照写链路实测 451 TPS 取略高值。
- 取略高而非取低的原因：全局限流位于预检**之前**，被放行的请求中大部分会在预检被挡（无票/重复），
  真正落到 DB 的远小于 500。若阈值压到 400 以下，会误伤正常的均匀流量。
- 配置化，不写死，后续可按压测数据调整。

### 3.3 Lua 复用

`resources/lua/rate_limit.lua` 已实现参数化令牌桶（KEYS[1] 为桶 key，ARGV 为容量/速率/时间/ttl），
**同一脚本可直接用于两个 key**，无需新增脚本。

## 四、代码改动清单

### 4.1 `service/RateLimitService.java`

新增方法：

```java
/**
 * 全局（按车次）限流：保护系统入口容量。
 *
 * @param trainNo 车次号
 * @return true 放行；false 触发全局限流
 */
boolean tryAcquireGlobal(String trainNo);
```

保留原 `tryAcquire(Long userId, String trainNo)` 不变。

### 4.2 `service/impl/RateLimitServiceImpl.java`

- 新增两个配置注入：`rate-limit.global.capacity`（默认 500）、`rate-limit.global.refill-per-second`（默认 500）
- 新增私有方法生成全局 key：`rate:global:{trainNo}`
- `tryAcquireGlobal` 复用同一个 `rateLimitScript`
- 把「ttl 计算 + execute + 判定」抽成私有方法 `acquire(String key, int capacity, int refillPerSecond)`，
  单用户与全局共用。**抽取不得改变原 tryAcquire 的 ttl 计算结果**
  （原为 `capacity * 1000L / Math.max(1, refillPerSecond) + 60000L`，逐字符保持一致）

### 4.3 `service/impl/OrderServiceImpl.java`

在 `createOrder` 中，单用户限流**之前**插入全局限流：

```
validate(request)
  ↓
【新增】全局限流 tryAcquireGlobal(trainNo) → false 抛 RateLimitException("当前抢票人数过多，请稍后再试")
  ↓
单用户限流 tryAcquire(userId, trainNo) → false 抛 RateLimitException("操作过于频繁，请稍后再试")
  ↓
isAvailable / 乘车人归属校验 / 预检 / MQ ...
```

注意：`userId` 的获取位置需保持在全局限流之后（全局限流不需要 userId）。

### 4.4 `resources/application.yml`

在现有 `rate-limit:` 节点下新增嵌套配置：

```yaml
rate-limit:
  capacity: 3
  refill-per-second: 1
  global:
    capacity: 500
    refill-per-second: 500
```

### 4.5 验证脚本

扩展 `jmeter/verify_rate_limit.py`，新增「全局桶」验证场景：确认 `rate:global:{trainNo}`
与单用户 key 使用同一脚本、行为一致、互不干扰。

## 五、禁止事项

1. 禁止把全局 key 写成 `rate:{trainNo}`，避免与单用户 key 的 `{userId}` hash tag 混淆语义。
2. 禁止在 `tryAcquireGlobal` 里新增 HGET/HSET 等直接 Redis 命令，必须走 Lua。
3. 禁止为了"省一次调用"把两层限流合并成一个 Lua 脚本——两层语义不同，合并后无法独立调整阈值。
4. 禁止修改 `RateLimitException → 429` 的映射。
5. 禁止在限流失败分支里做任何副作用；**也不加日志**。洪峰下每个被拒请求打一行 warn，
   日志本身就会成为瓶颈（磁盘 IO 和字符串拼接），可观测性由 429 响应码本身承担。
6. 禁止给限流加 try-catch 降级（见第七节 fail-close 策略）。

## 六、对既有压测结论的影响（必须提前告知）

**这是本次改造最重要的副作用，必须写清楚，否则会被误判为"压测坏了"。**

现有写压测计划：1000 线程 / 1 Loop / SyncTimer 1000-10000ms，即**约 1 秒内涌入 1000 个请求**。

加了全局限流（500/秒）之后：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 成功下单 | 100 单（库存打满） | 100 单（不变） |
| 被限流拒绝 | 0 | **约 500 个** |
| 错误率 | 0% | **约 50%** |
| 零超卖 | 是 | **仍是** |

**结论：错误率上升是限流生效的预期表现，不是 bug，也不是超卖回归。**
零超卖这条生死线不受影响，因为限流只是让请求"进不来"，不会让库存账目错乱。

若要在压测中复现"0 错误"的旧结论，把全局阈值临时调高：

```yaml
rate-limit:
  global:
    capacity: 10000
    refill-per-second: 10000
```

压测完再调回 500。**这一步必须做，否则下次压测会得出错误判断。**

## 七、fail-close 策略（不降级）

限流依赖 Redis。若 Redis 异常，`redisTemplate.execute` 会抛异常，直接冒泡成 500，**不做 try-catch 兜底放行**。

理由：
- Redis 在本项目中是**核心依赖**，库存扣减、乘车人判重全在 Redis。Redis 挂了，下单链路本来就不可能成功。
- 此时"降级放行"只会让请求涌入一个注定失败的下游，白烧 Tomcat 线程和 DB 连接。
- 快速失败（让用户看到"系统繁忙"）比假装放行、最后在更深处失败更诚实。

面试可讲：**限流组件的 fail-open / fail-close 取决于它保护的下游是否强依赖同一组件**。
同源的强依赖选 fail-close，独立的旁路组件（如日志、埋点）选 fail-open。

| # | 检查项 | 判定标准 |
|---|---|---|
| 1 | 全局 key 格式 | `rate:global:{trainNo}`，含 hash tag |
| 2 | 单用户 key 未变 | 仍为 `rate:{userId}:{trainNo}` |
| 3 | Lua 未新增 | `resources/lua` 下文件数与执行前一致 |
| 4 | 两种限流阈值独立可配 | 改 yml 一项不影响另一项 |
| 5 | 执行顺序 | 全局在单用户之前 |
| 6 | 拒绝语义区分 | 全局"人数过多"、单用户"过于频繁" |
| 7 | 状态码 | 两者均为 429 |
| 8 | 不变量 | 限流未通过时不查 DB、不进预检、不发 MQ |
| 9 | 编译 | mvn compile exit 0 |
| 10 | 脚本行为 | 连打 N 次、前 N 次放行，N+1 拒绝，等待后恢复 |
| 11 | 压测影响已知会 | 已在第六节写明错误率会升至约 50%，且零超卖不受影响 |
| 12 | 无降级 | 代码中不存在包住限流的 try-catch 放行 |

### 附：Cluster 下的 hash tag 说明

- 单用户 key：`rate:{userId}:{trainNo}` → hash tag = `{userId}`
- 全局 key：`rate:global:{trainNo}` → hash tag = `{trainNo}`

两者落到**不同 slot**。这不构成问题，因为**每次 Lua 调用只操作一个 key**（单 key 脚本不涉及跨槽）。
真正的 CROSSSLOT 风险只出现在"一个脚本里同时操作多个 key 且它们不同槽"，库存三件套就是靠统一
`{trainNo}` 解决的；限流这里不存在多 key 操作，所以 tag 可以各按各的语义取。

## 附：限流下零超卖补测（2026-11-15）

**为什么补测**：限流上线后跑 1000 线程只成交 3 单。根因是 1000 个线程共用同一个 admin token（user_id=1），单用户桶 capacity=3 只放 3 个——测出来的不是"业务层能撑多少并发"，而是"单用户桶有多严"。简历上的零超卖数据因此只能用限流前的旧压测，缺一条"限流生效时仍然零超卖"的证据。

**方法**：只把 `rate-limit.capacity` 临时调到 1000（单用户桶不再卡），全局限流保持 `500/500` 不动，重启后跑 1000 线程。

**数据基线**：订单表清空，DB 库存 二等 100/100、一等 20/20、商务 5/5，Redis 预热 100/100。

**结果**：

| 指标 | 数值 |
|---|---|
| 样本数 | 1000，HTTP 全 200，失败 0 |
| 成交订单 | **100 单**（订单表 100 行，状态全「已确认」） |
| DB 库存 | 二等 0/0（两段全耗尽），一等、商务未动 |
| Redis 库存 | 0/0，与 DB 一致 |
| 响应分布 | 100 抢票成功 / 875 余票不足 / 25 乘车人已购 |
| 耗时 | 平均 1145ms，最大 1524ms，最小 319ms |

**结论**：100 张库存恰好 100 单，第 101 单不存在，超卖数为 0。限流层只做流量整形、不参与正确性判断，扣减正确性仍由 Lua 原子扣减 + 唯一索引保证。

**两个坑（面试可讲）**：

1. **JMeter 的 `bytes` 列含响应头**，不是 body 长度。结果里 490 字节看着像失败响应，但手工发「余票不足」只有 165 字节，对不上；用 `jmeter/probe_oversell_response.py` 发 100 并发复现才确认——490 = 响应头 325 + body 165。看 JTL 不能只盯 bytes 猜语义。
2. **乘客 CSV 只有 200 个乘客（2001~2200）重复用 5 次**，所以出现 25 个「该乘车人已购买此车次车票」。这是重复乘客撞幂等检查，不是超卖，也不影响成交数（库存耗尽后大部分请求走「余票不足」，压根进不到建单阶段）。

**配置已恢复**：压测结束后 `rate-limit.capacity` 已改回 3。
